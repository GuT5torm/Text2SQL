# fix_empty —— 空结果回灌

上一条 SQL **执行成功**，但返回 0 行。这不是语法或字段错误，语句本身能跑，
只是条件把数据筛没了。请判断「条件太严」还是「确实没有数据」。

## 两种答案，选一种

**A. 放宽条件后重写。** 只在下面两条边界内放宽：

- 放宽**时间区间的端点**（如近 7 天 → 近 30 天、本月 → 近三个月）；
- 放宽**枚举取值范围**（如某个品类 → 该品类所属的一级类目、某个城市 → 所在大区）。

**B. 确认无数据。** 判断该条件下确实没有记录时，输出 `confirm_no_data: true`
并在 `reasoning` 里写清依据（例如「该区间内订单表无记录」），不输出语句。

## 硬边界

1. **不得移除时间过滤**。整条删掉 `WHERE created_at >= ...` 也能凑出行数，
   但那样得到的不是用户问的那段时间。只允许移动端点。
2. **不得移除维度过滤**。把 `WHERE region = '华东'` 整条删掉同样能凑出行数，
   得到的却是全域口径，与问题不是同一件事。只允许把取值放宽到更粗的粒度。
3. **不得跨入未走完的周期**。当前数据截止到 {data_cutoff}，把区间放宽到
   包含尚未走完的周期（如本月）会得到不完整周期与完整周期的混合值，不能当作
   可比数据。放宽后的区间右端点不得超过数据截止日期。
4. **只放宽一次**。这是本轮唯一一次回灌机会，之后无论有没有数据都会直接出结论。

## 为什么限制这么死

空结果回灌最大的风险不是拿不到数据，而是拿到**看起来有数据但口径已经变了**的
结果。使用者不会去核对条件被改成了什么，他只会看到结论里的数字。放宽一旦越过
上面四条边界，这个数字就与提问无关了，比直接说「没有数据」更糟。

## 输出格式

只输出 JSON：

```json
{
  "confirm_no_data": false,
  "sql": "放宽条件后的完整 SQL",
  "reasoning": "放宽了什么，以及为什么认为放宽后仍能回答原问题",
  "metric_used": ["成交总额"]
}
```

判定确认无数据时：

```json
{
  "confirm_no_data": true,
  "sql": "",
  "reasoning": "确认无数据的依据",
  "metric_used": []
}
```
