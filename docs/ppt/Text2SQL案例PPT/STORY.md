# STORY.md · Text2SQL 案例 PPT

## 一、意图对齐

- **目标受众**：课程答辩与教学案例评审场景下的评审老师与技术听众。他们关心三件事：这个系统解决了什么问题、为什么可信、数字是怎么测出来的。
- **核心目标**：讲完后观众相信「口径集中配置 + 执行前校验」是可信文本转 SQL 的关键，而不只是搭了个能调模型的界面；记住三条硬约束与九条守卫规则的存在；照提纲复述评测方法时能指出数字来自哪里。
- **页数**：12 页，Hero 页 3 个（封面、状态机、总结），占 25%。
- **视觉调性**：工程感、克制、信息密度高、蓝色系、无装饰插画。
- **内容边界**：
  - 必讲：痛点链路、六层架构、八节点链路与重试回环、语义层配置、SQL 安全沙箱、评测方法与判据。
  - 不讲：模型训练、Prompt 逐字内容、部署运维细节、与其他产品的横向对比。
  - 禁碰：未实测的数值、未取得的截图、红绿涨跌语义色。

## 二、页面骨架

按「问题 → 方案 → 实现 → 验证 → 收束」五段铺开，共 12 页，无目录页与章节扉页。

| 段 | 页码 | 内容 |
|---|---|---|
| 问题 | 01–02 | 封面、业务取数的等待链路 |
| 方案 | 03 | 一句话到可信结果 |
| 实现 | 04–08 | 架构、状态机、语义层、安全沙箱、技术栈 |
| 验证 | 09–10 | 运行演示、评测结果 |
| 收束 | 11–12 | AI 共创开发流程、总结与演进 |

Hero 页定位：01 封面、05 状态机与重试回环、12 总结。三者互不相邻，中间均隔有支撑页。

Hero 页数量 3 / 12 = 25%，落在 20–30% 区间。

节奏曲线：P1 peak → P2 valley → P3 valley → P4 peak → P5 peak → P6 valley → P7 peak → P8 valley → P9 peak → P10 valley → P11 valley → P12 peak。最长连续 valley 为 2 页（P2–P3、P10–P11），未触及「连续 3 页 valley 必须打断」的门禁。

版式预算：非对称版式 9 页（75%），对称版式 3 页（P1 封面全屏视觉、P9 上下分栏、P12 三栏清单）。其中「非对称双栏」用在 P2、P5、P7、P10 共 4 页，占 33%，未超过 40% 上限；「左大图+右侧文字」不使用。

## 四、数据与判据的对应关系

关键数值一律写明来源，JSON/XML/评测报告以外的数字不出现在页面上。

- 九条守卫规则、八业务节点、三条终态：取自 `backend/app/db/guard.py` 与 `backend/app/agent/graph.py`。
- 七层依赖的版本号：取自本机 `backend/.venv` 的 `pip list` 结果。
- 评测题数、三组通过率：`backend/eval/report.json`，本版留占位，回填时逐项对照。
- 演示截图：`llm_mock=false` 的真实运行记录，本版留占位。
