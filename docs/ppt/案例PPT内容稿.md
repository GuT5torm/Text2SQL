1. **文本框必须可编辑。** 架构图、流程图、表格与文字全部用 PPT 原生形状与文本框实现，不贴图片。需要图形的地方用矢量绘制，不使用模型生成的示意图。

## P2 场景痛点：业务取数的等待链路

**标题**：业务要一个数，要等多久

**核心信息**

传统取数链路：业务提需求 → 沟通口径 → 数据分析师排期 → 写 SQL → 复核 → 出结果。链路上有三处损耗：

| 损耗 | 表现 |
|---|---|
| 等待 | 排期以天计，临时需求插不进队列 |
| 口径歧义 | 「销售额」是否扣退款，双方理解不同，数出两版 |
| 重复劳动 | 相似问题反复写，SQL 不复用，口径不沉淀 |

BI 看板解决了固定报表的问题，解决不了临时提问。看板的维度与指标在建看板时就固定了，换一个切分角度就要提需求。

**版式元素**

- 左侧：纵向五步流程图（提需求 → 沟通口径 → 排期 → 写 SQL → 出结果），每步下方标注耗时量级。
- 右侧：三行表格，列出三处损耗。
- 底部一行结论：问题的核心不是「写 SQL 慢」，而是「口径没有沉淀，每次都要重新确认」。

**演讲要点**

强调第三点。Text2SQL 的价值不只是省掉写 SQL 的时间，更重要的是把口径从人的记忆里搬到可维护的配置文件里。

**素材要求**：流程图用矩形 + 箭头绘制，文本框可编辑。

## P3 解决方案：一句话到可信结果

**标题**：一句话进来，可追溯的结果出去

**核心信息**

四个能力构成闭环：

1. 自然语言提问，不要求用户知道表结构。
2. SQL 全程可见，可展开核对，不是黑盒。
3. 口径显式标注，每个数字都带统计范围说明。
4. 结果自动配图表，同时保留表格。

**「可信」的三条判据**

| 判据 | 实现方式 |
|---|---|
| 口径可追溯 | 指标口径集中配置，结果区展示命中口径 |
| 过程可核对 | SQL 面板展示实际执行语句 |
| 越权不会发生 | 守卫七条规则在 SQL 执行前拦截，执行超时由仓储层单独中断 |

**版式元素**

- 中部横向四段式流程：提问 → 生成 → 校验 → 结果。
- 下方三列表格，列出「可信」的三条判据与实现方式。

**演讲要点**

这一页是全篇的论点。后面 P5 到 P7 分别展开校验、语义层与安全，都是为「可信」服务。

**素材要求**：无。

## P4 系统架构总览

**标题**：六层职责，单进程部署

**核心信息**

| 层 | 职责 | 关键约束 |
|---|---|---|
| 接入层 | FastAPI 路由、SSE 推送、静态资源 | 不含业务逻辑 |
| 编排层 | LangGraph 状态机、节点与条件边 | 节点内不直接连数据库 |
| 语义层 | 指标口径、表元数据、同义词 | 无 LLM 调用，无 SQL 执行 |
| LLM 网关 | 模型调用、结构化输出、用量统计 | 唯一的外部调用出口 |
| 数据访问层 | 只读连接、安全守卫、结果封装 | 唯一的 SQL 执行出口 |
| 前端 | 对话区、结果区、图表与历史 | 不参与校验与生成 |

**三条硬约束**

- `agent/nodes/` 下不出现数据库连接。
- `semantic/` 下不出现 LLM 调用与 SQL 执行。
- 密钥只在 `.env`，不进代码与日志。

**为什么是模块化单体而非微服务**：单机演示场景，一条问答的瓶颈在模型调用而非服务间通信。拆成微服务会引入网络、注册与部署复杂度，收益为零。模块之间用函数调用，边界靠目录与约束保证，需要拆的时候按层切即可。

**版式元素**

- 主体为六层纵向分层图，每层一个矩形，右侧标注该层职责，左侧标注关键约束。
- 图的右侧用一条纵向箭头标出一次问答的流向：接入 → 编排 → 语义 → 网关 → 编排 → 数据 → 接入。
- 底部一行小字：单进程 FastAPI，无消息队列、无 Redis、无向量库、无容器编排。

**演讲要点**

重点讲三条硬约束。它们听起来平淡，但决定了这个系统能不能长期维护：语义层不调模型，意味着口径变更不需要动生成逻辑；节点不连数据库，意味着编排层可以单测。

**素材要求**：分层图用矩形 + 箭头绘制，全部为可编辑形状。

## P5 Agent 状态机与重试回环

**标题**：八个业务节点，三条出口

**核心信息**

八业务节点：`route`（意图识别）→ `retrieve`（口径召回）→ `generate`（生成 SQL）→ `validate`（安全校验）→ `execute`（执行）→ `fix`（修正）→ `visualize`（图表决策）→ `summarize`（生成结论）。

三条终态：`respond`（正常回答）、`clarify`（信息不足，回问）、`give_up`（重试耗尽，给出失败原因）。

合计十一个节点。标题写「八个业务节点」，正文说清终态另计，避免口头讲成十个。

**重试回环的两个设计选择**

**第一，`fix` 回到 `validate` 而不是 `execute`。** 修正后的语句可能引入新的越权或语法问题，必须重新走一遍完整校验，不能跳过校验直接执行。

**第二，把原始报错原样回传给模型。** `no such column: x` 直接告诉模型字段写错了，`R7 JOIN 缺少 ON 条件`直接指出连接条件缺失。让模型自查，它往往重新写一条风格不同的查询，可能引入新的错误。原样回传比让模型推理更有效。

**进度反馈**

每个节点完成时通过 SSE 推一条 `stage` 事件，前端进度条依次点亮。一次问答要等模型多轮响应，没有进度反馈的界面会让人以为卡死。

**版式元素**

- 主体为状态机图，八节点横向排布，三条终态在右侧。
- `fix` 到 `validate` 的回环用一条明显的回向箭头，标注「最多 N 次」。
- 图的下方用两行文字说明上述两个设计选择。
- 右下角一个小示意：`stage` 事件的四个字段（`node` 节点名 / `label` 展示文案 / `status` 进行中与已完成 / `detail` 可读详情，例如「R7 缺少 JOIN 条件」「第二次修正」）。

**演讲要点**

回环这一页是技术含量的集中体现。两个「为什么」要讲清楚，尤其是「回到 validate 而不是 execute」——这是安全设计，不是性能考虑。

**素材要求**：状态机图用圆角矩形 + 箭头绘制。回环箭头用不同颜色区分。

## P6 语义层：口径从猜测到显式配置

**标题**：口径写在配置里，不在模型的猜测里

**核心信息**

NL2SQL 的困难不在语法，在三处：口径歧义、字段编造、范围理解。语义层解决第一处与第三处。

**三份配置**

| 文件 | 内容 | 数量 |
|---|---|---|
| `metrics.yaml` | 指标口径：口径表达式、依赖表、必带条件、可用维度、边界说明 | 7 个指标 |
| `tables.yaml` | 表与字段元数据、枚举值说明 | 6 张表、9 类维度 |
| `synonyms.yaml` | 业务黑话映射、枚举值口语、相对时间词 | — |

**口径表达式写成 SQL 片段，不写自然语言**

写成「金额加起来」，模型每次的组合方式都可能不同；写成 `SUM(oi.quantity * oi.unit_price)`，结果就固定了。

边界说明写清「不含什么」：成交总额不含已取消订单、不扣退款；退款率以订单数为分母而非金额。

**一份元数据三处消费**

表结构元数据同时供 Prompt 拼接、守卫白名单校验、前端展示使用。同一份配置供三处使用，避免「Prompt 里写的字段」与「守卫校验的字段」不一致。

**相对时间由代码换算**

「上个月」这类词换算成左闭右开的日期区间后写进 Prompt，并明确告诉模型不要重新解释。这一步消除的是模型对日期的自行推断。

**版式元素**

- 左侧：三份配置的清单。
- 右侧：一个指标口径的展开示例，用表格列出名称、口径表达式、依赖表、边界说明。
- 中部：一条从配置到三个消费方的分叉箭头，标注「Prompt 拼接 / 守卫白名单 / 前端展示」。
- 底部：一行相对时间换算示例，标出左闭右开。

**演讲要点**

「口径表达式写成 SQL 片段」是这一页的核心论点。它把「让模型理解业务」变成「让模型引用配置」，准确率提升主要来自这里。

**素材要求**：示例用真实配置文件中的指标，不使用构造内容。

## P7 SQL 安全沙箱：七条校验规则与一层执行期保护

**标题**：执行前的最后一道闸

**核心信息**

守卫共七条规则，按固定顺序执行；语句超时不是守卫规则，由仓储层在执行时中断。

| 规则 | 含义 | 拦截后 | 实现位置 |
|---|---|---|---|
| R1 SINGLE_STATEMENT | 只允许单条语句 | 拦截 | 守卫 |
| R2 SELECT_ONLY | 只允许查询类语句 | 拦截 | 守卫 |
| R3 FORBIDDEN_KEYWORD | 不得出现 DDL / DML / 管理类关键字 | 拦截 | 守卫 |
| R4 TABLE_NOT_ALLOWED | 表必须在语义层登记 | 拦截 | 守卫 |
| R5 COLUMN_NOT_ALLOWED | 字段必须存在于所属表元数据 | 拦截 | 守卫 |
| R7 CARTESIAN_JOIN | 多表查询必须带连接条件 | 拦截 | 守卫 |
| R6 LIMIT_ENFORCED | 无 LIMIT 或超限时自动包裹 | 自动改写 | 守卫 |
| R8 STATEMENT_TIMEOUT | 执行超时中断 | 中断 | 仓储层 |

表格顺序即校验顺序，R7 排在 R6 之前。R6 会把语句包裹成 `SELECT * FROM (...) AS _guard_limited LIMIT 1000`，若先执行 R6，R7 面对的 `FROM` 只剩一个派生表，连接条件检查会恒定通过。

**三层纵深防御**

1. **AST 校验**：用 sqlglot 解析语句树后逐条比对，不做字符串匹配。字符串匹配会被注释、字符串字面量与换行绕过。
2. **只读连接**：业务库以只读模式打开。即便守卫被绕过，写操作也无法落盘。
3. **超时与扫描行数限制**：由 SQLite 的 progress handler 实现，避免一条慢查询拖死进程。

**R6 是唯一自动改写的规则**。守卫的其余六条一律拦截，不做「善意修正」——自动改写越多，行为越不可预测。

**R4 与 R5 顺带解决了字段编造**。模型按一般电商库的习惯写出 `orders.amount` 这类不存在的字段，白名单直接在执行前拦下，报错原样回传给模型重试。

**版式元素**

- 主体为七条规则的表格，R6 一行用不同底色标出「唯一自动改写」，R8 一行另用底色标出「实现在仓储层」。
- 右侧一列小图：AST 校验 → 只读连接 → 超时限制，三层叠加。
- 底部一行：拦截率与拦截次数统计（实测后填入，未实测则删除本行）。

**演讲要点**

强调「不做善意修正」这个设计选择。自动改写看起来友好，实际上让系统行为不可预测，出问题难以复现。

**素材要求**：表格用 PPT 原生表格。七条规则的名称与含义按实际代码填写。

## P10 评测结果与准确率

**标题**：准确率怎么测，测出来是多少

**核心信息**

**评测集构成**：20–30 题，按难度分三层（简单 40%、中等 40%、困难 20%），覆盖全部 7 个指标与 9 类维度，每个指标至少 2 题。另留 3–5 题负例，用于检验拦截与澄清分支。

**为什么比对结果集而不是 SQL**：同一结果可以有多种写法，JOIN 与子查询、HAVING 与外层 WHERE 都算对。用标准 SQL 做唯一判据会把正确的回答判成错误。改为执行后比对结果集，忽略列顺序，浮点数按相对误差比较。

**评测指标**

| 指标 | 定义 |
|---|---|
| 结果一致率 | 主指标，执行结果与标准结果集一致的比例 |
| 执行成功率 | 生成 SQL 能成功执行的比例 |
| 口径命中率 | 召回指标与标注指标一致的比例 |
| 平均尝试轮次 | 走完链路平均经历几次生成 |
| P95 端到端耗时 | 95 分位问答耗时 |

**结果**（以下数值位置留空，评测跑完后填入；未跑则不填，本页改为只讲方法）

- 口径命中率：＿＿
- 平均尝试轮次：＿＿

**数字使用规则**：上述数值必须来自评审记录中真实跑出的评测结果。未跑出实测值时，删除结果区、只保留方法说明，不得填入估算值或示例值。

**版式元素**

- 左侧：评测集构成的三层难度分布。

## P11 AI 共创开发流程回顾

**标题**：人和 AI 各自负责什么

**核心信息**

本项目全程采用 AI 共创模式开发，分工如下：

| 阶段 | 人负责 | AI 负责 | 人审查 |
|---|---|---|---|
| 需求 | 定范围、定优先级 | 生成 PRD 初稿、补全视角 | 删减、确认不做的事 |
| 设计 | 定交互与布局约束 | 生成 UIUX 初稿、给出组件清单 | 核对契约与状态覆盖 |
| 任务 | 定依赖与里程碑 | 拆解任务、排序 | 核对关键路径 |
| 编码 | 定边界与约束 | 写实现代码 | 检查三层约束是否被遵守 |
| 测试 | 定评测集与判据 | 生成用例与脚本 | 检查标准答案是否正确 |

**三条经验**

**第一，先定约束再让 AI 写。** 约束写在前面，AI 生成的代码才不会越界。本项目把「节点不连数据库」「语义层不调模型」写成硬约束后，生成代码的结构明显稳定。

**第二，AI 生成的中间数值需要核对。** 未明确给出的数值会被补全。凡是要在汇报中出现的数字，必须逐项核对来源。

**第三，报错原样回传比让 AI 自查有效。** 这一条同时适用于模型修 SQL 和人让 AI 改代码：给出具体报错，比说「这里有问题，你看看」得到的修改更准确。

**版式元素**

- 主体为五行三列的表格：阶段 / 人负责 / AI 负责 / 人审查。
- 底部三条经验，每条一行。

**演讲要点**

第二条经验值得多讲一点。这是实践中最容易出问题的地方：生成物看起来完整且合理，但其中的数字可能是补出来的。

**素材要求**：无。

## P12 总结与后续演进
