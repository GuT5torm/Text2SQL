# 12 — 核心技术实现语料库

## NL2SQL 的难点

自然语言转 SQL 的困难不在语法，而在三处：

**口径歧义。** 「销量」可能指订单数也可能指商品件数；「销售额」是否扣退款、是否含取消订单，都是口径问题。同一句话两次问，模型可能给出两个不同的数。

**字段编造。** 模型按一般电商库的习惯写出本库不存在的字段，例如 `orders.amount`、`products.price`。语句语法正确，执行时报错。

**范围理解。** 「上个月」是自然月还是最近 30 天，「上个季度」的起止是哪两天，模型自行解释容易出错。

本项目的三个核心实现分别针对这三点：语义层口径定义解决第一点，字段白名单与错误回传解决第二点，相对时间词由代码换算解决第三点。

## 语义层口径定义

### 指标口径配置

每个指标包含：名称、显示名、同义词、口径表达式、依赖表、必带条件、可用维度、边界说明、单位、示例问法。

口径表达式写成可直接嵌入 SQL 的片段，不是自然语言描述。写成「金额加起来」，模型每次的组合方式都可能不同；写成 `SUM(oi.quantity * oi.unit_price)`，结果就固定了。

边界说明写清「不含什么」。例如成交总额不含已取消订单、不扣退款；退款率以订单数为分母而非金额。

### 表结构元数据

逐表列出字段名、类型、中文名、枚举值说明与备注。它同时供三处使用：

| 用途 | 消费方 |
|---|---|
| 拼接 Prompt 的表结构段落 | `retrieve` 节点 |
| 表与字段白名单校验 | 安全守卫 |
| 前端展示与调试 | 语义层接口 |

同一份配置供三处使用，避免「Prompt 里写的字段」与「守卫校验的字段」不一致。

### 同义词与相对时间词

同义词把业务黑话映射到标准字段或指标，例如「卖了多少钱」映射到成交总额。

相对时间词由代码换算成左闭右开的日期区间后写进 Prompt，并在 Prompt 中明确告诉模型不要重新解释相对时间。这一步消除的是模型对日期的自行推断。

### 召回策略

起步用规则匹配，不引入向量数据库。流程为：同义词归一与短语命中打分，字符二元组重叠度兜底，按命中的指标反查依赖表，最后渲染成 Prompt 段落。

召回子集而不是全库 schema，有三个好处：Prompt 长度可控、无关字段不干扰模型、无额外依赖。

**切换触发条件**：表数量超过约三十张，或规则匹配的漏召回在评测集上可观测地拉低准确率时，替换 `retrieve` 节点为向量检索。

## 重试修正回环

### 为什么把报错原样回传

数据库或守卫给出的原始报错，信息量远大于让模型自查。`no such column: x` 直接告诉模型字段错了，`R7 JOIN 缺少 ON 条件`直接指出连接条件缺失。

让模型自查，它往往重新写一条风格不同的查询，可能引入新的错误。

### 回环结构

```
generate → validate ─┬─ 通过 → execute ─┬─ 成功 → visualize → summarize
                     └─ 失败 → fix ─────┘
                                │
                                └──── 失败 → fix（共享配额）
```

修正后回到 `validate` 而不是直接 `execute`，不允许绕过校验。

校验与执行共享重试配额，达到上限后进入 `give_up`，返回包含最后一次语句与报错的可读说明，而不是无限循环消耗 token。

### 修正 Prompt 的写法要点

四个要求写进 Prompt：

1. 尊重报错原因，报错说什么就改什么，不要顺手改动无关部分；
2. 保持口径不变，只针对语法与字段错误；
3. 不要重复上一版的错误，明确列出本次改了什么；
4. 携带历史修正记录，避免两次修正之间来回横跳。

第 4 点容易被忽略。没有历史记录，模型可能在两个错误方案之间反复切换。

## 图表类型决策规则

### 两条路径

模型输出为主，规则兜底。模型给出图表类型与字段映射，规则模块依据结果集结构生成兜底配置。

模型输出不通过字段校验时退回规则决策，因此模型出错时仍能产出可渲染的图表。

### 决策表

| 结果集特征 | 类型 |
|---|---|
| 横轴是时间且行数大于 3 | 折线 |
| 单个维度对比且行数不超过 30 | 柱状 |
| 问占比构成，单度量且维度取值不超过 12 个 | 饼图 |
| 列数超过 4，或无数值度量，或维度组合复杂 | 表格 |

补充规则：单行单列用表格；行数超过 30 的柱状图改折线或表格。

### 字段映射校验

模型给出的 `x_field` 与 `y_fields` 必须原样取自结果集列名，包括中文别名。填一个不存在的字段会导致图表作废，退回规则决策。

规则模块生成配置时同样要区分维度列与度量列。区分依据是整列是否全为数值，而不是列名是否像度量。

## SQL 安全校验

守卫共七条规则，按固定顺序执行，其中六条拦截、一条自动改写。规则编号、检查内容与实现要点见《附录B-SQL安全沙箱规则与校验实现》。

语句超时不是守卫规则，它由仓储层在执行时通过进度回调中断，属于执行期保护。文档里出现「八条规则」的说法是把这两件事合并计数了，写作时应分开表述：守卫七条规则，外加仓储层一项超时中断。

四处容易出错的实现细节：

1. 表名校验要排除 CTE 名与子查询别名，否则任何用了 CTE 或派生表的合法查询都会被误拦；
2. 笛卡尔积检测要同时覆盖显式 JOIN 缺条件与逗号分隔多表两种写法；
3. 强制 LIMIT 用外层包裹实现，不改写 AST 节点；
4. 笛卡尔积检测（R7）必须排在强制 LIMIT（R6）之前。R6 把语句包裹为 `SELECT * FROM (...) AS _guard_limited LIMIT 1000` 之后，`FROM` 里只剩一个派生表，R7 再检查就必然通过。

## 结构化输出处理

节点需要模型返回结构化数据时，定义对应的 Pydantic 模型，网关负责解析与校验。

三次尝试顺序：JSON mode、去掉 JSON mode、强化格式提示。

国内模型对结构化输出的支持程度不一，以 JSON mode 为主、文本解析兜底比直接用函数调用稳。解析时容忍 Markdown 代码围栏与前后说明文字。

## 相对时间换算

相对时间词在 `synonyms.yaml` 的 `time_terms` 中登记，共 22 条词条，由代码换算为左闭右开区间：

今天、昨天、本周、上周、本月、这个月、上个月、上月、本季度、这个季度、上季度、上个季度、今年、本年度、去年、去年同期、近7天、近30天、近三个月、近半年、上半年、下半年。

三点需要注意：

1. 词条是精确匹配。同一个意思的多种说法要各占一条，例如「本月」与「这个月」、「上季度」与「上个季度」分别登记；
2. 「近7天」没有空格，用户问「最近 7 天」不会命中。需要在 Prompt 或前端输入提示中引导写法，而不是靠代码容错；
3. 配置中没有「今年以来」这个说法，对应的是「今年」与「本年度」，按自然年换算。

换算结果同时给到 Prompt 与前端展示，前端展示时给出可读的区间描述，例如「2026-04-01 起至 2026-06-30 止」。

Prompt 中明确要求模型不要自行重新解释相对时间，直接用给定的区间。
