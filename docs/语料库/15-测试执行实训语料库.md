# 15 — 测试执行实训语料库

## 测试的四个层次

本项目的测试从下往上分四层，每层测的东西不同，不能互相替代。

| 层次 | 对象 | 手段 | 是否需要 API Key |
|---|---|---|---|
| 单元 | 安全守卫、语义层加载、时间换算 | pytest | 否 |
| 集成 | 仓储层读写、节点单跑 | pytest + 临时 SQLite | 否 |
| 端到端 | 完整链路 | 冒烟脚本 `/api/chat/sync` | 否（桩实现） |
| 评测 | 问答准确率 | 评测集 + 评测脚本 | 是（真实模型） |

前三层在无密钥环境下可以全跑通，这是桩实现存在的意义。第四层必须有真实模型，桩实现的评测结果没有参考价值。

## 单元测试

### 安全守卫的用例矩阵

守卫是唯一一处「出错就会造成数据事故」的代码，测试要覆盖守卫的全部七条规则，每条至少一正一反两个用例。

| 规则 | 反例 | 预期 | 实现位置 |
|---|---|---|---|
| R1 单语句 | `SELECT 1; DROP TABLE orders` | 拦截 | 守卫 |
| R2 仅 SELECT | `DELETE FROM orders WHERE 1=1` | 拦截 | 守卫 |
| R3 禁用关键字 | `SELECT * FROM orders WHERE id IN (SELECT ...)` 中含 `INSERT` | 拦截 | 守卫 |
| R4 表白名单 | `SELECT * FROM user_info` | 拦截，表不在白名单 | 守卫 |
| R5 字段白名单 | `SELECT secret_field FROM orders` | 拦截 | 守卫 |
| R7 笛卡尔积 | `SELECT * FROM orders, users` 无 WHERE 关联 | 拦截 | 守卫 |
| R6 LIMIT 强制 | `SELECT * FROM orders` | 放行并改写为带 `LIMIT 1000` | 守卫 |
| R8 语句超时 | 慢查询 | 超时中断 | 仓储层 |

表格顺序即校验顺序：**R7 排在 R6 之前**。R6 会把语句包裹成 `SELECT * FROM (...) AS _guard_limited LIMIT 1000`，若先执行 R6，R7 面对的 `FROM` 只剩单个派生表，多表连接条件检查会恒定通过。

R8 不是守卫的拦截规则，它由仓储层的执行进度回调实现，因此用例写在 `tests/test_repository.py`，不写在 `tests/test_guard.py`。把两者混在一起会导致守卫测试依赖真实耗时，运行不稳定。

R6 是唯一会自动改写的规则，因此它的用例要额外断言改写后的语句确实带了 LIMIT，且原语句自带的更小 LIMIT 不被覆盖。

边界用例另列四类：CTE（`WITH x AS (...)`）、子查询中的表、别名与真实表名的区分、字符串字面量里含关键字。这四类最容易在 AST 解析上出错。

### sqlglot 版本差异的防护

sqlglot 的 AST API 在不同版本间有变化。30.x 中 `stmt.args["from_"]` 返回单个 `exp.From` 节点，表清单挂在它的 `expressions` 上，直接按列表迭代会抛 `TypeError: 'From' object is not iterable`。

守卫的测试必须锁定一个具体版本跑，升级 sqlglot 后重跑这一组测试。依赖版本写进 `requirements.txt` 时加下限约束。

`requirements.txt` 由 T6.3 用 `pip freeze` 生成，在此之前该文件不存在，下限约束无处落地。做法是先按实训步骤安装依赖、跑通测试，再生成文件并补下限。

### 语义层测试

测三件事：

1. YAML 能加载，且指标数与表数符合预期。
2. 每个指标的同义词与示例问法都能召回该指标。
3. 相对时间词换算结果正确，特别是跨月、跨年、跨季度的边界。

第 2 条是最有价值的测试。新增指标后忘了配同义词，这条测试会立刻失败，而不必等到评测集跑完才发现。

### 时间换算的边界用例

| 输入 | 关注点 |
|---|---|
| 今天 | 结束时间是明天零点 |
| 上个月 | 跨年时起始月份是去年的 12 月 |
| 上个季度 | 第一季度时上个月度是去年的第四季度 |
| 近7天 | 是否包含今天，本实现含今天，区间为 7 个自然日。配置中的词条是「近7天」，没有空格 |
| 上半年 / 下半年 | 结束日期是 7 月 1 日与次年 1 月 1 日 |

所有区间均为左闭右开。测试要断言 `end` 等于下一个区间的 `start`，这样区间拼接不会有重叠或缝隙。

## 集成测试

### 仓储层

用临时目录建库，跑建表、造数、查询、列裁剪、行数统计。断言的重点不在 SQL 是否写对，而在返回结构是否稳定：列名顺序、空结果的表现、超长字段的截断。

一致性校验的测试要覆盖 SQLite 内部表干扰这一情况。执行 `ANALYZE` 之后 `sqlite_master` 里会出现 `sqlite_stat1`，如果 `list_tables()` 不过滤 `sqlite_%` 前缀，`/api/semantic/health` 会误报 `consistent: false`。

### 节点单跑

每个节点可以脱离图单独调用，传入构造好的 `AgentState` 片段，断言输出字段。`retrieve`、`validate`、`execute` 三个节点不依赖模型，是最值得单测的。

`generate` 与 `fix` 依赖模型，单测时用桩实现，断言的是「桩实现下节点字段被正确写入」，而不是 SQL 内容本身。真实 SQL 质量交给评测集。

## 端到端冒烟

`backend/tests/smoke.py` 用 FastAPI 的 `TestClient` 依次调用：

1. `GET /api/health`
2. `GET /api/semantic/health`，断言 `consistent` 为 true
3. `POST /api/session`
4. `POST /api/chat/sync`，问三个不同指标的问题

每一步的失败都收集到 `failures` 列表，最后统一打印并决定退出码。全部通过后输出每个问题的 `status`、`sql`、`row_count` 与 `stages`。

```bash
cd backend
python -m tests.smoke
```

冒烟不测准确率，只测链路通不通与字段齐不齐。它的价值在于改动任何一个节点之后三十秒内知道有没有把链路跑断。

## 评测集构造

### 题目设计

评测集落在 `backend/eval/cases.yaml`。该目录当前为空，没有现成文件可跑，建立评测集是本实训的第一步产出，不是可选动作。

20 到 30 题，按难度分三层：

| 层 | 占比 | 特征 | 例子 |
|---|---|---|---|
| 简单 | 40% | 单指标、无维度或单维度、相对时间 | 上个月的成交总额 |
| 中等 | 40% | 单指标加维度，或含筛选、排序、TopN | 上季度各渠道的订单数前 5 |
| 困难 | 20% | 双指标、跨三张表、复杂筛选或需要澄清 | 今年各月份的客单价与退款率 |

题目要覆盖全部 7 个指标与全部 9 个维度，每个指标至少 2 题。这一条是硬要求：漏掉的指标在评测中不可见，等于没测。

另留 3 到 5 题作为「应当被拦下或应当澄清」的负例，例如查未登记的表、要求删除数据、语义不清的问题。本项目只连一个 SQLite 库，不存在跨库场景，不要出「跨库查询」类的负例。这类题的评判标准不是 SQL 对不对，而是系统有没有给出合理的拒绝或回问。

### 标准答案怎么定

标准答案有两个选择：标准 SQL 或标准结果集。

**标准 SQL 比对**实现简单，但会误判。同一结果可以有多种写法，`JOIN` 与子查询、`HAVING` 与外层 `WHERE` 都算对。用它做唯一判据会把正确的回答判成错误。

**标准结果集比对**更贴近业务语义。执行标准 SQL 与生成 SQL，比对两个结果集是否一致，忽略列顺序，比较行集合。

本评测采用结果集比对，同时人工复核 SQL 是否使用了正确口径。口径对而结果偶然一致的情况在小数集上会发生，人工复核这一环不能省。

### 结果集归一化

比对前做三步归一化，缺一不可：

1. 列名统一小写并去掉别名差异，只保留语义列。
2. 浮点数按相对误差 1e-6 比较，不比较字符串。
3. 行集合按内容排序后逐行比较，忽略原始顺序。

`ORDER BY` 缺失导致的顺序不同不算错，但缺失 `ORDER BY` 本身在 TopN 类题目上是错的。因此 TopN 题额外检查是否带了排序与 LIMIT。

## 评测指标

| 指标 | 定义 | 用途 |
|---|---|---|
| 执行成功率 | 生成 SQL 能成功执行的比例 | 衡量语法与字段编造问题 |
| 结果一致率 | 执行结果与标准结果集一致的比例 | 主指标，衡量语义正确 |
| 口径命中率 | 召回的指标与标注指标一致的比例 | 衡量语义层质量 |
| 平均尝试轮次 | 走完链路平均经历几次生成 | 衡量首次生成质量 |
| P95 端到端耗时 | 95 分位问答耗时 | 衡量可用性 |
| 拦截准确率 | 负例被正确拦截或澄清的比例 | 衡量安全与澄清分支 |

结果一致率是主指标，其余是诊断指标。一致率下降时，看口径命中率是否同步下降：同步下降说明是召回问题，单独下降说明是生成问题。

## 评测执行

### 跑基线

第一次评测在使用真实模型的环境里跑，保存为基线文件。基线包含每题的得分、耗时与 SQL，供后续对比。

基线必须记录当时的模型名与 Prompt 版本。换模型或改 Prompt 之后重跑，数字不可直接比较。

### 回归流程

改动语义层配置、Prompt 模板或节点逻辑之后重跑评测，与基线逐题对比。关注三类变化：

- 新增失败：原本对的题变错，需要定位。
- 新增通过：原本错的题变对，确认不是偶然。
- 耗时变化：P95 明显上升要查是不是召回范围变大了。

### 常见测试陷阱

**造数用了随机数导致断言不稳。** 造数脚本必须固定随机种子，否则两次建库的数据不同，结果集比对失去意义。

**桩实现与真实模型混用。** 同一份评测结果里不能混。桩实现只按关键词返回固定 SQL，跑出来的数字不代表任何真实能力。

**并发跑评测。** 评测脚本串行调用。并发会打满模型限流，也会让 SQLite 的只读连接出现锁竞争，两类失败都表现为随机错误，难以复现。

**把 `stages` 跨轮累积当成正常现象。** `stages` 的作用域是单轮，跨轮累积是缺陷而不是特性。断言阶段数量时应按单轮口径写，若发现第二轮出现上一轮的阶段条目，应回到 `app/agent/state.py` 检查 `merge_stages` 是否仍是该字段的归约器，而不是把断言放宽成兼容累积，也不要寄望于在接口层换一种读取方式——每个节点 update 里带回的 `stages` 已是归约后的全量。

**在评测中修改标准答案。** 标准答案只能在确认标注错误时改，且要记录改动原因。为了让系统通过而改答案，评测就失去了意义。
