# 07 — 开发任务文档编写实训语料库

## 开发任务文档的作用

它回答三个问题：按什么顺序做、每一步做完能验证什么、什么时候算完成。

与 PRD 的区别：PRD 说「要什么」，开发任务文档说「怎么做、什么顺序做」。混在一起写，结果是 PRD 里出现实现细节，任务文档里又重复描述需求。

## 三条拆解原则

**按依赖排序，不按模块排序。** 同一模块的工作可能被拆到不同阶段。例如数据访问层中，守卫属于安全沙箱阶段，会话存储属于后端阶段。按目录罗列的后果是看不出先后顺序。

**每一步都有可独立验证的产出。** 做完一步就能运行一次看到结果，不攒到最后联调。这条原则决定了任务粒度：一次能跑通并看到结果的一组改动算一条任务。

**最早暴露最大的不确定性。** 本项目最大的不确定性是模型能否稳定产出可执行 SQL，因此三节点链路要在网关打通之后立刻验证，不等语义层与前端。

## 任务编号与表格结构

编号采用 `T<阶段号>.<序号>`，例如 T1.1。任务表包含五列：

| 列 | 内容 |
|---|---|
| 编号 | `T<阶段>.<序号>` |
| 任务 | 一句话说明做什么 |
| 依赖 | 前置任务编号，无则填「无」 |
| 产出 | 具体文件 |
| 验收 | 可观察的结果 |

「验收」列最容易被写成「完成某某功能」。正确写法是给出的结果可观察，例如「一致性校验接口返回 `true`」。

## 阶段划分

本项目分六个阶段：

| 阶段 | 内容 | 出口条件 |
|---|---|---|
| 一 | 数据与语义层 | 一致性校验通过，召回能命中典型问题 |
| 二 | 数据访问层与安全沙箱 | 守卫七条规则单测通过，仓储层超时中断另有用例 |
| 三 | 网关与最小链路 | 不接语义层也能跑出结果 |
| 四 | 完整编排 | 多轮问答可用，重试回环可触发 |
| 五 | 接入层与前端 | 浏览器内完成一次完整问答 |
| 六 | 评测与交付 | 评测基线产出，六类资源齐全 |

阶段出口是里程碑的判定依据。没有出口条件的阶段，等于没有完成标准。

## 依赖关系图

用 ASCII 箭头图表示任务之间的依赖：

```
T1.1 → T1.2 ─┬─→ T2.1 → T2.3 ─┐
      T1.3 ──┼─→ T1.6 ────────┼─→ T3.3 → T4.2 → T4.4 → T5.1 → T5.2
      T1.4 ──┤                 │
      T1.5 ──┘                 ├─→ T2.4
                               │
      T3.1 → T3.2 ─────────────┘
                               └─→ T4.3 → T4.4 → T4.6
                                              └→ T5.5 → T5.6 → T5.7
                                                            └→ T6.1 → T6.2
```

图上要单独标出**关键路径**，即决定最短工期的任务序列。本项目的关键路径是：

```
T1.1 → T1.2 → T2.1 → T2.3 → T3.3 → T4.3 → T4.4 → T5.1 → T5.2 → T5.5 → T5.6 → T5.7
```

关键路径取的是每个汇合点上游较长的那条：`T4.4` 的前置有 `T4.2` 与 `T4.3`，二者可并行，取经 `T4.3` 的一支；`T5.6` 的前置 `T5.2` 与 `T5.5` 同理，`T5.5` 不依赖后端，但必须排在 `T5.6` 之前。

同时要标出可并行的部分。本项目中，三份 YAML 之间无依赖，前端工程初始化不依赖任何后端任务，可以提前开始。

只画父子关系而不标关键路径的图，看不出哪些任务延期会影响整体进度。

## 里程碑

每个里程碑写清时点、交付内容与判定标准：

| 里程碑 | 时点 | 交付内容 | 判定标准 |
|---|---|---|---|
| M1 | 阶段一结束 | 样例库与语义层 | 一致性校验通过，召回可命中 |
| M2 | 阶段二结束 | 安全沙箱 | 守卫七条规则单测通过 |
| M3 | 阶段三结束 | 最小链路 | 不接语义层也能跑出结果 |
| M4 | 阶段四结束 | 完整编排 | 多轮问答可用，重试回环可触发 |
| M5 | 阶段五结束 | 可用系统 | 浏览器内完成一次完整问答 |
| M6 | 阶段六结束 | 交付齐套 | 评测基线产出，六类资源齐全 |

## 交付标准

按五类写：

| 类别 | 标准 |
|---|---|
| 代码 | 三条分层硬约束全部满足；依赖锁定；配置模板不含真实密钥 |
| 测试 | 守卫七条规则逐条有用例，仓储层超时中断单独有用例；语义层加载与召回有用例；接口有冒烟用例 |
| 文档 | 六类资源数量与交付规范一致 |
| 可复现 | 干净环境按 README 步骤可启动并完成一次问答 |
| 数据真实 | 演示截图取自真实运行，评测数字取自脚本输出 |

最后一条是针对 AI 共创场景加的。用 AI 生成含数据的交付物时，未经实测的数字会被模型补全，交付前必须逐项核对。

## 风险表

每条风险写四列：风险、影响、对策、责任任务。

「责任任务」一列容易被省略，但没有它，风险就只是一份提醒，不知道该在哪一步处理。例如「模型产出 SQL 不稳定」的对策是语义层注入口径加失败修正回环加评测回归，责任任务是 T4.3 与 T6.1。

## AI 共创时的注意点

让 AI 拆解任务时，把已有架构决策与目录结构一并给出，并要求按依赖排序。只给一句「帮我拆解开发任务」，得到的是按模块罗列的清单。

审查时对每条任务问两个问题：做完这一步能运行什么？它的前置任务是不是真的必须？第一个问题答不上来说明拆解无效，第二个问题答「不一定」说明可以并行。
