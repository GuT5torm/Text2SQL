# 17 — 部署运维语料库

## 三种部署形态

| 形态 | 适用 | 进程 | 前端 |
|---|---|---|---|
| 本地演示 | 课程演示、单人使用 | `uvicorn` 单进程 | Vite 开发服务器或已构建产物 |
| 单机服务 | 实验室内网、多人访问 | `uvicorn` 挂载构建产物 | 由 FastAPI 静态托管 |
| 反向代理 | 需要 HTTPS 或域名 | `uvicorn` + Nginx | Nginx 托管静态资源 |

三种形态跑的是同一份代码，区别在于进程怎么起、静态资源由谁托管。本项目是模块化单体，没有微服务，不需要容器编排，也不需要 Redis 或消息队列。

## 环境变量

全部配置从环境变量或 `backend/.env` 读取，代码中不出现任何密钥字面量。

### 应用

| 变量 | 默认值 | 说明 |
|---|---|---|
| `APP_NAME` | Text2SQL 电商数据分析 Agent | 应用名 |
| `DEBUG` | false | 调试模式 |
| `LOG_LEVEL` | INFO | 日志级别 |
| `CORS_ORIGINS` | http://localhost:5173,http://127.0.0.1:5173 | 逗号分隔的允许来源 |

### LLM 网关

| 变量 | 默认值 | 说明 |
|---|---|---|
| `LLM_API_KEY` | 空 | 密钥。留空时自动走桩实现 |
| `LLM_BASE_URL` | https://dashscope.aliyuncs.com/compatible-mode/v1 | OpenAI 兼容入口 |
| `LLM_MODEL` | qwen-plus | 模型名，以服务商控制台为准 |
| `LLM_FALLBACK_MODEL` | 空 | 主模型连续失败时降级使用，留空不启用 |
| `LLM_TIMEOUT` | 30.0 | 单次调用超时秒数 |
| `LLM_MAX_RETRIES` | 2 | 网关层重试次数 |
| `LLM_TEMPERATURE` | 0.0 | 取 0 保证同问同答 |
| `LLM_MAX_TOKENS` | 2048 | 单次生成上限 |
| `LLM_MOCK` | false | 强制使用桩实现。生产必须置 false |

换服务商只需要改 `LLM_BASE_URL`、`LLM_MODEL`、`LLM_API_KEY` 三项，不需要动代码。任何 OpenAI 兼容入口都可以接入。

### 存储

| 变量 | 默认值 | 说明 |
|---|---|---|
| `BUSINESS_DB_PATH` | backend/data/ecommerce.db | 业务库，只读连接 |
| `APP_DB_PATH` | backend/data/app.db | 应用库，存会话与轮次 |

两个库分开，是为了让业务库保持只读。业务库的连接以只读模式打开，即便守卫被绕过，写操作也无法落盘。

### SQL 安全沙箱

| 变量 | 默认值 | 说明 |
|---|---|---|
| `SQL_TIMEOUT_SECONDS` | 10.0 | 语句超时秒数 |
| `SQL_MAX_ROWS` | 1000 | 自动补 LIMIT 的上限与结果行上限 |
| `SQL_MAX_RETRY` | 3 | 校验失败与执行失败共享的修正次数。判定为 `retry_count <= max_retry`，即首次生成之外最多再修正 3 次，合计 4 次尝试 |
| `SQL_SCAN_LIMIT` | 20000000 | 单次查询允许扫描的最大行数，超过由 progress handler 中断 |

### 会话

| 变量 | 默认值 | 说明 |
|---|---|---|
| `HISTORY_WINDOW` | 6 | 历史会话回灌给模型的最近轮数 |
| `CHECKPOINTER` | memory | `memory` 或 `sqlite`。`memory` 下进程重启后多轮上下文丢失 |

演示场景用 `memory` 足够，进程重启即重置。需要长期保留多轮上下文时改为 `sqlite`，检查点写入应用库。

## 部署流程

### 准备

```bash
cd backend
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
```

`requirements.txt` 由《开发任务文档》T6.3 产出。若该文件尚未生成，先按下面流程装完依赖再冻结版本：

```bash
pip install fastapi uvicorn langgraph langchain-core sqlalchemy sqlglot pydantic pydantic-settings openai pyyaml pytest httpx
pip freeze > requirements.txt
```

Windows 的 PowerShell 中激活命令为：

```powershell
.\.venv\Scripts\Activate.ps1
```

### 建库与造数

```bash
python -m app.db.seed             # 建表并写入示例数据
```

执行后确认 `data/ecommerce.db` 存在，`/api/semantic/health` 的 `row_counts` 显示六张表都有数据。

### 配置

```bash
cp .env.example .env              # Windows: Copy-Item .env.example .env
```

填入 `LLM_API_KEY`。不填也能启动，走桩实现，用于先把链路跑通。

### 前端构建

```bash
cd frontend
npm install
npm run build                     # 产物在 frontend/dist
```

构建产物存在时，FastAPI 会把它挂载到根路径，后端单进程即可提供完整服务，不需要另起前端服务器。

### 启动

开发模式：

```bash
uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

生产模式：

```bash
uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 1
```

`--workers` 必须为 1。Checkpointer 用 `memory` 时多worker 之间不共享状态，同一次会话的请求落到不同进程会导致上下文丢失。

### 健康检查

```bash
curl http://127.0.0.1:8000/api/health
```

确认 `llm_mock` 为 `false`（生产环境）、`metrics` 与 `tables` 数量正确。

## 日志

应用日志使用标准 `logging`，随 uvicorn 输出到标准输出，由进程管理器收集。

关键日志条目：

| 内容 | 含义 |
|---|---|
| `对话链路异常` | 编排层兜底异常，带完整堆栈 |
| `问答记录写入失败（不影响本次返回）` | 落库异常，不影响当次回答 |
| 守卫拦截记录 | 被拦的 SQL 与规则编号 |

需要更详细输出时把 `LOG_LEVEL` 改为 `DEBUG`。排查模型问题时，DEBUG 级别会打印完整的 Prompt 与响应，注意其中可能包含业务数据。

Linux 下由 systemd 管理的进程用 `journalctl -u text2sql -f` 查看实时日志。Windows 本地运行时日志直接输出在启动终端里，用 `Start-Process` 起的进程看 `-RedirectStandardOutput` 指定的文件。

## 进程守护

### Linux（systemd）

`/etc/systemd/system/text2sql.service`：

```ini
[Unit]
Description=Text2SQL E-commerce Analytics Agent
After=network.target

[Service]
Type=simple
User=www-data
WorkingDirectory=/opt/text2sql/backend
Environment="PATH=/opt/text2sql/backend/.venv/bin"
ExecStart=/opt/text2sql/backend/.venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 1
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now text2sql
sudo systemctl status text2sql
```

`Restart=always` 保证进程崩溃后自动拉起。`WorkingDirectory` 必须指向 `backend`，配置里的相对路径依赖它。

### Windows

演示环境常用 PowerShell 后台任务或 nssm 注册为服务。临时起法：

```powershell
Start-Process -NoNewWindow -FilePath ".\.venv\Scripts\python.exe" `
  -ArgumentList "-m","uvicorn","app.main:app","--host","127.0.0.1","--port","8000" `
  -RedirectStandardOutput ".\logs\out.log" -RedirectStandardError ".\logs\err.log"
```

停止服务前先确认没有其他实例在跑。重复启动同一命令会造成端口占用，表现为新进程起不来而旧进程仍在服务，日志里没有报错。

## 数据备份

业务库与应用库都是单文件，备份即拷贝文件。

拷贝前先确认没有正在执行的查询。SQLite 在写入过程中拷贝可能得到不一致的快照，应用库有会话写入，风险更高。稳妥做法是先停服务再拷贝。

Windows（PowerShell）：

```powershell
Get-Process python -ErrorAction SilentlyContinue | Stop-Process -Force
Copy-Item data\ecommerce.db data\ecommerce.db.bak
Copy-Item data\app.db data\app.db.bak
```

Linux（systemd）：

```bash
systemctl stop text2sql
cp data/ecommerce.db data/ecommerce.db.bak
cp data/app.db data/app.db.bak
systemctl start text2sql
```

业务库在部署后不再变更（造数脚本只在初始化时跑一次），实际只需备份一次。应用库随使用增长，建议定期备份。

体积膨胀时执行 `VACUUM` 回收空间。注意 `VACUUM` 会产生 `sqlite_stat1` 表，语义层的一致性检查已过滤该前缀。

## 升级步骤

1. 停服务。
2. 备份两个数据库文件。
3. 拉取或覆盖代码。
4. 激活虚拟环境，重装依赖：变更依赖后必须重装，尤其是 sqlglot，版本差异会改变 AST 行为。
5. 若语义层 YAML 有变更，重跑 `/api/semantic/health` 确认 `consistent` 为 true。
6. 跑冒烟脚本：`python -m tests.smoke`。
7. 起服务，确认 `/api/health` 的 `llm_mock` 为 false。

第 6 步不能省。它三十秒内就能发现链路是否被打断，比手工点几轮快。

## 运维检查清单

| 检查项 | 命令或位置 | 正常表现 |
|---|---|---|
| 进程存活 | Linux：`systemctl status text2sql`；Windows：`Get-NetTCPConnection -LocalPort 8000 -State Listen` | active (running) / 有监听记录 |
| 接口存活 | `GET /api/health` | `status: ok` |
| 模型可用 | `GET /api/health` | `llm_mock: false` |
| 语义层一致 | `GET /api/semantic/health` | `consistent: true` |
| 数据完整 | 同上 | `row_counts` 六张表非零 |
| 用量监控 | `GET /api/stats` | 累计调用与 token 数 |
| 磁盘 | 数据库所在分区 | 有余量 |

## 安全注意事项

- `.env` 不进版本库。密钥只在 `.env` 里，代码与日志中都不出现。
- 生产环境 `LLM_MOCK` 必须为 false。桩实现的返回值与真实模型无关，出现在生产环境会给出错误的数字。
- 业务库以只读模式连接。这一条是纵深防御，不替代 SQL 守卫。
- 只监听 `127.0.0.1`，对外服务由 Nginx 代理。直接暴露 uvicorn 端口等于放弃 HTTPS 与访问控制。
- 前端构建产物不含密钥。密钥只在后端进程内。
