# 16 — 错误处理方案语料库

## 排查顺序

出问题时按固定顺序定位，避免在错误的地方反复尝试：

1. 看 `/api/health` 的 `llm_mock`。为 `true` 说明当前是桩实现，所有结果都是预设的固定 SQL，不要在此基础上调 Prompt。
2. 看 `/api/semantic/health` 的 `consistent`。为 `false` 说明语义层与业务库对不上，先修这个再谈别的。
3. 看回答的 `status` 字段。`ok`、`clarify`、`chitchat`、`error` 四种状态各有对应的处理方向：正常回答、信息不足、非取数问题、失败。`status` 不是三个值，漏掉后两种会把闲聊回答当成空结果、把失败当成无返回。
4. 看 `stages` 的最后一个节点。它指出链路停在哪里。
5. 看 `error` 字段的原文。执行类错误会把数据库的原始报错原样带回。

## 启动与环境类

| 现象 | 原因 | 处理 |
|---|---|---|
| 启动时报 `SemanticError`，detail 列出多个字段 | `metrics.yaml` / `tables.yaml` / `synonyms.yaml` 有缺失字段或类型错误 | 按 detail 列出的路径逐项修，配置是启动时全量校验的 |
| `/api/health` 的 `metrics` 或 `tables` 为 0 | YAML 没读到，通常是工作目录不对 | 在项目根目录启动，或检查配置里的资源路径 |
| 提示缺少 `OPENAI_API_KEY` | 未配置密钥 | 复制 `.env.example` 为 `.env` 并填入；不配也能启动，走桩实现 |
| 端口被占用 | 上一个进程没退出 | 换端口或结束旧进程 |
| 导入报 `ModuleNotFoundError` | 未激活虚拟环境或未安装依赖 | 激活 venv 后重装依赖 |

## 语义层类

| 现象 | 原因 | 处理 |
|---|---|---|
| `/api/semantic/health` 的 `missing_in_db` 非空 | 语义层登记了库里不存在的表 | 补建表或删掉该登记项 |
| `missing_in_semantic` 非空 | 库里有表没登记 | 往 `tables.yaml` 补表，否则 SQL 会被 R4 拦下 |
| 一致性原本正常，执行 `ANALYZE` 后变 `false` | SQLite 生成了内部表 `sqlite_stat1` | 已在 `list_tables()` 中过滤 `sqlite_%` 前缀，若仍出现说明用了旧代码 |
| 问题命中不到指标 | 同义词未覆盖该说法 | 用 `/api/semantic/recall` 确认，再往 `synonyms.yaml` 补词 |
| 命中了错误的指标 | 同义词有歧义，多个指标共享同一个词 | 给词加限定，或把它从泛指标移到具体指标 |
| 时间范围与预期不符 | 用了系统支持的相对时间词之外的说法，或口径本身是自然月 | 查 `/api/semantic/synonyms` 的 `time_terms`，按支持的词提问 |

## SQL 校验拦截类

拦截信息以 `R` 加编号开头，出现在 `error` 字段里。守卫实现七条规则（R1–R7），R8 语句超时由仓储层的 progress handler 完成，不在守卫内。含义与修法如下。

**R1 只允许单条语句。** 模型输出了带分号的多条语句。通常是 Prompt 里没有明确禁止，或模型在末尾追加了补充说明。修正 Prompt 的语句约束段。

**R2 只允许查询类语句。** 出现了 `INSERT`、`UPDATE`、`DELETE`、`CREATE` 等。这类输出应当触发重试，重试仍失败则进入 give_up。

**R3 语句树中不得出现 DDL / DML / 管理类关键字。** 包括嵌套在子查询或 CTE 里的。注意 `PRAGMA`、`ATTACH` 也在此列。

**R4 表未在语义层登记。** 分三种文案：

- `R4 不允许访问 {db} 库中的表 {name}`：语句带了库名前缀，而白名单只登记了表名。
- `R4 表 {name} 未在语义层登记，疑似模型编造`：模型按一般电商库的习惯写出了本库不存在的表。这是字段编造的典型表现，把报错原样回传给模型重试通常能修好。
- `R4 表别名不合法`：别名与已登记的表名冲突或为空。

**R5 字段不存在。** 同样分三种：带表前缀的字段不在该表的元数据里、引用了未知的表或别名、无前缀字段未在任何被引用的表中登记。第二种往往是 JOIN 之后用了没在 FROM 里出现的别名。

**R6 LIMIT 强制。** 不是错误，是唯一会自动改写的规则。无 `LIMIT` 补 1000，超过 1000 截断到 1000。若发现结果被截断，说明查询本身应该加聚合条件而不是调大上限。

**R7 多表查询必须带连接条件。** 三种文案分别对应 `CROSS JOIN`、`JOIN` 缺 `ON`、逗号分隔的多表 `FROM` 且 `WHERE` 中没有表间关联。第三种最容易被忽略，AST 需要遍历 `FROM` 节点的 `expressions` 而不是直接迭代 `from_`。

**R8 执行超时。** 由 SQLite 的 progress handler 实现，超时时间可配。超时后连接中断，重试时模型会收到超时信息。

### sqlglot 版本引起的假报错

升级 sqlglot 后守卫可能抛 `TypeError: 'From' object is not iterable`。这不是 SQL 的问题，是 AST API 版本差异。30.x 中 `stmt.args["from_"]` 返回单个 `exp.From` 节点，表清单挂在它的 `expressions` 上。修法是判断 `isinstance(from_node, exp.From)` 后取 `from_node.expressions`，或直接锁定版本。

## 模型调用类

| 现象 | 原因 | 处理 |
|---|---|---|
| 报 `LLMError`，提示鉴权失败 | API Key 错误或过期 | 到服务商控制台重新生成并更新 `.env` |
| 报 `LLMError`，提示限流 | 超出并发或 QPS 限制 | 降低并发，评测脚本改串行 |
| 报模型不存在 | 模型名写错或该账号未开通 | 核对控制台的模型名，注意带版本后缀 |
| 返回内容无法解析为 JSON | 模型输出带了 Markdown 代码围栏或解释文字 | 网关已做三次尝试：直接解析、剥离围栏后解析、正则提取首个 JSON 对象。仍失败时重试该节点 |
| 响应很慢 | 上下文过长或模型本身慢 | 缩小召回范围，减少无关表进入 Prompt |
| 桩实现下三个不同问题返回同一条 SQL | 关键词匹配对整段 Prompt 生效，而 Prompt 里含全部指标名 | 已在桩实现中只取「问题」小节之后的内容做匹配；这是桩实现的问题，不影响真实模型 |

## 前端类

| 现象 | 原因 | 处理 |
|---|---|---|
| 页面白屏 | 静态资源未构建或路径不对 | 构建前端产物并确认 `frontend_dist` 路径 |
| 接口 404 | 前端未配代理，请求打到了前端端口 | 配 Vite 代理或直连后端地址 |
| 进度一次性全部出现 | 反向代理缓冲了 SSE | Nginx 配 `proxy_buffering off`，应用已带 `X-Accel-Buffering: no` |
| 进度停在某个节点不动 | 节点在等模型响应 | 看后端日志，确认是否有请求发出 |
| 图表不出但表格有数据 | 结果集结构与图表类型不匹配，或字段名映射失败 | 看 `chart` 字段是否为 null，校对 `x_field` 与列名 |
| 图表数据错位 | 图表字段映射未做校验，列顺序变化时取错了列 | 前端渲染前校验 `chart` 里的字段名确实存在于 `columns` |
| 历史会话打开是空的 | 轮次落库失败 | 看后端日志里的 `问答记录写入失败`，落库失败不影响当次返回 |

## 日志与定位

应用日志走标准 `logging`，uvicorn 的访问日志与它分开。需要更详细的输出时调整日志级别配置。

几处关键日志：

- `对话链路异常`：编排层的兜底异常，会带完整堆栈。
- `问答记录写入失败（不影响本次返回）`：落库异常，不影响当次回答。
- 守卫的每次拦截：记下被拦的 SQL 与规则编号。

数据库报错原文会一路带回给模型，也会出现在日志里。看到 `no such column: x` 时，说明是字段编造，不是连接问题。

## 已知行为

以下现象属于预期行为，不需要处理：

- 删除会话后，该会话在 LangGraph 检查点里的数据仍然存在。
- 无密钥启动时全部问答走桩实现，`/api/health` 会明确标出 `llm_mock: true`。
- 实际执行的语句可能被 R6 包裹成 `SELECT * FROM (...) AS _guard_limited LIMIT 1000`，与模型原始语句不同。核对口径时看 `original_sql`。

以下现象不是预期行为，出现即需修复：

- 同一会话多轮提问时，进度阶段跨轮累积，例如第二轮显示 14 个阶段。原因是 `stages` 用追加归约，Checkpointer 保留了上一轮的内容。修法是接口按逐节点更新采集本轮事件，不从终态整体取；前端在发起新一轮时也先清空阶段列表。
- 结果集落库截断到 200 行。落库内容与当轮下发的一致，不做额外截断。若历史回看的结果与当时不一致，属于落库环节的问题。
