# 02 — 系统架构与技术选型语料库

## 架构形态

采用**模块化单体**，单进程 FastAPI。整体形态为：

```
[浏览器] → [FastAPI 单进程] → [LangGraph Agent 模块] → [SQLite]
```

模块划分在代码层面强制隔离，模块之间只通过明确的函数签名交互。这不是为了将来一定拆分，而是让模块边界在开发期就保持清晰。

选型对比：

| 形态 | 是否采用 | 理由 |
|---|---|---|
| 模块化单体 | 采用 | 单机演示、无并发压力、调试链路短 |
| 微服务 | 不采用 | 采用条件（团队十人以上、边界稳定、有运维能力）三条全部不满足 |
| 事件驱动 | 不采用 | 无异步削峰需求，问答链路本身是同步的 |
| CQRS | 不采用 | 唯一的写入是会话记录，读写比不悬殊 |
| Serverless | 不采用 | 长连接 SSE 加本地演示，冷启动与厂商绑定都是负担 |

核心判断是：这个项目的技术价值在于 Agent 编排与语义层，不在于基础设施。基础设施刻意保持极简，把全部工程复杂度投入到「自然语言到可信 SQL」这一件事上。凡不能直接提升 SQL 准确率或结果可信度的组件，一律不加。

## 六层职责边界

| 层 | 职责 | 明确不做什么 |
|---|---|---|
| 接入层 | HTTP 路由、SSE 推送、请求校验、静态资源 | 不写业务逻辑，不直接访问数据库 |
| 编排层 | 状态机流转、节点调度、重试控制、会话记忆 | 不拼接 SQL 字符串，不解析图表 |
| 语义层 | 指标口径、表结构元数据、同义词、召回 | 不执行 SQL，不调用模型 |
| LLM 网关 | 统一模型调用、超时重试、结构化输出解析、用量统计 | 不含任何业务 Prompt 内容 |
| 数据访问层 | 连接管理、SQL 校验、执行、结果规整 | 不生成 SQL，不做业务判断 |
| 前端 | 渲染对话、图表、SQL、表格 | 不做任何计算与判断 |

编排层之上不保存请求级状态，会话状态统一交给 LangGraph 的 Checkpointer，以会话 ID 为键。

## 落到代码的三条硬约束

架构分层要可执行，需要可检查的约束。以下三条在代码评审时逐条核对：

1. `agent/nodes/` 目录下不出现数据库连接。节点只能调用仓储暴露的方法，不允许直接导入数据库驱动或持有引擎。
2. `semantic/` 目录下不出现模型调用，也不出现 SQL 执行。语义层只做加载、校验与召回。
3. 密钥只出现在 `.env`。代码与配置文件中不出现密钥字面量。

违反任意一条即视为结构问题，需要在合入前修正。

## 技术栈

| 类别 | 选型 | 说明 |
|---|---|---|
| 前端 | React 18、TypeScript、Vite、Ant Design、ECharts | 组件化与图表能力 |
| 后端 | FastAPI、Python 3.12+、SQLAlchemy、Pydantic、LangGraph、sqlglot | 编排与校验 |
| AI 服务 | 阿里云百炼 OpenAI 兼容模式 | 换服务商只需改三项配置 |
| 数据存储 | SQLite、本地文件系统 | 零运维，单文件 |
| 架构 | 前后端分离、RESTful API、SSE 流式推送、Nginx 网关 | 单入口对外 |

Python 版本取 3.12，原因是 LangGraph 与配套依赖在 3.12 上的预编译包最完整。SQL 校验采用 sqlglot 做 AST 解析，不用正则处理 SQL 语法。

## 关键架构决策

| 编号 | 决策 | 代价 | 切换触发条件 |
|---|---|---|---|
| ADR-001 | 模块化单体而非微服务 | 边界依赖代码规范自律 | 产品化时编排层最先拆出 |
| ADR-002 | SQLite 起步，Repository 抽象隔离 | 少量样板代码 | 单表超过约五百万行或出现真实并发写入 |
| ADR-003 | 在模型与数据库之间引入语义层 | 需人工维护 YAML | 无，口径显式化是前提而非可选项 |
| ADR-004 | SQL 安全沙箱前置校验 | 少数复杂语句可能被误拦 | 无，拦截原因可回传修正 |
| ADR-005 | 会话记忆用 Checkpointer | MemorySaver 重启后丢失 | 需要跨重启保留时切 SQLiteSaver |
| ADR-006 | 召回先用规则匹配 | 表数量增长后召回率下降 | 表超过约三十张或漏召回明显影响准确率 |

## 演进阶段

| 阶段 | 形态 | 现在不做 |
|---|---|---|
| P0 演示版 | 单进程、SQLite、规则召回、MemorySaver | 向量库、缓存、容器化、鉴权 |
| P1 加固 | SQLiteSaver、结果缓存、评测回归 | 换数据库、多租户 |
| P2 产品化 | PostgreSQL、向量召回、鉴权、容器编排 | 微服务需先满足三条前置条件 |

每个阶段的「现在不做」清单与要做的事同等重要。跳过 P0 直接按产品化设计，是这类项目最常见的过度设计风险。

## 依赖版本

本项目不在此处固化具体版本号。版本号由 `backend/requirements.txt` 承载，该文件在《开发任务文档》T6.3 中用实际环境生成：

```bash
cd backend
pip freeze > requirements.txt
```

重建环境时以该文件为准，不使用文档里抄来的版本组合。

关键依赖的下限约束如下，写进 `requirements.txt` 时按此设下限、不锁上限：

| 包 | 下限 | 理由 |
|---|---|---|
| Python | 3.12 | LangGraph 与配套依赖在 3.12 上的预编译包最完整 |
| sqlglot | 按当前稳定版 | SQL 解析结果受版本影响，跨大版本可能改变 AST 形态 |
| pydantic | 2.x | v1 与 v2 的校验语义不同，不可混用 |

需要说明版本时，从运行环境中取实际值，不从记忆或其他文档中转抄。转抄得到的版本号看起来完整，但没有来源，属于未核实数据。
