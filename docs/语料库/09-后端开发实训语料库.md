## SSE 响应

事件类型四类：`stage` 节点进度、`result` 本轮结果、`error` 未预期异常、`done` 流结束。

实现要点：

**响应头。** 设置 `Cache-Control: no-cache`、`Connection: keep-alive`、`X-Accel-Buffering: no`。最后一项用于关闭 Nginx 缓冲，缺了它进度会被攒到最后一次性吐出。

**帧格式。** 每帧为 `event:` 行、`data:` 行与一个空行。`data` 用单行 JSON，换行会破坏帧边界。

**结束帧。** 主动发送 `done` 并结束流，避免前端认为连接仍在等待。

**异常兜底。** 捕获编排层的意外异常并作为 `error` 事件推送，保证前端一定能收到终止帧。

## 状态定义

状态是节点之间的唯一数据契约，字段按生命周期分组：会话、意图、语义召回、SQL 生命周期、结果集、输出、控制。

两处需要特别注意：

**`messages` 用追加归约。** 配合 Checkpointer 实现多轮记忆。

**`stages` 用追加归约。** 节点把进度事件追加进去，接入层据此推送 SSE。但正因为是追加语义，使用 Checkpointer 时会跨轮累积。接口层应按逐节点更新采集本轮事件，不从终态整体取，否则第二轮会把第一轮的进度一起返回。

节点只写自己负责的那组字段，读别人的字段，不修改别人的字段。这样任何一个节点都能单独测试。

## 图编排

八个业务节点加三个终态节点：

| 节点 | 职责 |
|---|---|
| `route` | 意图识别，判断取数、闲聊还是信息不足 |
| `retrieve` | 语义层召回 |
| `generate` | SQL 生成 |
| `validate` | 调用守卫做安全校验 |
| `execute` | 经仓储执行查询 |
| `fix` | 携带报错修正 SQL |
| `visualize` | 结果集转图表配置 |
| `summarize` | 结果集转经营结论 |
| `respond` / `clarify` / `give_up` | 三个终态，只做文案组装 |

条件路由四处：按意图分流、判断是否生成了语句、校验失败是否修正、执行失败是否修正。

关键设计：**修正后回到 `validate` 而不是直接 `execute`**。绕过校验直接执行会破坏安全边界。校验与执行两个节点共享重试配额，达到上限后进入 `give_up`，返回包含最后一次语句与报错的可读说明。

三个终态节点直接写在图定义里，不单独开文件——它们不调用模型也不访问数据库，为三行函数各开一个文件反而看不出结构。

## 节点实现约束

三条硬约束在此落实：

1. 节点中不出现数据库连接，只调用仓储暴露的方法；
2. 语义层不调用模型也不执行 SQL；
3. 密钥只出现在 `.env`。

节点内部的异常要自行兜住，返回结构化的错误说明，不让异常打断整张图。理由是一次的失败应该给出可读说明，而不是让整个请求失败。

## Prompt 外置

五个 Prompt 放在 `agent/prompts/` 下的 Markdown 文件中，占位符用 `{name}` 形式。

替换时用正则而不是 `str.format`，因为 Prompt 正文里有 JSON 示例，`str.format` 会把 JSON 的花括号当成占位符处理。

外置的价值：改 Prompt 不需要改代码，也便于在实训环节直观对比同一段 Prompt 改动前后的输出差别。

## 网关设计

网关集中处理四件事：超时重试、模型降级、结构化输出解析、用量统计。节点不持有客户端。

**重试只对超时、限流、连接类错误生效。** 参数错误重试多少次都一样。

**结构化输出三次尝试。** JSON mode、去掉 JSON mode、强化格式提示。国内模型对结构化输出的支持程度不一，这个顺序比直接用函数调用稳。

**桩实现。** 未配置密钥时自动启用，按问题关键词返回预置内容，让整条链路在拿到密钥之前就能跑通。桩的关键词匹配只针对 Prompt 中问题小节之后的内容，否则语义层上下文里列出的指标名会干扰匹配。

## 数据访问层

Repository 抽象两个接口：只读业务库的仓储，与会话元数据的存储。换数据库只需新增实现类。

SQLite 实现中的三个要点：

| 机制 | 实现 |
|---|---|
| 超时中断 | 进度回调，每千条指令回调一次，超时或超扫描上限则返回非零值中断 |
| 行数上限 | 取 `max_rows + 1` 行判断是否超限 |
| 只读加固 | 连接串用 `mode=ro`，并执行 `PRAGMA query_only = ON` |

## 开发顺序建议

按依赖顺序，先跑通最小链路再补节点：

1. 配置与依赖注入；
2. 网关（先验证桩实现可用）；
3. 数据访问层与守卫；
4. 三节点图，验证文本进 SQL 出结果回；
5. 补齐其余节点与条件路由；
6. 接入层与 SSE。

第 4 步不通，后面的语义层与图表都无从谈起。
