# 13 — 操作流程说明语料库

## 一次完整的使用流程

系统跑起来之后的正常路径只有六步：

1. 打开前端页面，点「新建会话」，拿到一个会话。会话 ID 同时是 LangGraph 的 thread_id，多轮上下文靠它累积。
2. 在输入框里提第一个问题。问题要包含指标、维度与时间范围三类信息中的至少两类，否则系统会走澄清分支。
3. 观察中间区顶部的阶段进度条。正常路径的八个业务节点依次点亮：意图识别 → 口径召回 → 生成查询 → 安全校验 → 执行查询 → 生成图表 → 生成结论，最后落到终态节点。阶段数量不是固定的三条原因：校验或执行失败时会回到「生成查询」再走一遍；闲聊类问题只经过意图识别就进入终态；信息不足时进入澄清分支，不执行后面的节点。修正次数上限由 `SQL_MAX_RETRY` 控制，默认 3，含义是首次生成之外最多再修正 3 次，合计 4 次尝试。
4. 读结果：先看顶部的一句话结论，再看口径标签确认统计范围，最后看图表与表格。需要核对时展开 SQL 面板。
5. 追问。第二轮可以直接说「那上个月呢」「按渠道拆开」，系统会接住指代。
6. 关掉页面后从历史会话回到同一个会话，之前的问答、SQL 与图表都在。

## 提问技巧

### 一句话里放哪些信息

自然语言取数的歧义主要来自三类信息缺失：指标不明确、维度不明确、时间范围不明确。补齐这三类，第一次就能出结果。

| 组成 | 说明 | 例子 |
|---|---|---|
| 指标 | 要算什么 | 成交总额、订单数、退款率、客单价 |
| 维度 | 按什么分组或看哪一类 | 按商品类目、按渠道、按城市 |
| 时间 | 统计区间 | 上个月、近7天、2025 年第三季度 |
| 筛选 | 额外的取值限制 | 只看已支付订单、只看华东 |
| 排序与条数 | 要前几名还是全部 | 前 10 名、按金额降序 |

### 好问法与差问法

**差**：帮我看下销售情况。
指标、维度、时间全缺，系统只能走澄清分支回问。

**好**：2025 年 8 月各商品类目的成交金额，按金额降序取前 10。
指标是成交总额，维度是商品类目，时间是 2025 年 8 月，排序与条数也给了。

**差**：上个月卖得最好的商品有什么问题？
「卖得最好」没有定义（按件数还是按金额），后半句的「问题」不是数据能回答的。拆成两句：先问「上个月销量前 10 的商品」，拿到结果后再问具体商品的退款率。

**好**：今年 618 期间，各渠道的订单数和退款率分别是多少？
两个指标同时问是可以的，前提是它们共享同一套维度与时间范围。

### 相对时间词的支持范围

配置中共 22 个相对时间词，由代码换算成具体日期区间后写进 Prompt，左闭右开：

今天、昨天、本周、上周、本月、这个月、上个月、上月、本季度、这个季度、上季度、上个季度、今年、本年度、去年、去年同期、近7天、近30天、近三个月、近半年、上半年、下半年。

换算结果会写进 Prompt，模型不需要再解释相对时间。这意味着「上个月」的口径固定为上一个自然月的 1 号到次月 1 号，不是最近 30 天。要最近 30 天就说「近30天」。

词条是精确匹配，写法要和配置一致：「最近 7 天」在配置里是「近7天」，中间没有空格，写成「最近 7 天」不会命中。配置里没有「今年以来」这个说法，对应的词条是「今年」与「本年度」，按自然年换算。

### 不适合问的问题

以下几类问题的答案不在数据库里，系统会给不出结果或给出无意义的结果：

- 预测类：「下个月销售额会是多少」。库里只有历史数据，没有预测模型。
- 归因类：「为什么转化率下降了」。下降幅度能算，原因需要业务判断与外部信息。
- 外部知识类：「我们的客单价在行业里算高吗」。库里没有行业基准。
- 跨数据源类：「把广告投放数据和订单数据放一起看」。系统只连一个 SQLite 库。
- 多步推理类：「先算出复购用户，再看他们的客单价分布」。两轮问答可以拆开做，一轮里做不了。

## 结果解读方法

### 先看口径标签

结果区顶部有一排口径标签，列出本轮命中的指标名、统计范围与边界说明。数字对不对，第一判断依据在口径标签，不在图表。

常见需要留意的三处：

**成交总额不扣退款。** 口径表达式是 `SUM(oi.quantity * oi.unit_price)`，只排除已取消订单，不减退款金额。要看扣退款后的净收入，需要单独问退款金额再相减。

**退款率的分母是订单数。** 口径是「有退款的订单数 / 已支付订单数」，不是退款金额除以成交总额。两种口径的数值可能差很多。

**时间区间左闭右开。** 「上个月」的结束日期是次月 1 号，SQL 里的条件是 `>= 起始 AND < 结束`。

### 再看 SQL 面板

SQL 面板默认折叠，展开后可以看到本轮实际执行的语句。核对三处就够：

1. `FROM` 后面的表是否是预期的那几张。
2. `WHERE` 里的时间条件是否与口径标签上的日期一致，是否带上了指标口径要求的必带条件（例如成交总额要排除已取消订单）。漏掉必带条件比聚合表达式写错更常见，而且从结果上更难发现。
3. 聚合表达式是否与指标口径一致，例如成交总额是否用了 `SUM(quantity * unit_price)`。

面板默认展示的是实际执行的语句，它可能已被安全守卫包裹成 `SELECT * FROM (...) AS _guard_limited LIMIT 1000` 的形式。手工核对时用展开区里的原始语句，它与模型输出一一对应；两条都能复制到 SQLite 命令行里执行。

### 图表怎么读

图表类型由结果集结构自动决定：

| 结果结构 | 图表 | 说明 |
|---|---|---|
| 维度 + 指标，维度是时间且按序 | 折线图 | 看趋势 |
| 维度 + 指标，维度是类别 | 柱状图 | 看对比 |
| 明确的占比语义 | 饼图 | 看构成，占比之和为 100% |
| 无维度或无法归类 | 表格 | 图型只有折线、柱状、饼图、表格四类，没有数字卡 |
| 行数过多或列数过多 | 只出表格 | 图表表达不了就出表格 |

图型由后端在 `chart.chart_type` 中给出，前端不重新决策。图表右上角的切换只改变渲染形态（例如在柱状图与折线图之间切、切到纯表格），不改变后端给出的图型与数据，也不触发重新查询。

### row_count 与展示行数

`row_count` 是本轮下发的行数，不是结果集的真实命中行数。安全沙箱对无 `LIMIT` 或超限的语句自动包裹 `LIMIT 1000`，截断发生时 `truncated` 为 `true`，此时 `row_count` 等于上限值，真实行数比它大。

前端表格默认只渲染前若干行，超过部分需要滚动或翻页，这与截断是两回事，不属于数据丢失。需要全量数据时应改成聚合查询而不是调大上限。

## 多轮追问能接住什么

多轮上下文由 LangGraph 的 Checkpointer 按 thread_id 保存，历史消息与上一轮的状态都会带进下一轮。

能接住的：

- 指代时间：「那上个月呢」「去年同期」。
- 增删维度：「按渠道拆开」「不看渠道，看类目」。
- 增减筛选：「只看已完成的」「排除测试订单」。
- 改排序与条数：「改成前 5 名」。

接不住的：

- 隔轮指代：在第三轮说「再看看它的退款率」，而第二轮里没有明确的「它」。
- 跨指标引用：上一轮问成交总额，这一轮说「把上面那个数除以订单数」。
- 隐含口径切换：上一轮是含退款的口径，这一轮说「按净额算」，系统不知道净额指什么。

接不住的表现是系统重新生成一条与预期无关的 SQL，或者走澄清分支。遇到这种情况，把问题写完整即可，不必重开会话。

## 结果存疑时的三步核查

数字与预期不一致时，按下面三步定位，比反复改问法有效：

**第一步，看 SQL 与口径标签是否一致。** 如果 SQL 里的聚合表达式与指标口径不同，说明模型没有采用召回的口径，是生成问题。

**第二步，用 `/api/semantic/recall` 看召回了什么。** 传入原问题，接口会返回命中的指标、表、维度、匹配词与时间区间。如果指标没命中，问题多半出在同义词配置上，需要往 `synonyms.yaml` 里补词。

**第三步，把 SQL 复制到 SQLite 里手工执行。** 这一条区分「模型写错」与「口径本身就是这个数」。很多看似错误的数字，其实是口径定义与提问者的预期不同，例如成交总额不扣退款。

## 演示时的建议顺序

课程演示按下面的顺序走，能覆盖全部关键能力且不容易翻车：

1. 单指标单维度：最近 30 天各渠道的订单数。展示基础链路与柱状图。
2. 时间趋势：2025 年每月的成交总额。展示折线图与相对时间换算。
3. 追问：改成按商品类目。展示多轮上下文与指代接住。
4. 触发澄清：就问「看看销售」。展示澄清分支的回问。
5. 触发拦截：问一个会命中守卫规则的问题，例如让模型去查一张未登记的表，或让它执行删除类操作。展示守卫的拦截文案与规则编号。本项目只连一个 SQLite 库，不存在跨库查询的场景。
6. 打开 SQL 面板与 `/api/semantic/health`。展示口径可追溯与一致性自检。
