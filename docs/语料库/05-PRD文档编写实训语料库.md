# 05 — PRD 文档编写实训语料库

## PRD 的作用

产品需求规格说明书回答三个问题：要做什么、为什么做、做到什么程度算完成。它是后续所有工作的共同依据——架构设计、界面设计、任务拆解都要与它对齐。

一份 PRD 写得好不好，判断标准不是篇幅，而是能否用它做验收。读完以后还不知道「做完没有」的 PRD，等于没写。

## 标准结构

本项目采用的六节结构：

| 节 | 内容 | 作用 |
|---|---|---|
| 背景与问题 | 现状、现有方案局限、本项目切入点 | 说明为什么做 |
| 目标用户与场景 | 角色、特征、使用场景 | 界定为谁做 |
| 功能需求 | 按模块的需求表，含编号、优先级、验收方式 | 说明做什么 |
| 数据范围 | 表结构、指标口径、可用维度 | 界定数据边界 |
| 非功能需求 | 安全、性能、可复现、可观测、可移植、透明 | 界定质量底线 |
| 明确不做的事 | 本版不实现的范围 | 防止范围蔓延 |
| 验收标准 | 每项对应一个可执行的检查动作 | 说明做完的标志 |

「明确不做的事」这一节在多数 PRD 模板中不存在，但对本项目是必要的。评审时最常被问到的不是「你还打算做什么」，而是「这个功能为什么没有」，提前写清楚更省事。

## 需求分析方法

### 从链路找痛点

不要笼统地说「取数效率低」，要把它定位到具体链路上的等待。本项目的表述是：提需求、等排期、拿报表，一个简单问题要等半天到一天。这样定位之后，解决方案才有的放矢。

### 用对比表找切入点

列出三种现有方案，逐条写明「能做到什么」与「局限是什么」。本项目的切入点是保留第三种方案（直接把表结构交给模型）的低门槛，用工程手段消除它的两个问题。

### 按模块组织需求

按用户能感知的功能模块分组，不要按技术模块分组。用户感知的是「对话取数」「图表与结论」，不是「编排层」「语义层」。

技术模块的分工属于架构设计文档，不属于 PRD。

## 优先级标注

采用 MoSCoW：

| 标记 | 含义 | 本项目中的例子 |
|---|---|---|
| M | 必须交付 | 对话取数、SQL 展示、图表与结论、评测集 |
| S | 应当交付 | 历史会话 |
| C | 可以交付 | 结果导出 |
| W | 本次不做 | 鉴权、多数据源、缓存 |

标注优先级的意义在于发生冲突时知道砍什么。全部标 M 等于没标。

## 验收标准写法

常见的错误写法是把需求复述一遍：

| 错误 | 正确 |
|---|---|
| 「支持多轮追问」 | 「连续三问，后两问能继承上文的主体与指标」 |
| 「查询要快」 | 「单条查询十秒内返回，超出则中断并说明原因」 |
| 「图表展示合理」 | 「时间维度得折线、单维度对比得柱状、占比得饼图」 |
| 「系统安全可靠」 | 「守卫七条规则逐条有一正一反两个用例，仓储层超时中断另有用例」 |

规律是：验收标准必须包含一个动作和一个可观察的结果。读到它就知道该去哪里看什么。

## 数据范围为什么写进 PRD

多数 PRD 不涉及具体表结构，但本项目必须写，原因是口径是这个项目的核心。

如果 PRD 里只写「支持销售额分析」，架构设计就没法确定要定义哪些口径，语义层的配置也就失去了依据。写明七个指标及其口径要点，后续所有环节才有共同参照。

同时它也划定了数据边界：只有这六张表、这七个指标、这九个维度是受支持的，超出部分不在本版范围内。

## 与非功能需求有关的本项目特性

| 类别 | 本项目的具体要求 | 原因 |
|---|---|---|
| 安全 | 只允许单条 SELECT，表与字段走白名单 | 模型输出不可信 |
| 可复现 | 样例库固定随机种子 | 演示与评审需要一致的结果 |
| 可移植 | 密钥只在 `.env`，依赖锁定 | 干净环境可重建 |
| 透明 | 任何数字可追溯到语句与口径 | 这是本项目的核心卖点 |

## AI 共创时的注意点

让 AI 写 PRD 时，把技术栈、运行形态、目标用户、已有架构文档一并给出。审查时重点看三处：是否混入了实现细节（实现细节属于开发任务文档）、是否出现本项目不具备的能力、验收标准是否可检验。

篇幅控制在 2000 到 3000 字。超过这个量级通常说明混入了不该在 PRD 里出现的内容。
