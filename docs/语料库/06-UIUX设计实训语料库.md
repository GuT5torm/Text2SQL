# 06 — UI/UX 设计实训语料库

## 本项目的界面设计约束

界面设计不是从美观出发，而是从三条约束出发：

1. 一次问答要等模型多轮响应，中间经过八个业务节点，最后落到三个终态节点之一（一次问答只会命中其中一个），等待必须可感知；
2. 任何数字都要能追溯到具体语句与具体口径；
3. 前端不做业务判断，只做展示与字段校验。

第三条尤其重要。模型给出的图表配置可能引用不存在的字段，前端必须校验，但校验的是「字段是否存在」，不是「图表类型对不对」。后者由后端决定。

## 信息架构

```
ChatPage（主页面）
├── 顶部栏            会话标题 / 新建会话 / 历史入口
├── 左侧：对话区
│   ├── 消息流        用户提问气泡 + 助手回答卡片
│   └── 输入框        自适应高度，Enter 发送，Shift+Enter 换行
└── 右侧：结果区
    ├── 结论卡片      经营解读 + 亮点 + 口径说明
    ├── 图表区        ECharts 容器，高度固定 320px
    ├── SQL 面板      Collapse，默认折叠
    └── 结果表格      可横向滚动，行数多时分页

HistoryPage（历史会话）
├── 搜索框            按问题关键词过滤
├── 状态筛选          全部 / 未归档 / 已归档
└── 会话列表          标题、时间、轮次、操作（查看 / 归档 / 删除）
```

归档是软删除：归档后的会话不在默认列表中出现，通过状态筛选可以找回，记录本身不删除。

## 三区布局规范

| 区域 | 宽度 | 说明 |
|---|---|---|
| 对话区 | 默认 420px，可拖拽，范围 320–560px | 拖拽边界即上下限 |
| 结果区 | 自适应 | 最小 640px |
| 间距 | 区域间 16px，卡片间 12px | 沿用组件库基础间距 |

窗口宽度小于 1024px 时改为上下堆叠，对话区在上、结果区在下。

## 助手回答卡片的固定结构

```
┌────────────────────────────────────────┐
│ 阶段指示（完成后收起为一行）              │
├────────────────────────────────────────┤
│ 结论文本                                │
│ · 亮点 1                                │
│ · 亮点 2                                │
├────────────────────────────────────────┤
│ [口径标签] 成交总额  [口径标签] 不含取消单  │
├────────────────────────────────────────┤
│ 图表区                                  │
├────────────────────────────────────────┤
│ ▸ 查看执行的 SQL                        │
├────────────────────────────────────────┤
│ 结果表格                                │
└────────────────────────────────────────┘
```

顺序的依据是阅读路径：先看结论，再看依据，最后看明细。口径标签紧跟着结论，是因为它解释结论中的数字是怎么来的。

## 流式进度反馈设计

这是本项目界面区别于普通聊天界面的地方。后端通过 SSE 推送节点进度，前端按事件追加显示。

节点名到展示文案的映射：

| 节点 | 展示文案 |
|---|---|
| `route` | 正在理解问题 |
| `retrieve` | 正在匹配指标口径 |
| `generate` | 正在生成查询 |
| `validate` | 正在校验查询安全性 |
| `execute` | 正在执行查询 |
| `fix` | 正在依据报错修正查询 |
| `visualize` | 正在选择图表 |
| `summarize` | 正在分析结果 |
| `respond` | 已给出回答 |
| `clarify` | 需要补充信息 |
| `give_up` | 未能生成可执行查询 |

共十一个节点：八个业务节点加 `respond`、`clarify`、`give_up` 三个终态节点。终态节点同样推送 `stage` 事件，因此映射表里漏掉 `respond` 会让闲聊类问答的最后一个阶段直接显示英文节点名。

设计要点：阶段事件按到达顺序追加，不重排；完成后收起为一行，避免占用过多空间；`fix` 阶段要标明是第几次修正，让用户知道系统在自我纠正而不是卡住；`stages` 的作用域是单轮问答，发起新一轮时先清空，否则第二轮会带上第一轮的阶段记录。

## 状态设计

| 步骤 | 界面表现 |
|---|---|
| 用户提交 | 输入框禁用，出现用户气泡 |
| 收到 `stage` | 阶段指示追加一条，显示标签与耗时 |
| 收到 `result` | 渲染结论、口径标签、图表、SQL 面板、表格 |
| 收到 `error` | 展示错误文案，保留已收到的阶段记录 |
| 收到 `done` | 关闭连接，输入框恢复可用 |

## 异常态设计

| 状态 | 表现 | 引导 |
|---|---|---|
| SQL 被拦截 | 黄色提示条，展示规则编号与原因 | 建议换更具体的问法 |
| 重试中 | 阶段指示中出现修正，标注第几次 | 无需干预 |
| 重试耗尽 | 红色提示，展示最后一次语句与报错 | 建议缩小范围或补充口径 |
| 结果为空 | 蓝色提示，说明可能原因 | 建议放宽时间范围 |
| 反问（`status = clarify`） | 灰色提示条，列出需要补充的信息与可选项 | 点选可选项或重新表述问题 |
| 闲聊（`status = chitchat`） | 常规回答气泡，附可用问法示例 | 从示例中选一个继续提问 |
| 网络中断 | 顶部全局提示 | 提供重试按钮 |

失败态的设计原则是：给出原因，给出下一步。只显示「出错了」的界面会把问题推给用户去猜。

## 视觉规范

### 配色

| 用途 | 取值 |
|---|---|
| 主色 | `#1677FF` |
| 成功 | `#52C41A` |
| 警告 | `#FAAD14` |
| 错误 | `#FF4D4F` |
| 文本主色 | `rgba(0,0,0,0.88)` |
| 文本次色 | `rgba(0,0,0,0.45)` |
| 图表序列色 | 10 色循环 |

**金额与涨跌不使用红绿语义色。** 本项目是经营数据分析，不是行情看板，用红绿会与股票涨跌的配色惯例混淆。这是本项目刻意偏离常见做法的一处。

### 字体与圆角

| 项 | 取值 |
|---|---|
| 正文字号 | 14px，行高 1.6 |
| 结论文本 | 15px，行高 1.75 |
| 代码字号 | 13px，等宽字体 |
| 圆角 | 卡片 8px，标签 4px，输入框 6px |

### 图表规范

| 项 | 规则 |
|---|---|
| 高度 | 固定 320px |
| 标题 | 由后端给出，用卡片标题呈现，不画在图表内 |
| 图例 | 序列数大于 1 时显示，置于底部 |
| 坐标轴标签 | 超过 8 个字符截断加省略号，悬浮显示全称 |
| 数值格式 | 金额千分位加两位小数；比率显示百分比 |
| 空数据 | 不渲染图表，改为表格呈现 |

## 组件清单与约束

| 组件 | 职责 | 关键约束 |
|---|---|---|
| `StageIndicator` | 显示节点进度 | 事件按到达顺序追加，不重排 |
| `ChatPanel` | 输入与消息流 | 发送后禁用输入直到收到结果或错误 |
| `ChartPanel` | 图表渲染 | 渲染前校验字段存在于结果集列，否则退回表格 |
| `SqlPanel` | SQL 折叠展示 | 展示实际执行的语句；存在改写时同时展示改写前语句 |
| `ResultTable` | 结果集表格 | 超过 50 行分页；列名直接取结果集列名 |
| `MetricBadge` | 口径标签 | 内容取自返回的指标与边界说明 |
| `useChatStream` | SSE 接收 | 解析四类事件，`done` 时关闭连接 |

## 前后端契约

前端直接消费的字段：

| 字段 | 用途 |
|---|---|
| `stages[]` | 阶段指示的数据源。每项含 `node` / `label` / `status`（`running` / `done` / `failed`）/ `duration_ms` / `detail`。作用域为单轮问答，不跨轮累积 |
| `answer` / `insight` / `highlights` | 结论卡片 |
| `metric_used` / `caveats` / `time_range` | 口径标签 |
| `chart.chart_type` / `chart.option` | 图表渲染，图型由后端决定 |
| `sql` / `original_sql` | SQL 面板。`sql` 是实际执行语句，可能已被行数上限包裹；`original_sql` 是模型原始语句 |
| `columns` / `rows` / `row_count` / `truncated` | 结果表格。`truncated` 为 `true` 时 `row_count` 是截断后的行数，不是真实命中行数 |
| `guard.rule_id` / `guard.reason` | 拦截提示条 |
| `attempts` | 生成尝试次数（整数）；每次修正的改动说明取自 `stages[].detail` |
| `status` | 决定展示哪一类终态。取值为 `ok` / `clarify` / `chitchat` / `error` 四个，分别对应成功态、反问态、闲聊态、失败态 |

## AI 共创时的注意点

让 AI 设计界面时，必须写明「一次问答要等数秒到十几秒」。不写这条，AI 会按几百毫秒响应的常见聊天界面设计，不会考虑阶段进度。

审查时重点看四处：是否只设计了成功态、是否混入了鉴权界面、是否用红绿表示涨跌、组件职责中是否出现了业务判断。
