# 01 — 项目背景与需求语料库

## 业务背景

电商经营分析中，业务人员需要看一个临时数据时的典型路径是：向数据团队提出需求、等待排期、拿到报表。一个简单问题从提出到拿到结果，通常需要半天到一天。对于「上个季度华东区各品类的成交总额」这类明确且一次性的问题，等待时间远超问题本身的价值。

这条路径的成本不在于计算，而在于沟通与排队。问题本身可能只需要一条十几行的 SQL，但要让数据团队理解意图、确认口径、安排时间、交付结果，中间每一步都要等人。

## 传统方案的局限

**固定报表平台**覆盖常规指标，数据经过验证，但维度组合是预先定义的。业务人员想看一个报表上没有的切分角度，就只能重新提需求。报表数量与覆盖率之间是一对矛盾：做得全则维护成本高，做得少则覆盖面不足。

**自助 BI 工具**把取数能力交给了业务人员，通过拖拽维度与度量生成查询。它解决了排期问题，但要求使用者理解表结构与指标定义。业务人员面对几十张表和上百个字段，通常不知道「成交额」应该取自订单主表还是明细表，也不知道是否要排除取消订单。

**直接把表结构交给大模型**是出现大语言模型之后的一种直觉做法。它把门槛降到了最低，用中文就能提问，但暴露出两类问题：

1. 口径歧义。「销售额」「销量」在不同人眼里指向不同的聚合方式，「销量」可能指订单数也可能指商品件数，「销售额」是否扣退款、是否含取消订单都是口径问题。模型只能猜测，同一句话两次问可能得到两个不同的数。
2. 输出不可控。模型可能编造不存在的字段，写出语法正确的错误查询；也可能生成影响数据完整性的语句。

## 方案定位

本项目定位在第三种做法的基础上做工程加固，保留自然语言提问的低门槛，用两处手段消除它的两个问题。

**语义层解决口径问题。** 把业务词的聚合口径写成显式配置，包含口径表达式、依赖表、必带条件与边界说明。生成 SQL 之前先召回相关口径，模型只在给定口径内组合，不自行定义。问「销售额」得到什么，取决于配置怎么写，而不是模型当天怎么理解。

**SQL 安全沙箱解决输出可控问题。** 所有生成的语句在执行之前经过 AST 级校验，只放行单条只读查询，表与字段走白名单，强制 LIMIT，配合只读连接与超时中断。

这两处决定了本项目与「调一次大模型接口」的本质区别：结果可复现、可解释、可审计。每一个数字都能追溯到具体的口径定义与具体的执行语句。

## 核心功能需求

按四个模块组织：

**对话取数。** 单页对话界面，输入自然语言问题；支持多轮追问，能处理「那上个月呢」这类省略主语的问法；信息不足时主动反问而非猜测；等待期间按节点推送当前阶段。

**SQL 展示与口径标注。** 每轮回答下方展示实际执行的语句，默认折叠；标注本轮采用的指标口径与边界说明；校验拦截时展示具体原因；修正重试过程可见。

**图表与分析结论。** 结果集自动匹配图表类型，时间维度走折线、单维度对比走柱状、占比走饼图、多列宽表退回表格；图表配置在渲染前做字段校验；结论区给出经营解读并注明口径与数据范围。

**历史会话。** 保存历次问答记录，含问题、结论、语句与结果集快照；支持关键词搜索；支持查看、删除、归档。

## 目标用户

| 角色 | 特征 | 关注点 |
|---|---|---|
| 业务运营 | 不看 SQL，只看结论与图表 | 结论可读、口径可见 |
| 数据分析师 | 看得懂 SQL，关注口径定义 | 口径正确、语句可查 |
| 答辩评审与学习者 | 关注架构与实现 | 链路完整、可复现 |

演示场景以业务运营为主，因此「口径可见」与「结论可读」是必须项。

## 不解决的问题

本项目不解决以下问题，写在需求中是为了避免评审时被当成遗漏：不提供用户体系与鉴权；不做数据写入；不做多数据源接入；不做查询缓存与异步任务；不做实时数据同步。它是一个面向单机演示场景的查询助手，不是企业级 BI 平台。
