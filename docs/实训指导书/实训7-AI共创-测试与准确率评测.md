# 实训 7 — AI 共创：测试与准确率评测

## 一、实训目标

1. 为 SQL 安全守卫编写单元测试，守卫七条规则逐条有用例覆盖，语句超时中断在仓储层单独覆盖
2. 为语义层编写加载与召回测试，锁定配置改动的影响
3. 构造评测集，每条含问题与验证方式，覆盖七个指标与主要维度
4. 编写评测脚本，跑出可执行率与准确率基线
5. 理解为什么准确率目标要在基线产出之后再定，而不是预先拍一个数字

## 二、前置条件

| 项 | 要求 |
|---|---|
| 前置产出 | 实训 4 的语义层、实训 5 的后端链路 |
| 环境 | 已安装 `pytest`、`httpx`（用于接口测试） |
| API 密钥 | 建议配置真实密钥。桩实现只验证链路，不反映准确率 |

## 三、知识点

| 知识点 | 说明 |
|---|---|
| 规则单测 | 安全规则是安全边界的最后一道，逐条有用例才有说服力 |
| 召回测试 | 配置改动会改变召回结果，用测试锁定预期 |
| 评测集 | 问题与验证方式的集合，是 Prompt 调整的依据 |
| 可执行率 | 生成的语句能通过校验并成功执行的比例 |
| 结果准确率 | 在可执行的基础上，返回值与预期一致的比例 |
| 基线 | 先跑出基线再定目标，避免设定无法验证也无从改进的指标 |

## 四、操作步骤

### 步骤 1：守卫规则单测

`tests/test_guard.py` 按守卫七条规则组织用例，每条规则至少两个用例：一个应被放行，一个应被拦截。

用例来源要覆盖真实场景，例如多表查询缺少连接条件、字段未登记、语句缺少 LIMIT、结果集超限。

R8 语句超时不在守卫内实现，它的用例写在 `tests/test_repository.py` 中，与步骤 3 的三类断言放在一起，不混入本文件的用例矩阵。

**预期输出**：守卫七条规则各有对应用例，全部通过。

### 步骤 2：语义层测试

`tests/test_semantic.py` 验证三件事：三份 YAML 能加载且一致性校验通过；典型问题能召回预期指标与维度；相对时间词换算的区间正确。

**预期输出**：改坏一处配置时，测试能指出具体是哪一处。

### 步骤 3：仓储测试

`tests/test_repository.py` 验证只读连接拒绝写操作、超时中断生效、超长结果集被正确截断。

**预期输出**：写操作被拒绝，超时用例能在预期时间内返回。

### 步骤 4：节点测试

`tests/test_nodes.py` 用打桩的网关替换真实调用，验证单个节点的输入输出与异常分支。

打桩是关键。节点测试不应该依赖真实模型，否则测试既慢又不稳定。

**预期输出**：节点测试不产生任何真实模型调用。

### 步骤 5：接口冒烟测试

`tests/test_api.py` 用 `httpx` 的 `ASGITransport` 直接调用应用，不启动真实服务。覆盖四类接口：健康检查、语义层一致性、会话 CRUD 与归档、同步对话。

同步对话的用例需要先创建会话。对话接口在会话不存在时返回 404，不自动新建，用例里要先 `POST /api/session` 再拿返回的 `id` 发问。

**预期输出**：四类接口的正常路径各有一条用例，错误路径至少覆盖「会话不存在」一种。

### 步骤 6：构造评测集

`eval/cases.yaml` 中每条包含编号、问题、类别、验证方式。类别按指标与维度组合划分：七个指标各自至少一条，时间维度、区域、渠道、品类各若干条，另含多轮追问与反问场景。

验证方式分两类：可执行类只要求语句能跑通并返回非空结果；结果类给出期望值或期望的判定条件。

**预期输出**：评测集二十到三十条，覆盖七个指标与主要维度。

### 步骤 7：编写评测脚本

`eval/run_eval.py` 逐条调用同步接口，记录状态、语句、耗时与是否匹配预期，最后输出汇总：总数、可执行数、可执行率、结果正确数、准确率、平均耗时。

对失败条目输出问题与失败原因，便于逐条定位。

**预期输出**：汇总结果可复现，失败条目能定位。

### 步骤 8：跑出基线

在配置真实密钥的环境下运行评测脚本，把结果记录下来。

```bash
cd backend
python eval/run_eval.py
```

**预期输出**：一份汇总结果，含可执行率与准确率。

### 步骤 9：依据基线改进

从失败条目中归纳错误类型：字段编造、口径理解错误、时间范围错误、连接条件缺失。按类型归因后调整 Prompt 或补充语义层配置，再跑一次对比。

每次只改一处，改完立刻复跑。一次改多处，结果变好了也不知道是哪一处起作用。

**预期输出**：改进前后的对比记录。

## 五、AI 共创要点

**怎么问**：让 AI 写测试用例时，把规则定义一并给出。只说「给守卫写单元测试」，AI 会写出覆盖常规 SQL 的用例，漏掉本项目特有的规则。

一个可用的提问结构：

```
被测规则：<贴出守卫七条规则的编号与含义>
任务：为每条规则写至少两个用例（应放行 / 应拦截）
要求：
1. 用例覆盖真实失败场景，而不是理想输入
2. 断言要检查具体的规则编号，不只检查是否报错
```

**常见偏差**：

| 偏差 | 表现 | 处理 |
|---|---|---|
| 用例只测正常输入 | 全是合法 SELECT | 每条规则补一个应被拦截的用例 |
| 断言太宽 | 只断言「抛异常」 | 断言具体的规则编号与原因 |
| 节点测试调真实模型 | 测试很慢且结果不稳定 | 用打桩网关替换 |
| 评测集过小 | 只有五条问题 | 扩到二十条以上并覆盖七个指标 |
| 准确率目标先拍数字 | 先写「准确率达到 90%」 | 先跑基线，再按基线定目标 |
| 一次改多处 | Prompt 与配置一起改 | 每次只改一处并复跑 |

**审查动作**：跑一次测试并故意改坏一处配置，确认有测试失败。全部通过但改坏了配置却仍能通过，说明测试没有真正锁住行为。

## 七、检查点

- [ ] 守卫七条规则每条至少两个用例，全部通过；R8 超时用例在仓储测试中
- [ ] 语义层测试能在配置改坏时指出具体位置
- [ ] 仓储测试覆盖写拒绝、超时、截断三类
- [ ] 接口冒烟测试覆盖四类接口，会话不存在返回 404

- [ ] 基线与改进后的结果都有记录

## 八、常见问题

**问题：测试全绿，但改坏 YAML 后测试仍然通过。**
原因：测试只验证了「能加载」，没有断言具体内容。解决：断言具体的指标数量、维度名称与召回结果。

**问题：评测集跑出来全是失败。**
原因：多半是密钥未配置，走的是桩实现。解决：确认健康检查接口返回的 `llm_mock` 为 `false`。

**问题：可执行率高但准确率低。**
原因：语句能跑通，但口径或时间范围理解错了。解决：按错误类型归因，优先补充语义层的口径说明与同义词，而不是反复调 Prompt。

**问题：复跑结果和上次不一样。**
原因：模型输出有随机性，或评测集依赖了会变化的数据。解决：将温度设为 0，评测集中涉及时间的用例改用相对时间而非固定日期。
