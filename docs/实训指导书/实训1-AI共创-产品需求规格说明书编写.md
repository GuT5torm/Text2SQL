# 实训 1 — AI 共创：产品需求规格说明书编写

## 一、实训目标

1. 说清 Text2SQL 项目要解决的问题，能把「业务取数慢」这个模糊痛点拆成可验证的功能需求
2. 编写一份结构完整的 PRD，覆盖背景、用户、功能需求、非功能需求与验收标准
3. 在 PRD 中显式写出「明确不做的事」，避免评审时被当成功能遗漏
4. 用 AI 辅助完成需求梳理，并能判断 AI 给出的需求条目中哪些是臆造的

## 二、前置条件

| 项 | 要求 |
|---|---|
| 输入材料 | 《项目提示词.txt》《Text2SQL-Agent-系统架构设计.md》 |
| 环境 | 无特殊要求，Markdown 编辑器即可 |
| 知识 | 了解 SQL 基础语法与电商经营分析的基本指标概念 |

## 三、知识点

| 知识点 | 说明 |
|---|---|
| 问题定义 | 把「取数慢」定位为具体链路上的等待，而不是笼统的效率问题 |
| MoSCoW 优先级 | M 必须、S 应该、C 可以、W 本次不做，用于约束范围 |
| 功能需求条目化 | 每条需求写清验收方式，避免「支持某某功能」这类无法检验的表述 |
| 非功能需求 | 安全、性能、可复现、可观测、可移植、透明六个维度，本项目尤其重视安全与可复现 |
| 口径定义 | 业务词的聚合方式必须写成配置，这是本项目需求的特殊性 |

## 四、操作步骤

### 步骤 1：梳理现有方案的局限

列出三种现有取数方式并逐条写明局限，形成对比表：

- 固定报表平台：覆盖常规指标但维度组合固定
- 自助 BI 工具：可拖拽但要求使用者理解表结构
- 直接把表结构交给大模型：门槛低但口径靠猜、可能编造字段、有破坏性语句风险

**预期输出**：三行对比表，每行的「局限」列能直接对应到本项目要解决的手段。

### 步骤 2：确定目标用户与场景

区分三类角色：业务运营、数据分析师、答辩评审。指出演示场景以业务运营为主，由此推出「口径可见」与「结论可读」是必须项。

**预期输出**：角色表，含特征与使用场景两列。

### 步骤 3：按模块写功能需求

按五个模块展开：对话取数、SQL 展示与口径标注、图表与分析结论、历史会话、评测集。每条需求标注编号与优先级，并写出验收方式。

评测集这一模块不要漏。它是「准确率可验证」的载体，漏掉之后答辩时无法回答「准确率是多少」。

验收方式要可操作。例如「支持多轮追问」的验收方式是「连续三问，后两问能继承上文主体与指标」，而不是「支持多轮」。

**预期输出**：五张需求表，共十八条。

### 步骤 4：定义数据范围

列出六张表及其粒度与用途，列出七个指标的口径要点与边界说明，列出九个可用维度。这部分内容必须与后续 `semantic/` 下的配置保持一致。

**预期输出**：三张表格，可直接对照 `metrics.yaml` 核对。

### 步骤 5：写非功能需求

按安全、性能、可复现、可观测、可移植、透明六个维度各写一条。安全维度要把守卫七条规则与仓储层超时中断的意图写进去。

**预期输出**：六行表格。

### 步骤 6：明确不做的事

列出六条不实现的内容，例如不做用户鉴权、不做写入、不做向量检索、不做多数据源、不做缓存队列、不做容器化。

**预期输出**：六条清单。

### 步骤 7：写验收标准

每项标准对应一个可执行的检查动作，例如「查询安全」对应「守卫单测全部通过，守卫七条规则逐条有用例覆盖，语句超时中断在仓储层单独有用例」。

**预期输出**：六行验收表。

## 五、AI 共创要点

**怎么问**：把约束一起给 AI。只说「帮我写一份 PRD」，得到的是通用模板；把技术栈、运行形态、目标用户、已有的架构文档一起给进去，得到的内容才贴合项目。

一个可用的提问结构：

```
背景：<项目要解决什么问题>
约束：<技术栈 / 运行形态 / 目标用户 / 已有的架构决策>
任务：按 <背景 / 用户 / 功能需求 / 非功能需求 / 不做的事 / 验收标准> 六节写 PRD
要求：每条功能需求附验收方式；不要写本项目不具备的能力
```

**常见偏差**：

| 偏差 | 表现 | 处理 |
|---|---|---|
| 需求膨胀 | 加入权限管理、任务调度、多租户 | 与「明确不做的事」对照，删掉 |
| 验收空泛 | 「系统响应迅速」「界面友好」 | 改成可数可测的表述 |
| 臆造能力 | 写上实时数据同步、自动归因分析 | 对照架构文档第 10 节的演进阶段，超出 P0 的一律删 |
| 口径含糊 | 「支持各种指标分析」 | 换成七个具体指标及其口径要点 |

**审查动作**：AI 产出后，逐条问「这条需求的实现落在哪个模块」。答不上来的条目，要么是臆造，要么超出了当前形态。

## 七、检查点

- [ ] 现有方案的三个局限都能对应到本项目的具体手段
- [ ] 角色表中演示场景的主要角色已标明
- [ ] 功能需求每条都有编号、优先级与验收方式
- [ ] 数据范围的三张表与 `semantic/` 下的配置一致
- [ ] 非功能需求覆盖安全与可复现两类，共六个维度
- [ ] 功能需求覆盖五个模块，评测集模块未遗漏
- [ ] 「明确不做的事」不少于五条
- [ ] 每条验收标准能对应一个可执行的检查动作

## 八、常见问题

**问题：写出来的需求和架构文档对不上。**
原因：写 PRD 时没有先读架构文档，或者读的是早期版本。解决：以架构文档第 10 节的 P0 形态为准，凡属 P1、P2 的内容一律移入「不做的事」。

**问题：需求条目越写越多收不住。**
原因：把「用户可能想要」当成了「本项目要做」。解决：每条需求都要能回答「不做这条，演示链路还完整吗」。答「完整」的移入 C 或 W。

**问题：验收方式写成了需求本身的复述。**
原因：没区分「做成什么样」和「怎么知道做成了」。解决：验收方式必须包含一个动作和一个可观察的结果。
