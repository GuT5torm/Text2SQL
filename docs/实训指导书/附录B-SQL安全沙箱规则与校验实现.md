# 附录 B — SQL 安全沙箱规则与校验实现

> 适用：《实训5-AI共创-后端开发》第 4 步
> 实现位置：`backend/app/db/guard.py`
> 解析库：sqlglot

---

## 一、为什么需要安全沙箱

模型生成的 SQL 存在不确定性，一次 `DROP TABLE` 就意味着重建样例库。即使演示环境只有自己使用，也必须做执行前校验。

第二个理由是这套机制本身构成项目的技术亮点。把「模型输出不可信」这个前提用工程手段处理掉，比单纯展示一次成功问答更有说服力。

校验发生在执行之前，与执行分属两个节点：`validate` 节点只调守卫，`execute` 节点只调仓储。这条分界保证任何进入执行环节的语句都已经过校验。

---

## 二、守卫七条规则与一项执行期保护

守卫负责「这条语句能不能执行」的判断，共七条规则。语句超时不属于守卫，它由仓储层在执行过程中实现，列在表中是因为它与守卫七条共同构成安全边界。

| 编号 | 规则 | 检查内容 | 违反后的处理 | 实现位置 |
|---|---|---|---|---|
| R1 | `SINGLE_STATEMENT` | 只允许一条语句，不允许分号分隔多条 | 拦截，要求重新生成 | 守卫 |
| R2 | `SELECT_ONLY` | 语句类型必须是 SELECT，或 UNION / EXCEPT / INTERSECT | 拦截 | 守卫 |
| R3 | `FORBIDDEN_KEYWORD` | 禁止 DDL 与 DML 关键字及写操作语句 | 拦截 | 守卫 |
| R4 | `TABLE_NOT_ALLOWED` | 出现的表必须已在语义层登记 | 拦截，提示未登记的表名 | 守卫 |
| R5 | `COLUMN_NOT_ALLOWED` | 字段必须属于所引用的表 | 拦截，提示最接近的候选字段 | 守卫 |
| R6 | `LIMIT_ENFORCED` | 必须有 LIMIT 且不超过阈值 | 自动包裹，不改语义 | 守卫 |
| R7 | `CARTESIAN_JOIN` | 多表查询必须有连接条件 | 拦截，要求补连接条件 | 守卫 |
| R8 | `STATEMENT_TIMEOUT` | 执行超过阈值则中断 | 中断并返回超时说明 | 仓储层，非守卫规则 |

R6 与其他规则不同：它是唯一的自动改写规则，不拦截而是包裹。守卫其余六条一律拦截并把原因回传给 `fix` 节点。

### 2.1 R1 单条语句

用解析库把输入解析为语句序列，长度大于 1 即拦截。用分号计数不可靠，字符串字面量中可能出现分号。

### 2.2 R2 仅 SELECT

检查解析结果的根节点类型。允许的语句类型为 `Select`、`Union`、`Except`、`Intersect`。CTE 形式（`WITH ... SELECT`）同样放行，因为它的根节点仍是 `Select`。

### 2.3 R3 禁用关键字

按语句类型拦截，而不是按关键字文本匹配。遍历 AST 节点，命中禁用类型即拦截。

需要注意两类容易被遗漏的语句：

- `PRAGMA`。它可以修改数据库行为，不属于查询；
- `VACUUM`、`ATTACH`、`DETACH`。在某些解析库中这类语句不对应独立的表达式类型，而是落到通用命令节点上，需要按命令文本判断。

用关键字文本匹配会漏掉这两类，因此以 AST 节点类型为主、命令文本为辅。

### 2.4 R4 表白名单

遍历 AST 中的表节点，逐个比对语义层登记的表名。两处需要排除：

- CTE 名。WITH 子句定义的临时名称不是真实表；
- 子查询别名。派生表的别名同样不是真实表。

不排除这两类，任何用了 CTE 或派生表的合法查询都会被误拦。

### 2.5 R5 字段白名单

先建立别名到真实表名的映射，再逐个校验字段所属的表。作用域无法确定的部分（子查询内部、CTE 内部）跳过校验，避免误报。

对未登记的字段给出最接近的候选，便于 `fix` 节点做定向修正。只说「字段不存在」，模型下一轮往往还是猜错。

### 2.6 R6 强制 LIMIT

无 LIMIT 或 LIMIT 超过阈值时，用外层包裹的方式改写：

```sql
SELECT * FROM (原语句) AS _guard_limited LIMIT 1000
```

用外层包裹而不是改写 AST 节点，原因是包裹对任意语句结构都成立，改写 AST 需要处理各种子句形态，出错面大得多。

### 2.7 R7 笛卡尔积

两类情况都要覆盖：

- 显式 JOIN 缺少 ON 或 USING，以及显式的 CROSS JOIN；
- 逗号分隔的多表 FROM 且没有 JOIN，此时要求 WHERE 中存在跨表的等值条件。

只检查第一类会漏掉第二种写法，而模型生成第二种写法的概率并不低。

### 2.8 R8 执行超时

超时不是校验规则，而是执行阶段的保护，放在这里是因为它与其余七条共同构成安全边界。

实现上用 SQLite 的进度回调：每执行一千条虚拟机指令回调一次，回调中判断是否超过截止时间或扫描行数上限，超过则返回非零值中断查询。

这样做的好处是不需要独立线程或信号，中断在驱动层完成，连接状态可控。

## 三、连接层加固

校验之外还有三层保护，任何一层单独失效时其余层仍然生效：

| 层 | 做法 |
|---|---|
| 打开方式 | 连接串使用 `file:...?mode=ro` |
| 会话参数 | 连接建立后执行 `PRAGMA query_only = ON` |
| 结果集 | 取 `max_rows + 1` 行判断是否超限，超限则截断并标记 |

三层叠加的原因是任何单一机制都可能有遗漏：只读模式挡不住某些特殊语句，参数可能被重置，行数上限依赖查询本身能快速返回。

---

## 四、校验顺序

守卫七条规则按固定顺序执行，R8 不在其中，它在执行阶段由仓储层触发：

```
R1 单条语句 → R2 仅 SELECT → R3 禁用关键字 → R4 表白名单
→ R5 字段白名单 → R7 笛卡尔积 → R6 强制 LIMIT
                                              ↓
                                    R8 执行超时（仓储层，执行期间）
```

顺序的依据是代价：越早拦截的代价越低。语句数量与类型这两条判断成本最低，放在最前面；字段校验要遍历整个 AST，放在中间。

**R7 必须排在 R6 之前。** R6 会把语句包裹成 `SELECT * FROM (原语句) AS _guard_limited LIMIT 1000`，改写后的语句在 FROM 里只剩一个派生表。若先做 R6 再做 R7，多表连接条件检查面对的是一个派生表，必然通过，笛卡尔积规则等于失效。

---

## 五、返回结果

校验结果包含八个字段：是否通过、改写后的语句、改写前的原始语句、错误列表、警告列表、涉及的表、涉及的字段、是否应用了 LIMIT。

前端展示改写后的语句，因为它才是实际执行的那条；改写前的原始语句保留用于回溯，能看到模型原本写了什么。人工核对口径时用原始语句，因为它与模型的输出一一对应。

错误与警告分开：错误导致拦截，警告只提示。当前实现中 R6 的自动改写属于警告，守卫其余六条的错误属于拦截。

## 六、测试要求

《实训7-AI共创-测试与准确率评测》要求守卫七条规则逐条有用例覆盖，每条至少两个用例：一个应被放行，一个应被拦截。R8 语句超时在仓储层的用例中单独覆盖，不混入守卫的用例矩阵。

断言要检查具体的规则编号，而不是只断言「抛异常」。只断言异常，规则改动后测试仍会通过，测试就失去了锁定行为的作用。

建议补充三类边界用例：CTE 形式的合法查询、派生表别名的合法查询、字符串字面量中包含分号的查询。这三类是最容易出现误拦的形态。

---

## 七、常见问题

**问题：合法查询被 R4 拦下，提示表未登记。**
原因：查询中用了 CTE 或派生表，其名称被当成了真实表。解决：在校验前收集 CTE 名与子查询别名，从表名校验中排除。

**问题：遍历 FROM 子句时报错，提示对象不可迭代。**
原因：不同版本的解析库中，FROM 子句的存储形态不同，早期版本返回列表，新版本返回单个节点。解决：先判断类型，再从节点上取表达式列表，不要假定它一定是列表。

**问题：多表查询没被 R7 拦下。**
原因：只检查了显式 JOIN，漏掉了逗号分隔的多表 FROM。解决：补上对第二种写法的检查。

**问题：长查询没有超时中断。**
原因：进度回调的间隔设置过大，或回调中返回值不生效。解决：缩小回调间隔，并确认回调返回非零值时查询确实被中断。
