# 实训 3 — AI 共创：开发任务文档编写

## 一、实训目标

1. 按依赖关系而不是模块顺序拆解开发任务，使每一步都有可独立验证的产出
2. 编写含任务清单、依赖关系、里程碑、交付标准、排期的开发任务文档
3. 识别关键路径与可并行的任务，能说明为什么三节点链路要尽早跑通
4. 用 AI 辅助生成任务拆解，并用「可独立验证」这条标准筛掉不合理的拆分

## 二、前置条件

| 项 | 要求 |
|---|---|---|
| 输入材料 | 《PRD-产品需求规格说明书.md》《UIUX-界面设计文档.md》 |
| 环境 | 无特殊要求 |
| 知识 | 了解 LangGraph 的节点与边的基本概念 |

## 三、知识点

| 知识点 | 说明 |
|---|---|
| 依赖排序 | 同一模块的工作可能被拆到不同阶段，按依赖而非按目录组织 |
| 可独立验证 | 每步做完能运行一次看到结果，不攒到最后联调 |
| 关键路径 | 决定最短工期的任务序列，本项目为数据层到前端主链路 |
| 里程碑出口 | 每个阶段结束时有一个可运行的检查点 |
| 风险前置 | 最早暴露最大不确定性，本项目是模型能否稳定产出可执行 SQL |

## 四、操作步骤

### 步骤 1：确定拆解原则

写三条原则：按依赖排序、每步可独立验证、最早暴露最大不确定性。每条配一句解释。

**预期输出**：三条原则及说明。

### 步骤 2：按阶段列任务

六个阶段：数据与语义层、数据访问层与安全沙箱、LLM 网关与最小链路、完整编排、接入层与前端、评测与交付。每个阶段一张任务表，列为编号、任务、依赖、产出、验收。

编号用 `T<阶段号>.<序号>`，例如 T1.1。依赖列填前置任务编号。

**预期输出**：六张表格，共二十五到三十条任务。

### 步骤 3：定义阶段出口

每个阶段写一句出口条件。出口条件必须是该阶段当下就能执行的动作：阶段一还没有接入层，出口应写成「命令行执行一致性校验返回一致，且规则召回能命中典型问题」，写成「`GET /api/semantic/health` 返回一致」则无法在阶段一验收，因为该接口属于阶段五。

**预期输出**：六条出口条件。

### 步骤 4：画依赖关系图

用 ASCII 箭头图表示任务之间的依赖，并标出关键路径。

**预期输出**：一张依赖图，一条关键路径标注。

### 步骤 5：定里程碑

六个里程碑 M1 到 M6，每个写清时点、交付内容与判定标准。

**预期输出**：六行表格。

### 步骤 6：写排期

按 14 学时安排。理论 6 学时对应六个主题并与实训对应，实践 8 学时对应阶段一到阶段五的任务范围，阶段六不单独占学时、穿插完成。

核对一件事：把各阶段标注的实践学时相加应等于 8，再把排期表逐行对照，确认每个任务都有学时承载。两张表对不上是这里最容易出现的错误。

**预期输出**：两张排期表，合计 8 个实践学时。

### 步骤 7：列风险与对策

五到六条风险，每条写影响、对策与责任任务。条数不必凑整，能识别出的风险都要列，但每条都要有对应的责任任务，否则对策落不到人头上。

**预期输出**：一张风险表。

## 五、AI 共创要点

**怎么问**：把已有的架构决策与目录结构一并给 AI，让它按依赖而非按目录拆解。只给一句「帮我拆解开发任务」，得到的通常是按模块罗列的清单，看不出先后顺序。

一个可用的提问结构：

```
已有架构：<模块化单体 / 六层职责边界 / 目录结构>
任务：把实现过程拆成任务，按依赖关系排序
要求：
1. 每一步都有可独立验证的产出
2. 标注依赖编号与关键路径
3. 指出哪些任务可以并行
4. 最大的不确定性是什么，如何在最早阶段暴露它
```

**常见偏差**：

| 偏差 | 表现 | 处理 |
|---|---|---|
| 按目录罗列 | 「先写完 backend 再写 frontend」 | 改成按依赖排序，前端初始化可提前 |
| 粒度过大 | 一条任务写「完成后端」 | 拆到能在两小时内完成并验证 |
| 缺失验证 | 只有产出没有验收 | 每条补一列验收方式 |
| 忽略不确定性 | 按部就班排到最后才联调 | 把最小链路提到阶段三 |
| 依赖画成串行 | 所有任务排成一条线 | 标出可并行项，例如三份 YAML 之间无依赖 |

**审查动作**：对每条任务问两个问题。第一，做完这一步能运行什么？答不上来说明拆解无效。第二，它的前置任务是不是真的必须？答「不一定」的说明可以并行。

## 八、常见问题

**问题：任务拆得太细，表格有一百多行。**
原因：把同一次编码动作按文件拆成了多条。解决：以「能否独立验证」为界，一次能跑通并看到结果的一组改动算一条。

**问题：依赖关系画成了树，看不出关键路径。**
原因：只画了父子关系。解决：在图上单独标注关键路径，并说明它决定最短工期。

**问题：排期与实践学时对不上。**
原因：任务数量与学时没有做映射。解决：先定学时，再把任务按阶段归入学时，任务过多的阶段考虑提前到理论课做设计部分。
