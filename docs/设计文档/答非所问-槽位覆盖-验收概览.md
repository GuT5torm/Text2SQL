## 二、为什么放在 agent/ 而不是 semantic/

原方案写的是 `semantic/slot_coverage.py`，实际落在 `app/agent/slot_coverage.py`。
原因是分层约束：`tests/test_layering.py` 禁止 semantic 引用 `app.agent`，而时间边界
必须复用 `consistency.extract_sql_time_range`——重写一份会让两处对同一件事给出不同
答案。这个模块比较的是「模型的理解」与「模型写出的语句」，与 `consistency.py` 同类，
同属编排侧的一致性核对。

## 三、核对的五类槽位

指标不在其中：指标对不对由口径签名（`semantic/expression_check.py`）负责，槽位里的
指标是中文显示名，拿它直接比 SQL 既与签名校验重复又更不准。

| 槽位 | 判定方式 |
| --- | --- |
| dimension | 维度叫法经语义层解析成 (表, 列)，再看它是否出现在 GROUP BY（或 SELECT 投影） |
| filter | 取值是否出现在 WHERE / HAVING 的条件里；字段可解析时要求落在同一条件 |
| time_range | 槽位说法换算成日期区间（复用 `resolve_time_term`），与 `extract_sql_time_range` 比对 |
| top_n | 语句里全部 LIMIT 取值（含守卫包裹后的内外两层）是否包含该条数 |
| order_by | 排序方向是否与槽位一致 |

时间只判「完全没有可识别的时间过滤」与「区间完全错开」两种情况。部分重叠不判——
区间是否完全落在召回区间内是 FR-D-5 的事（`check_time_range_consistency`），同一件事
不判两次。

## 四、不阻断执行（实测依据）

原方案写的是「第三道关卡」。实测后改成**只记录、不阻断**：跑 10 条真实问句，桩模式下
9 条报出时间缺口（桩实现的语句由语义层模板派生，不带时间谓词），另有两类会让**正确
语句**也报出缺失：

1. **按输出别名分组**：`GROUP BY 品类` 是 SQLite 常规写法，桩实现和模型都这么写。
   不解析别名会把「按品类分组」判成「没按品类分组」。已在 `_projection_aliases` 修掉。
2. **被过滤到单一取值的字段又要分组**：「华东区各品类」里区域既是过滤条件又是维度槽位，
   过滤到单值后再按它分组只会有唯一一组，不分组才是正常写法。已在 `_filtered_columns`
   修掉（逻辑成立：单值过滤 + 该字段分组恒等于单组）。

据此拦执行的后果是：几乎每条问句都要吃掉一次修正配额，修完还是同一条 SQL，最后走到
give_up——把一个本该正常给出的结果改成放弃。所以核对结果进 `state.slot_gaps`、进审计
detail、进前端提示条，不进 `_after_validate` 的判据。

修正路径上仍然用得上它：fix 节点重写语句时把缺口清单一起给模型（不额外花一次调用），
报错与缺口是两类问题——前者让语句跑不起来，后者让语句跑得起来却答非所问。

## 六、效果

```
问：上个月华东区各品类的成交总额
槽位：维度[品类, 区域] 过滤[区域=华东] 时间[上个月]
核对：filter  限定「区域」为 华东 → 语句的条件里没有这个取值
      time_range 统计区间为上个月（2026-08-01 起至 2026-08-31 止） → 语句里没有可识别的时间过滤条件
```

前端在答案卡上给出黄色提示条，列出每一处「可能没覆盖你问到的部分」。
