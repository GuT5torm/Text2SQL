# 答非所问：诊断记录与优化方案

日期：2026-09-29
范围：只做诊断与方案，未改动任何代码
基线：pytest 520 passed，`backend/.venv/Scripts/python.exe`，语义层 `app/semantic/loader.py`

## 一、诊断方法

直接调用语义层召回函数，绕过模型，观察问句到「指标 / 维度 / 表 / 时间区间」的映射结果。
这一步能定位的前段问题占答非所问的绝大多数——模型再准，也救不回召错了的口径与表结构。

```python
from app.semantic.loader import load_catalog, recall
cat = load_catalog()
hit = recall("上个月退了多少", cat)
print(hit.metric_displays(), [t["name"] for t in hit.tables])
```

共 24 条问法，覆盖四类：规范问法、未登记的业务口语、需要拒答的域外问题、需要归因的问题。

## 二、实测结果

当前登记：7 个指标（成交总额 / 销量 / 订单量 / 客单价 / 退款率 / 成交用户数 / 毛利）、
10 个维度、6 张表。

### 2.1 规范问法全部正确

| 问法 | 指标 | 维度 | 时间区间 |
| --- | --- | --- | --- |
| 上个月各区域的销售额 | 成交总额 | region | 2026-08-01 至 08-31 |
| 上月各品类的销量 | 销量 | category_name | 同上 |
| 近30天各渠道的订单量 | 订单量 | channel | 2026-08-31 至 09-29 |
| 今年各区域的客单价 | 客单价 | region | 2026-01-01 至 12-31 |
| 上季度各区域的退款率 | 退款率 | region | 2026-04-01 至 06-30 |
| 近半年各品类的毛利 | 毛利 | category_name | 2026-04-01 至 09-29 |

已登记说法的问法（如「营收」「卖了多少钱」「卖出去多少件货」）也能正确命中。
问题集中在下面三类。

### 2.2 误召回：召回了语义相近但错误的指标

| 问法 | 实际召回 | 应当召回 |
| --- | --- | --- |
| 上个月退了多少 | **销量 + 毛利** | 退款率 |

成因已定位在 `loader.py::_approx_score`。该函数在整句零精确命中时启用字符二元组
重叠兜底（阈值 0.6）。「退了多少」与登记说法「赚了多少」「卖了多少」在「了多少」上重叠，
于是把销量与毛利拉了进来，而真正的目标指标退款率反而没进来。
误召回的代价高于漏召回：漏召回至少还能被空命中逻辑感知，误召回会带着模型一路走到底，
生成一条能执行、有数据、图表正常的 SQL。

### 2.3 空命中：指标与表同时为空，随后照常放行生成

| 问法 | 召回指标 | 召回表 |
| --- | --- | --- |
| 上个月赚钱能力怎么样 | 无 | 无 |
| 上个月生意怎么样 | 无 | 无 |
| 近7天经营情况 | 无 | 无 |
| 上个月每件商品平均卖多少钱 | 无 | products |
| 上个月平均每单多少钱 | 无 | 无 |
| 各品牌上个月表现 | 无 | products |
| 会员等级成交分布 | 无 | users |

空命中时 `render_context` 只输出一句「本次未召回任何已登记指标」，表结构段落直接缺失，
generate 节点拿到的上下文里既没有指标口径也没有字段清单，只能按常识编列名。
`retrieve.py` 对这种情况的处理仅是记一行阶段文案「将按通用规则生成」，不拦截。

### 2.4 域外与归因问题被当成取数处理

route 的意图枚举只有 `query / chitchat / clarify`（`llm/schemas.py::RouteDecision`），
没有「库里没有这份数据」和「要的是原因不是数字」这两类。

| 问法 | 当前行为 | 正确行为 |
| --- | --- | --- |
| 帮我预测下个月销量 | 召回销量 + order_month，去查历史销量 | 说明不支持预测 |
| 为什么上个月销售额下降了 | 召回成交总额，返回一个数字 | 说明只能给数据，给出下钻建议 |
| 库存还有多少 | 全空命中，进 generate 硬生成 | 说明库内无库存数据 |
| 怎么写一个爬虫 | 全空命中，进 generate 硬生成 | 说明能力边界 |

## 三、根因

### 根因 A：问句被三处独立理解，互不通信

这是最根本的一条。

1. `route` 用模型抽出结构化槽位 `slots`（metrics / dimensions / filters / time_range / order_by / top_n）；
2. `retrieve` 完全不读 `slots`，用字面规则把同一个问句重新召回一遍；
3. `generate` 拿到规则召回的上下文，由模型再理解一次。

实测确认 `slots` 在整个后端只被写进返回值供前端展示与落库（`graph.py:366`、`api/chat.py:138`），
下游没有任何一个节点读取它——它是事实上的死字段。
三处理解任一处与另两处不一致即答非所问，而链路中没有任何一处做交叉比对。

### 根因 B：召回是纯字面子串匹配，缺乏语义泛化

`_normalize` 去标点后做子串包含判定，未登记的说法一律零信号；
兜底的 `_approx_score` 用字形相似度，字形相近恰好是业务上最容易混淆的两个指标的特征
（销量 / 毛利 / 退款率在同一批说法模板上只差一个字）。

### 根因 C：空命中与弱命中直接放行，没有拒答路径

`retrieve` 不区分「弱命中」与「完全空命中」，也没有把空命中标记为不可回答。
下游 `generate` 对空上下文的兜底语是「请按问题意图谨慎生成」，等于把约束放开。

### 根因 D：多指标命中时无主次，过滤与排序缺少强制

`MAX_METRICS = 3`，命中多个指标时平权进 prompt，由模型自选。
`slots` 里的 filters / order_by / top_n 没有下传给 generate，
问「华东」查出全国、问「前 5」返回全量，在当前链路上没有任何机制能拦。

### 根因 E：事后校验只覆盖「安全」与「口径」，不覆盖「是否对题」

`validate.py` 的两道关卡是 guard（表名列名是否登记）与 `expression_signature`（聚合是否退化）。
这两项都拦不住「SQL 完全合法但答的不是问的那件事」——语句里少了华东的过滤条件，
签名照样匹配，守卫照样放行。

### 根因 F：桩实现是第三套理解，掩盖真实表现

`gateway.py::_mock_json`（约 391–494 行）按关键词填 `slots`，`mock_sql.py` 从语义层派生 SQL 且不生成时间谓词。
桩模式下评测全绿只说明规则自洽，不能证明真实模型下的理解正确。
这也意味着：任何依赖 `slots` 的新机制，必须同步维护桩实现，否则会出现
「桩模式评测通过、真实模型下失效」的假绿。

## 四、优化方案

按改动面从小到大排四层。前两层不动图结构，也不新增节点，风险最低。

### 方案一：把 slots 下沉为下游约束（P0，收益最大）

**目标**：让整个链路只有一次权威理解，其余环节服从它。

改动点：

1. `app/semantic/loader.py::recall` 增加 `slots` 参数。
   `slots["metrics"]` 作为种子指标参与打分并强制进入 `hit.metrics` 前位，
   `slots["dimensions"]` 同理注入维度候选，`slots["filters"]` 注入取值提示。
   字面召回结果与之合并去重，不再二选一。
2. `app/agent/nodes/retrieve.py` 把 `state["slots"]` 传给 `recall`。
3. `app/agent/prompts/generate.md` 增加「问题结构」小节，把 slots 原文渲染进去，
   并写明「维度、过滤、排序、TopN 必须与之一致，不得自行增删」。
4. `retrieved` 增加 `slot_conflicts` 字段：slots 与字面召回不一致时记录具体差异，
   写进 stages 与前端标注，让分歧可观测而不是静默。

不新增模型调用，不改图结构。

### 方案二：收紧近似兜底，空命中分级拦截（P0）

1. **收紧 `_approx_score`**：近似兜底限定在声明了同一 `denominator` 的指标族内，
   阈值由 0.6 提到 0.75，并禁止「退款」类词与「赚 / 卖」类模板互相命中。
   直接修掉「上个月退了多少」这条误召回。
2. **补全口语词表**：`synonyms.yaml` 与 `metrics.yaml` 的 synonyms 增加
   「生意」「经营情况」「赚钱能力」「表现」「件均」「单均」「退货」等已实测为空白的说法。
   这一步是配置改动，不改代码。
3. **空命中分级**：`retrieve` 区分三档并写进 `retrieved`：
   - 有指标无表 → 用指标声明的 `tables` 补全；
   - 有维度无指标 → 用维度反查可用指标，仍为空则标记需澄清；
   - 指标与表全空 → `retrieved["unanswerable"] = True`，
     `route` 之后新增一次判断，走澄清或拒答，不再进 generate。

### 方案三：新增 out_of_scope 与 attribution 意图（P1）

1. `llm/schemas.py::RouteDecision.intent` 的 Literal 增加 `out_of_scope` 与 `attribution`。
2. `app/agent/prompts/route.md` 补判定标准：
   - `out_of_scope` —— 库内不存在该数据（库存、员工、预测、写码）；
   - `attribution` —— 问「为什么 / 什么原因 / 怎么提升」，要的是原因不是数字。
3. `graph.py` 增加两个终态节点（与 respond / clarify / give_up 同层，均为纯文案组装）：
   - `out_of_scope_node`：说明库内数据边界，给出可用问法示例（复用 `CHITCHAT_REPLY` 的问法清单）；
   - `attribution_node`：说明只能提供数据不支持归因，并给出可下钻的维度建议
     （可复用 `app/agent/drilldown.py` 的维度建议能力）。
4. `app/llm/gateway.py::_mock_json` 同步补两个意图的关键词判定，
   否则桩模式下新分支永远不会触发（见根因 F）。

### 方案四：结果侧槽位覆盖校验，把答非所问变成可检测（P1）

新增 `app/semantic/slot_coverage.py`，用已有的 sqlglot 对比 `slots` 与最终 SQL 的 AST：

| 校验项 | 判据 |
| --- | --- |
| 维度 | `slots.dimensions` 的表达式是否出现在 GROUP BY 或 SELECT 列 |
| 过滤 | `slots.filters` 的取值是否出现在 WHERE 字面量 |
| 时间 | SQL 日期边界是否与 `hit.time_range` 的 start / end 一致 |
| 排序 | ORDER BY 的字段与方向是否匹配 `slots.order_by` |
| TopN | LIMIT 是否体现 `slots.top_n` |

时间边界的提取可复用 `app/agent/consistency.py::extract_sql_time_range`，不重复实现。

`validate.py` 增加第三道关卡：覆盖不通过时进 `fix`，报错写明「缺少维度 X 的分组」
「未体现时间区间 Y」这类可直接执行的修正指令，而不是笼统的「校验未通过」。

### 方案五：评测补组，把本次诊断固化为回归项（P1）

`eval/cases.yaml` 当前有 recall / pipeline / safety / datalineage / baseline / drilldown /
robust / alert / multiturn / advanced 十组，缺两类：

- `outofscope`：预测、归因、库存、写代码各 3 条，断言 `status` 与意图；
- `slotcoverage`：维度 / 过滤 / 时间 / 排序 / TopN 每类各 3 条，断言 SQL 覆盖。

把本次诊断用的 24 条问法全部固化进去，其中 2.2 与 2.3 两张表作为必须转绿的失败用例。

## 五、分期建议

| 批次 | 内容 | 改动面 | 风险 |
| --- | --- | --- | --- |
| 第一批 | 方案一 + 方案二 | loader / retrieve / generate / 两份 YAML，不改图结构 | 低。无新节点、无新模型调用 |
| 第二批 | 方案三 + 方案四 | 新增意图枚举、两个终态节点、一个新校验模块 | 中。需同步桩实现，需回归 multiturn 组 |
| 第三批 | 方案五 | 评测用例 | 低 |

第一批做完就能修掉本次实测暴露的全部误召回与空命中问题。
第二批是把「答非所问」从不可检测变成可检测，也是答辩时能讲清楚的一层：
当前系统能证明 SQL 安全、口径不退化，但不能证明它回答了问题。

## 六、验证方式

1. 复跑本次 24 条问法的召回诊断，2.2 与 2.3 两张表应全部转绿；
2. 后端 pytest 全量，基线 520 passed 不得回退；
3. `eval` 新增两组用例由红转绿；
4. 前端手工验证：多轮追问（「那上个月呢」「按品类拆一下」）在 slots 参与约束后不再丢失上一轮维度。
