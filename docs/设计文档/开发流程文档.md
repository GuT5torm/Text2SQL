### 2.2 命令行约定

Windows 下 PowerShell 与 Git Bash 都能跑通本项目。为避开 PowerShell 中 `curl` 别名指向 `Invoke-WebRequest` 的问题，请求接口时统一写 `curl.exe`。

venv 激活在两种 shell 下命令不同（PowerShell 用 `.\.venv\Scripts\Activate.ps1`，Git Bash 用 `source .venv/Scripts/activate`），本文档一律使用 `.venv/Scripts/python.exe` 全路径调用，两种 shell 通用，也免去激活步骤。

后续所有命令的工作目录均为 `C:\Text2SQL\backend`，除前端部分。

### 2.3 依赖锁定（当前缺失，需补）

### 2.4 环境变量配置（当前缺失，需补）

`backend/.env` 与 `.env.example` 均不存在。`config.py` 读取 `backend/.env`（路径由 `BACKEND_DIR` 计算，与工作目录无关）。配置项按代码实测分五组：

```
# —— 应用 ——
APP_NAME=Text2SQL 电商数据分析 Agent
DEBUG=false
LOG_LEVEL=INFO
CORS_ORIGINS=http://localhost:5173,http://127.0.0.1:5173

# —— LLM 网关 ——
LLM_API_KEY=
LLM_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
LLM_MODEL=qwen-plus
LLM_FALLBACK_MODEL=
LLM_TIMEOUT=30.0
LLM_MAX_RETRIES=2
LLM_TEMPERATURE=0.0
LLM_MAX_TOKENS=2048
LLM_MOCK=true

# —— 存储 ——
BUSINESS_DB_PATH=data/ecommerce.db
APP_DB_PATH=data/app.db

# —— SQL 安全沙箱 ——
SQL_TIMEOUT_SECONDS=10.0
SQL_MAX_ROWS=1000
SQL_MAX_RETRY=3
SQL_SCAN_LIMIT=20000000

# —— 会话 ——
HISTORY_WINDOW=6
CHECKPOINTER=memory
```

几点说明：

1. `LLM_MOCK` 默认值为 `false`。未配置密钥时若保持 `false`，网关会因缺少 Key 而调用失败，整条链路跑不通。开发前期必须显式设为 `true`，此时 SQL 来自内置模板，链路可端到端验证。接入真实模型后置回 `false`。
2. `LLM_BASE_URL` 与 `LLM_MODEL` 的默认值取自 `config.py` 中阿里云百炼的 OpenAI 兼容入口。换服务商只改这两项与 Key，不改代码。
3. 模型名称、接口地址、计费方式以服务商最新文档为准。
4. `Settings` 的 `case_sensitive=False`，`.env` 中大小写均可，上面用大写仅为可读性。
5. 相对路径配置项（`BUSINESS_DB_PATH`）由 `config.py` 内 `BACKEND_DIR` 拼接，写相对路径即可。

`.env.example` 内容与上表一致，但 `LLM_API_KEY` 留空且不含任何真实密钥。

## 三、开发循环

每个阶段内部按同一套循环推进，避免"写完一大片再联调"：

```
改代码 → 跑对应单测 → 跑冒烟脚本 → 浏览器/curl 验证 → 提交 → 记 CHANGELOG
```

提交粒度按任务编号，一个任务一次提交，提交信息写任务编号与产出：

```
T2.4 实现 SQL 安全守卫七条规则
```

`CHANGELOG.md` 已在仓库根目录，每完成一个任务追加一行，记录改动与验证方式。这既是答辩时的过程材料，也是回溯"哪次改动导致准确率下降"的依据。

## 五、阶段一：数据与语义层（T1.1–T1.6）

### 5.1 做什么

`data/schema.sql` 与 `data/seed.py` 已存在，`semantic/` 下的三份 YAML 与 `loader.py` 已存在。本阶段的工作是核对而非从零编写：确认 YAML 中的表字段与库内实际一致，确认召回能命中典型问法。

### 5.2 操作步骤

```bash
cd /c/Text2SQL/backend

# 造数（库已存在则覆盖重建；加 --keep 则跳过）
./.venv/Scripts/python.exe data/seed.py
```

造数脚本固定随机种子（代码内 `SEED = 20260914`），生成 2000 用户、500 商品、12000 订单，时间范围 2025-01-01 至造数当日，保证相对时间问法能命中数据。

核对语义层与库的一致性，这一步依赖服务启动：

```bash
./.venv/Scripts/python.exe -m uvicorn app.main:app --reload --port 8000
```

另开一个终端：

```bash
curl.exe http://127.0.0.1:8000/api/semantic/health
```

返回中 `consistent` 为 `true` 表示语义层登记的表与业务库实际表名一致。`missing_in_semantic` 与 `missing_in_db` 两个字段直接指出差异所在：前者是库里有、YAML 没登记的表，后者是 YAML 登记了、库里不存在的表。任何一个非空都要回到 `tables.yaml` 修正。

召回调试：

```bash
curl.exe "http://127.0.0.1:8000/api/semantic/recall?q=上个季度华东区各品类的成交总额&with_context=false"
```

检查返回的指标与表是否覆盖问题中的「成交总额」「华东」「品类」。漏召回时先补 `synonyms.yaml` 的同义词，再考虑改召回逻辑——按 ADR-006，演示阶段不上向量检索。

### 5.3 出口标准

- `seed.py` 重复执行生成的库一致（可校验文件大小与关键表行数）
- `/api/semantic/health` 返回 `consistent: true`
- 至少三个典型问法的召回结果命中正确指标

### 5.4 常见故障

| 现象 | 原因 | 处理 |
|---|---|---|
| 启动报 `FileNotFoundError` | 业务库未生成 | 先跑 `data/seed.py`。`main.py` 的 lifespan 会直接打印这条修复提示 |
| 启动报 `SemanticError` | 语义层校验未过 | 进程拒绝启动，错误清单含具体字段与表，逐条修 YAML |
| 召回结果为空 | 问法未命中同义词 | 补 `synonyms.yaml`，注意业务黑话与枚举值口语表达 |

## 六、阶段二：数据访问层与安全沙箱（T2.1–T2.4）

### 6.1 做什么

`db/` 下五个文件均已存在。本阶段的核心产出是守卫的单元测试——`tests/` 目录目前只有 `smoke.py`，`test_guard.py` 待建。

### 6.2 守卫规则与用例分工

守卫实现 R1–R7 共七条规则。R8（执行超时中断）由 `sqlite_repo.py` 的 progress handler 实现，属于仓储层职责，不计入守卫规则数，测试用例也分属两个文件：

| 规则 | 含义 | 实现位置 | 用例归属 |
|---|---|---|---|
| R1 | 只允许单条语句 | guard.py | test_guard.py |
| R2 | 只允许查询类语句（SELECT / UNION / EXCEPT / INTERSECT） | guard.py | test_guard.py |
| R3 | 语句树中不得出现 DDL / DML / 管理类关键字 | guard.py | test_guard.py |
| R4 | 表必须在语义层登记 | guard.py | test_guard.py |
| R5 | 字段必须存在于其所属表的元数据中 | guard.py | test_guard.py |
| R6 | 无 LIMIT 或 LIMIT 超限时自动包裹 | guard.py | test_guard.py |
| R7 | 多表查询必须带连接条件 | guard.py | test_guard.py |
| — | R8 执行超时中断 | `sqlite_repo.py` 用 progress handler | test_repository.py |

R6 是唯一一条自动改写规则，其余为拦截。执行顺序上 R7 先于 R6。用例要为每条规则准备一正一反两个输入：一条合法 SQL 应当放行，一条违规 SQL 应当被拦下并给出可识别的规则编号。

### 6.3 操作步骤

新建 `tests/test_guard.py`，按规则编号组织用例函数（如 `test_r1_single_statement`）。跑测试：

```bash
./.venv/Scripts/python.exe -m pytest tests -q
```

注意 pytest 只收集 `test_*.py`，`smoke.py` 不会被收集，冒烟单独跑。

超时规则单独验证：构造一条扫描行数超过 `SQL_SCAN_LIMIT`（默认 20,000,000）的查询，确认被 progress handler 中断而非挂起。`SQL_TIMEOUT_SECONDS`（默认 10 秒）是第二道保险。

### 6.4 分层约束自查

本阶段结束后执行一次结构检查，确认没有跨越分层边界：

```bash
grep -rn "import sqlite3\|create_engine" app/agent/ ; grep -rn "openai\|gateway" app/semantic/
```

两条命令都应当无输出。第一条命中说明编排层直接碰了数据库，第二条命中说明语义层引入了 LLM。这是《项目结构与交付规范》8.5 的三条硬约束中的两条，第三条（密钥只出现在 `.env`）用下面的命令检查：

```bash
grep -rn "sk-\|api_key\s*=\s*[\"'][^\"']" app/
```

### 6.5 出口标准

- `test_guard.py` 覆盖 R1–R7，每条规则有正例与反例
- R8 在 `test_repository.py` 中有独立用例
- 上述三条分层检查命令无输出

## 七、阶段三：LLM 网关与最小链路（T3.1–T3.3）

### 7.1 做什么

`llm/gateway.py` 与 `llm/schemas.py` 已存在，八个业务节点与三个终态节点的图已在 `agent/graph.py` 中装配完成。本阶段要验证的是整条链路在桩模式下能跑通，以及在真实模型下的稳定性。

### 7.2 桩模式验证

确认 `.env` 中 `LLM_MOCK=true`，然后：

```bash
curl.exe http://127.0.0.1:8000/api/health
```

返回中的 `llm_mock` 为 `true` 表示当前走模板 SQL，`model` 显示配置的模型名，`metrics` 与 `tables` 显示语义层加载的指标数与表数。

跑端到端冒烟：

```bash
./.venv/Scripts/python.exe tests/smoke.py
```

脚本依次检查 `/api/health`、`/api/semantic/health`、召回接口，建会话后依次提问「上个月各区域的成交总额」「各品类的退款率」「最近三个月的下单渠道分布」，打印每轮的 status、sql、columns、row_count、answer 摘要、chart 类型与 stages 数量。全部通过时末尾输出「全部通过」，退出码 0；有失败时逐条 `FAIL:` 打印并返回 1。

冒烟脚本用 `TestClient` 直接调用 ASGI 应用，不需要先启动服务。

### 7.3 接入真实模型

1. 按附录 A 申请密钥，写入 `.env` 的 `LLM_API_KEY`
2. 将 `LLM_MOCK` 改为 `false`
3. 重启服务，`/api/health` 中 `llm_mock` 应为 `false`
4. 重跑冒烟脚本，观察真实生成的 SQL 能否通过守卫并执行成功

此时最容易暴露的问题是模型输出格式不符（多余的解释文本、Markdown 代码围栏）。`generate` 节点需要模型只输出 SQL 文本，出现围栏时应在节点内做剥离，而不是降低守卫标准放行。

用量统计：`/api/stats` 返回本进程的 token 与耗时汇总，用于判断单次问答的消耗，也是答辩时的实测数据。

### 7.4 出口标准

- 桩模式下冒烟脚本退出码 0
- 真实模型下至少有一条提问能完整走完「生成 → 校验 → 执行 → 出图 → 结论」
- `/api/health` 中 `llm_mock` 与实际配置一致

## 八、阶段四：完整编排（T4.1–T4.6）

### 8.1 图结构（实测）

`agent/graph.py` 注册十一个节点：八个业务节点 `route`、`retrieve`、`generate`、`validate`、`execute`、`fix`、`visualize`、`summarize`，三个终态节点 `respond`、`clarify`、`give_up`。

条件路由：`route` 之后按意图分流；`validate` 之后按校验结果分流；`execute` 失败与 `validate` 失败共用重试配额；`fix → validate` 构成回环；`visualize → summarize → END` 为正常出口。

### 8.2 需要重点验证的三件事

**第一，重试回环能触发且能收敛。** 构造一条必然失败的 SQL（引用语义层未登记的字段），观察流程是否进入 `fix`，`sql_max_retry`（默认 3）次后进入 `give_up` 并返回可读说明，而不是无限循环。

**第二，反问分支可用。** 输入信息不足的问题（如「卖得怎么样」），应进入 `clarify` 而非猜测后给出错误结果。

**第三，多轮追问能继承上文。** 先问「上个月各区域的成交总额」，再问「那华东呢」，第二轮应当继承上轮的指标口径与时间范围。`history_window`（默认 6）控制回灌的历史轮数。

### 8.3 Prompt 外置

五个 Prompt 位于 `agent/prompts/`：`route.md`、`generate.md`、`fix.md`、`visualize.md`、`summarize.md`。调 Prompt 不改代码，改完重跑冒烟脚本即可。

调整 Prompt 前先建评测集（见第十一章）。没有评测集时改 Prompt 属于盲改，无法判断改动是提升还是劣化。

### 8.4 已知缺陷

`stages` 字段跨轮累积：状态归约使用 `operator.add`，Checkpointer 保存上一轮内容，导致第二轮显示 14 个阶段、第三轮 21 个。`stages` 的作用域应为单轮。修复方向是逐节点更新采集而非从终态整体取，前端发起新一轮时先清空。代码尚未修改，前端联调时会遇到这个现象。

### 8.5 出口标准

- 命令行或冒烟脚本可完成一次含多轮追问的完整问答
- 构造的失败场景能触发重试并在配额耗尽后兜底
- 反问类问题进入 `clarify` 分支

### 9.2 SSE 联调要点

```bash
curl.exe -N -X POST http://127.0.0.1:8000/api/chat ^
  -H "Content-Type: application/json" ^
  -d "{\"session_id\":\"<id>\",\"question\":\"上个月各区域的成交总额\"}"
```

Git Bash 下把行尾的 `^` 换成 `\`。`-N` 关闭缓冲，事件应逐条推送而非最后一次性吐出。事件类型四类：`stage`、`result`、`error`、`done`。

若通过 Nginx 访问时事件一次性到达，是 Nginx 缓冲所致，需在 location 中关闭缓冲并延长超时，见附录 C。

## 十二、故障排查表

| 现象 | 原因 | 处理 |
|---|---|---|
| 启动时 `FileNotFoundError` | 业务库未生成 | 跑 `data/seed.py` |
| 启动时 `SemanticError`，进程退出 | 语义层与库不一致 | 按错误清单修 YAML，改完重启 |
| `/api/health` 中 `llm_mock` 为 `false` 但无密钥 | `LLM_MOCK` 未显式置为 `true` | `.env` 设 `LLM_MOCK=true` |
| 接口返回大量 `R5` 字段错误 | 模型编造字段 | 属正常拦截，观察 `fix` 节点能否据报错修正 |
| 查询长时间无响应 | 大表扫描 | `SQL_SCAN_LIMIT` 与 `SQL_TIMEOUT_SECONDS` 双重兜底，检查是否生效 |
| SSE 事件一次性到达 | 服务端或 Nginx 缓冲 | curl 加 `-N`；Nginx 关缓冲 |
| 图表空白 | ECharts option 引用了不存在的字段 | 前端渲染前校验字段，退回表格展示 |
| 第二轮阶段指示变多（14、21…） | `stages` 跨轮累积，已知缺陷 | 见 8.4 |
| `pytest` 收集 0 项 | 测试文件未以 `test_` 开头 | 重命名；冒烟脚本单独跑 |
| PowerShell 中 `curl` 输出异常 | `curl` 是 `Invoke-WebRequest` 别名 | 用 `curl.exe` |
| 中文输出乱码 | Windows 控制台编码 | 命令前加 `PYTHONUTF8=1`（Git Bash）；PowerShell 用 `$env:PYTHONUTF8=1` |
