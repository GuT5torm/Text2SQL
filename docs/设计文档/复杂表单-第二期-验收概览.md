## 3. 关键落点

### 3.1 取值体系只有语义层一个来源

前端不写死任何取值。`GET /api/semantic/filters` 把 `filters.yaml` 的字段连同 `tables.yaml` 的 enum 取值一起下发，界面上的每一个选项都能在语义层里找到出处。日期类字段 `values` 为空，前端按 `values_from` 改渲染日期选择器。

### 3.2 三级联动与置灰

| 层级 | 联动 | 置灰原因 |
|---|---|---|
| 指标 → 维度 | 维度选项取语义层全部维度，指标不支持的置灰 | 「指标『订单量』不支持按此维度分组」 |
| 指标 → 条件区 | 未选指标时禁用条件行与「添加条件」 | 「先选指标再添加条件」 |
| 字段 → 算子 | 算子下拉随字段的 `ops` 收窄 | — |
| 算子 → 取值 | `eq` 单选、`in` 多选；日期字段 `between` 用区间选择器、`gte`/`lte` 用单日选择器 | — |
| 互斥字段 | `orders.status` 与 `refunds.reason` 互相置灰 | 「与已选条件『退款原因』互斥，同时使用结果恒为空集」 |
| 顶部区间 ↔ 时间条件 | 已选顶部区间时，条件行里的下单时间置灰 | 「已选顶部时间区间，同一字段不可重复设置」 |

置灰而不是隐藏：只列该指标支持的维度会让用户以为其它维度不存在；置灰并给原因才能解释「为什么不能选」。这与 AlertCenter 里 deviation 模式禁用维度的处理一致。

换字段或换算子时清空取值——旧取值对新字段几乎没有意义，留着只会让人以为已经设好了。

### 3.3 提交前回显走后端，不在前端抄一份

点「执行查询」先调 `/api/query/form/preview`，把后端渲染的问句与谓词清单放进确认弹窗，确认后才执行；另有独立的「预演」按钮只回显不执行。

渲染规则（`render_predicate` / `render_form_question`）只有后端一份。前端照抄一遍必然漂移，而且漂移后的回显会骗人——用户看到的谓词不是实际下发的内容。

### 3.4 同字段查重

同一字段出现多次按「且」处理，`region = 华东 AND region = 华南` 恒为空集、`created_at >= A AND created_at >= B` 只留更严的那个，两种都不报错。因此提交期直接拒绝：普通字段提示改用 `in`，时间字段提示顶部区间与条件行二选一。顶部时间区间会被解析成同一个 `created_at` 条件，故一并参与查重。

## 4. 实跑结果

以下取自 2026-10-19 本机实跑（桩模式），非构造数据。

### 4.1 `/api/semantic/filters`

```
orders.region     ops=['eq','in']  values_from=enum  取值 7 个
orders.channel    ops=['eq','in']  values_from=enum  取值 4 个
orders.status     ops=['eq','in']  values_from=enum  取值 6 个  exclude_with=['refunds.reason']
orders.created_at ops=['between','gte','lte']  values_from=date  取值 0 个
users.level       ops=['eq','in']  values_from=enum  取值 4 个  join=users.id = orders.user_id
refunds.reason    ops=['eq','in']  values_from=enum  取值 4 个  exclude_with=['orders.status']
```

### 4.2 `/api/query/form/preview`

请求与方案 §5.9 的走查用例一致（gmv + 按品类分组 + 大区 IN（华东、华南）+ 渠道 = app + 时间 2026-01-01 至 2026-07-01 + TopN 10）：

```
question: 2026-01-01 至 2026-07-01，销售大区属于华东、华南，下单渠道为App的成交总额，按商品类目分组，取前 10
predicates:
  orders.region IN ('华东', '华南')
  orders.channel = 'app'
  orders.created_at >= '2026-01-01' AND orders.created_at < '2026-07-01'
descriptions:
  销售大区属于华东、华南
  下单渠道为App
  下单时间从 2026-01-01 到 2026-07-01
```

### 4.3 提交期拒绝（四条实跑）

| 场景 | 错误信息 |
|---|---|
| 互斥：订单状态 + 退款原因 | 条件「订单状态」与「退款原因」不能同时使用：两者在业务上不同时成立，组合后结果恒为空集 |
| 同字段重复：region 两行 | 条件「销售大区」出现了 2 次：多个取值请用算子 in，不要加 2 行 |
| 顶部区间 + 时间条件行 | 条件「下单时间」出现了 2 次：顶部的时间区间与条件行里的下单时间二选一即可 |
| 未登记字段（预演同样拒） | 第 1 个条件的字段「orders.coupon_id」未登记为可用条件，可用字段：…… |

### 4.4 加载期校验

`exclude_with` 指向未登记字段、只在一侧声明，均在 `load_catalog` 阶段抛 `SemanticError`（用例覆盖）。

1. **条件是否落进 SQL 仍无判据**。本期把条件完整送到了 generate 节点并在界面上回显谓词，但桩 SQL 不带过滤条件，结果区会用「条件覆盖核对」提示缺口。真正的判据是第三期的 `check_form_conditions` 强断言，且需在真实模型下复验。
2. **结果区复用了 `ResultTable` 与折叠 SQL**，没有接入图表（ChartPanel）。表单查询结果要不要出图取决于演示需要，暂按表格 + 结论处理。
3. **前端未做空结果与 fix 回灌的条件清单展示**（方案 §5.7）：目前只在结果区列出槽位覆盖缺口，没有把「本轮全部条件」回灌进结论文案。
4. **互斥规则只登记了一对**（订单状态 / 退款原因）。`refunds.reason` 与成交类指标组合会得到空集，这条目前只在 `note` 里提示、渲染进 prompt，没有升级为提交期拒绝——它依赖指标而非字段组合，需要另一类规则才能表达。
5. **真实模型仍 401**，第四期阻塞状态不变。
