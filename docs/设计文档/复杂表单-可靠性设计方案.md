> 版本：v1.1（在 v1.0 基础上完善：槽位结构与兼容要求、SQL 片段级失败样例、端到端走查、影响面与测试计划、回滚策略）
> 日期：2026-10-16
> 状态：方案阶段，未动代码。本文所有现状判断均附代码位置，可逐条核对。
> 关联：FR-A-5（槽位结构化）、FR-O-1（订阅规则表单）、FR-L-2（下钻）、FR-D-5（时间一致性）、R1–R9（守卫）、T46.1（时间锚点）

---

## 1. 问题定义

复杂查询表单指条件数量多、结构动态、带组合逻辑的查询条件录入界面：用户在下拉与输入框里选定指标、分组维度、若干过滤条件、时间区间、排序与条数，提交后系统产出可执行 SQL 并给出结果与结论。

本方案关注的可靠性包含三层，缺一不可：

| 层 | 含义 | 失效后果 |
|---|---|---|
| 条件保真 | 表单里每一个条件都落进 SQL，算子与取值不失真 | 查询答的不是用户问的事，且全程无报错 |
| 边界受控 | 安全与口径仍由既有机制把守，表单复杂度不削弱它们 | 复杂条件绕过守卫或写歪口径 |
| 失败可归因 | 失败时能说清是守卫拦的、口径不符、条件缺口还是生成问题 | 用户与开发者都无法定位，只能猜 |

表单查询与自由提问的本质区别：**表单条件是确定的，模型只负责"怎么写"，不负责"问的是什么"**。这一条决定了本方案的全部设计取向——确定的东西不交给模型猜，猜的部分用校验把住。

## 2. 现状盘点

### 2.1 已有的三处表单

| 表单 | 位置 | 复杂度 |
|---|---|---|
| 订阅规则 | `frontend/src/pages/AlertCenter.tsx` | 字段联动（`Form.useWatch` 下 deviation 模式禁用维度）、动态标签、提交前归一化 |
| 连接数据库 | `frontend/src/components/DataSourceModal.tsx` | dialect 条件渲染、多步状态（测试→预览→应用） |
| 运行时设置 | `frontend/src/components/SettingsModal.tsx` | 敏感字段不回填、按需打 patch |

三处均为单层字段，无动态行、无嵌套、无组合逻辑。antd Form v5 与 pydantic v2 的组合原生支持 `Form.List`、嵌套 `name`、跨字段校验，引入属于工作量，不是能力缺口。

### 2.2 已存在、可直接复用的机制

| 机制 | 位置 | 对表单查询的作用 |
|---|---|---|
| 六类槽位 `metrics / dimensions / filters / time_range / order_by / top_n` | `app/agent/state.py`、`app/llm/schemas.py::RouteDecision` | 表单字段与槽位几乎一一对应，不需要另造模型 |
| 指标口径登记（expression、required_filters、dimensions、examples、expression_signature） | `app/semantic/metrics.yaml` | 指标下拉、口径标注、签名断言的唯一来源 |
| 字段白名单与枚举 | `app/semantic/tables.yaml` | 守卫 R4/R5 的校验依据；枚举值即表单取值来源 |
| 取值同义词 | `app/semantic/synonyms.yaml::value_synonyms` | 口语取值到库内标准值与字段的映射 |
| 相对时间词 | `app/semantic/synonyms.yaml::time_terms` | 时间边界计算集中在语义层，模型不算日期 |
| SQL 守卫 R1–R9 | `app/db/guard.py` | 未登记表/字段、危险语句、超限 LIMIT、笛卡尔连接、超时、函数白名单 |
| 口径签名断言 | `app/semantic/expression_check.py`，validate 与 eval 共用 | 聚合表达式写歪即报，与表单复杂度无关 |
| 槽位覆盖核对 | `app/agent/slot_coverage.py` | 比对槽位与 SQL AST，当前只记录不阻断 |
| 结构化转问句先例 | `app/agent/drilldown.py`、`app/agent/alert_eval.py::build_question` | 证明"结构化字段→查询"路径已跑通两次 |
| 时间锚点 | `QueryRepository.data_as_of`（T46.1） | 时间词一律按库内数据截止日换算 |

### 2.3 入口现状

`POST /api/chat`（`app/api/chat.py`）只收 `question`（≤500 字）与 `session_id`。链路为 route（意图 + LLM 抽槽位）→ retrieve（语义召回，无 LLM）→ generate（LLM 写 SQL）→ validate（守卫 + 签名 + 槽位核对）→ execute → enrich/summarize/visualize。槽位由 route 从问句抽出后，只被槽位覆盖核对与前端标注消费，retrieve 与 generate 均只读问句文本。

### 2.4 槽位的具体结构与表单直填的兼容要求

`state.slots` 的键与取值形态（`RouteDecision.slots` 的说明与 `gateway._mock_route_decision` 的填充实例）：

```python
{
  "metrics": ["成交总额"],                          # 指标显示名
  "dimensions": ["品类"],                           # 维度显示名
  "filters": [{"field": "区域", "value": "华东"}],   # field 用显示名；
                                                    # 数值型为 {"field","op",">","value"}
  "time_range": "上个月",                           # 时间词标签，不是日期
  "order_by": {"field": "成交总额", "direction": "desc"},
  "top_n": 10
}
```

表单路径直填 slots 时必须遵守三条兼容约定，否则既有消费方（`slot_coverage._dimension_index`、前端标注）认不出：

1. `filters[].field` 与 `dimensions[]` 用显示名或配置名，两者 `_dimension_index` 都收录（display / name / synonyms 全收），与 `drilldown._dimension_name` 的归一化一致；
2. `time_range` 只作展示标签（如"2026 年上半年"）。表单提交的确定区间不走 `_time_gaps` 的相对词换算，而是作为普通条件（`orders.created_at` 的 between）进强断言，避免给 `_time_gaps` 增加第二条输入形态；
3. 多值条件（IN）在 slots 里只存主值，全部取值以 §5.1 新增的 `form_conditions` 为准。slots 继续服务标注与既有核对，不断言。

## 3. 失效模式清单

### 3.1 九类失效与防线归属

复杂表单下的九类失效。F1–F4 是本方案要新设防线的，F5–F9 是既有防线在复杂条件下会被加压的。

| 编号 | 失效模式 | 成因 | 现有检测 | 防线归属 |
|---|---|---|---|---|
| F1 | 条件丢失：表单条件没进 SQL | 条件只存在于问句里，模型转述时漏项 | 槽位覆盖核对能查，但只记录不阻断（`validate.py` 注释说明原因：过滤字段同时被要求分组时会产生假告警） | 新设：表单条件强断言（§5.4） |
| F2 | 布尔组合失真：OR / 嵌套经自然语言转述后丢结构 | 路线 A（表单拼问句）的固有缺陷，`(A OR B) AND C` 拼不成一句完整的话 | 无 | 新设：结构化入口（§5.1） |
| F3 | 区间与多值写法错误：between 边界错位、IN 漏值 | 模型自选写法，左右边界与闭开区间无约束 | 无 | 新设：算子白名单 + 谓词清单（§5.2、§5.3） |
| F4 | 跨表 JOIN 遗漏 | city / user_level 在 users 表，漏 JOIN 后语句照样执行（`metrics.yaml` order_count 注释已记录此坑） | 无专用检测 | 新设：条件字段携带所属表信息（§5.2） |
| F5 | 口径退化 | 聚合表达式写歪，如问毛利只算成交额；条件叠加时更容易发生 | 口径签名断言，已阻断 | 既有防线，回归覆盖 |
| F6 | 多维度同时分组顺序混乱、结果行数爆炸 | 模型自行决定 GROUP BY 顺序 | 无 | 约束：维度取自 `metric.dimensions`，组合规则登记在语义层（§5.2） |
| F7 | 时间错位 | 滚动窗口整体落到数据截止日之后返回空集（T46 实测坑）；表单若传相对词仍依赖换算 | 时间一致性核对（FR-D-5） | 约束：表单直接给确定区间（§5.5） |
| F8 | 未登记条件 | 表单给出的字段或取值语义层没有，守卫拦截或模型编造 | 守卫 R4/R5 拦截编造，但拦截即失败，用户体验差 | 新设：条件白名单制，提交前挡（§5.2） |
| F9 | 空结果不可解释 | 多条件叠加后 0 行，用户分不清是没数据还是条件错了 | 空结果回灌（`empty_retry`、fix 节点 `confirm_no_data`） | 既有机制，回灌提示带条件清单（§5.7） |

另有一条贯穿性风险，不属于表单本身但直接影响验收：**桩模式会掩盖 F1 与 F2**。mock SQL 从语义层模板派生，不带时间谓词、不带区域过滤，缺条件的问句照样出语句还算得出基准。当前 pytest 548 通过、eval 12 组 109 条通过，全部是在 `LLM_MOCK=true` 下取得；真实模型 key 自 T46 起 401 阻塞，真实链路未完整回归。因此本方案所有验收数字必须分桩模式与真实模型两组出，不合成一组（§6.3）。

### 3.2 失败样例（SQL 片段级）

以下样例供评审对照，每条给出"长什么样"，而不只是"为什么会发生"。

**F1 条件丢失**。表单条件：渠道为 app。生成：

```sql
-- 缺 AND o.channel = 'app'
SELECT c.name AS 品类, ROUND(SUM(oi.quantity * oi.unit_price), 2) AS 成交总额
FROM orders o JOIN order_items oi ON oi.order_id = o.id
WHERE o.status NOT IN ('cancelled', 'pending')
GROUP BY c.name
```

语句可执行、有数、图正常，唯一异常是数字比预期大。这是全部九类里最难被发现的一种。

**F2 布尔组合失真**。表单条件：大区属于华东或华南，且渠道为 app。拼成问句"华东或华南的 app 渠道成交总额"后，模型可能写成 `region IN ('华东','华南') AND channel='app'`（碰巧对），也可能写成 `region='华东' OR (region='华南' AND channel='app')`（错，华南丢了渠道条件）。问句无法承载分组语义，对错全看模型一次发挥。

**F3 区间边界**。表单条件：2026-01-01 至 2026-07-01（左闭右开）。模型写成 `created_at <= '2026-07-01'`，7 月 1 日当天数据被算入，无任何报错；或写成 `created_at > '2026-01-01'`，1 月 1 日被漏掉。

**F4 跨表 JOIN 遗漏**。表单条件：会员等级为 gold。生成语句漏 `JOIN users ON users.id = orders.user_id`。这一条 SQLite 会报 `no such column: users.level`，属于幸运的一类；若字段名在本库其他表中巧合存在，则静默出错。`filters.yaml` 的 `join` 字段与强断言共同防它（§5.2、§5.4）。

**F5 口径退化**。问毛利，条件叠加后写成 `SUM(oi.quantity * oi.unit_price)`。口径签名断言拦截（既有防线，`require_all: ["cost_price"]`）。

**F6 多维度分组**。`GROUP BY o.region, c.name` 与 `GROUP BY c.name, o.region` 结果集相同、行序不同，前端图表系列与图例错乱。表单通过约束维度取自 `metric.dimensions` 并登记顺序来防。

**F7 时间错位**。数据截止 2026-10-14，表单快捷选项"近 7 天"若按系统日期换算成 10-09 至 10-16，区间整体落到数据之后，返回空集而不是"没有数据"的明确提示。T46.1 已把锚点接到 `data_as_of`，表单侧直接给确定区间可绕开整类问题。

**F8 未登记条件**。表单传 `orders.coupon_id`（语义层没有）。守卫 R5 拦截，用户看到的是 `R5 ...` 错误码，而不是"这个字段没有登记，不能按它查"。

**F9 空结果不可解释**。三个条件叠加后 0 行，结论只说"没有数据"。用户无法判断该放宽哪个条件，多试两次后放弃。

## 4. 设计原则

| 编号 | 原则 | 说明 |
|---|---|---|
| P1 | 表单即槽位，不绕自然语言 | 结构化条件直填 `state.slots`，route 对表单输入跳过 LLM 抽取。确定的条件不交给模型猜 |
| P2 | 条件白名单制 | 表单只能产出语义层已登记的字段、算子与取值，从源头消灭编造，与守卫 R4/R5 同向 |
| P3 | 双层校验 | 表单侧 pydantic 结构校验（字段、算子、取值、闭开区间），链路侧守卫 + 口径签名 + 条件断言 |
| P4 | 确定条件强断言 | 表单槽位是确定的，其覆盖核对从"启发式记录"升级为"必须命中、可阻断"，与自由提问的"只记录"区分 |
| P5 | 提交前回显 | 条件到 SQL 谓词的映射对人可见后再执行，把可解释性放在执行前而不是失败后 |
| P6 | 失败四归因 | guard / signature / slot / generate 四类，评测与前端按同一套编码分流（守卫 notice 已带 R 编号，可直接沿用） |
| P7 | 验证分两组 | 桩模式与真实模型数字分开标注，任何一组不单独作为验收依据 |

## 5. 方案设计

### 5.1 结构化入口

新增查询请求模型，与 `ChatRequest` 并行而非替换：

```python
class FormCondition(BaseModel):
    field: str                        # filters.yaml 登记的字段，如 orders.region / orders.created_at
    op: Literal["eq", "in", "between", "gte", "lte"]
    value: str | list[str] | None = None
    value_to: str | None = None       # between 上界，左闭右开

class FormQueryRequest(BaseModel):
    session_id: str
    metric: str                       # 必填，语义层已登记指标
    dimensions: list[str] = []        # 分组维度，取自该指标的 dimensions
    conditions: list[FormCondition] = []
    time_range: dict[str, str] | None = None   # {"start": "2026-01-01", "end": "2026-07-01"}
    order_by: dict[str, str] | None = None     # {"field": "...", "direction": "asc"|"desc"}
    top_n: int | None = None
```

算子白名单先收这五个。`like` 等模糊算子不放初期白名单：文本模糊匹配的语义边界宽，出问题难以归因。

**state 新增两个字段**（`app/agent/state.py`）：

```python
query_source: Literal["chat", "form"]          # 缺省按 chat 行为
form_conditions: list[dict[str, Any]]          # 校验通过的条件原文，强断言的数据源
```

必须显式声明：LangGraph 只归约 `AgentState` TypedDict 里声明过的键，未声明字段会被静默丢弃（项目已踩过，`state.py` 注释有记录）。`query_source` 缺省不写时按 `chat` 走，行为与现在完全一致，这是回滚策略的一部分（§8.4）。

**route 节点分支**（`app/agent/nodes/route.py`）：

```python
def route_node(state, *, gateway, history_window=6):
    if state.get("query_source") == "form":
        # 表单路径：不调模型，槽位直填，确定性信息不猜
        return {
            "intent": "query",
            "intent_reason": "结构化表单查询，槽位由表单直填",
            "slots": build_slots_from_form(state),
            "question": render_form_question(state),   # 供落库与回看的可读问句
            "rewritten_question": render_form_question(state),
            "stages": [new_stage(NODE, "理解问题", "表单条件直填，未调用模型", _ms(started))],
        }
    # ……现有 LLM 路径不变
```

`build_slots_from_form` 按 §2.4 的三条兼容约定填 slots；`render_form_question` 把条件渲染成一句可读问句（例："2026 年上半年华东区与华南区、app 渠道的成交总额，按品类分组，取前 10"）。落库、history、feedback、share、审计全部复用现有路径，不新增写入分支。

**算子到 slots 的映射**（多值只在 `form_conditions` 保留全量，slots 按现有形态填主值）：

| 表单算子 | slots.filters 条目 | 强断言依据 |
|---|---|---|
| eq | `{"field": 维度显示名, "value": 标准值}` | form_conditions 全量 |
| in | `{"field": 维度显示名, "value": 主值}` | form_conditions 全量（所有值逐一核对） |
| between / gte / lte | `{"field": 指标或字段显示名, "op": ">" 或 "<", "value": 边界}`（沿用 mock 的数值过滤形态） | form_conditions 全量 |

不匹配白名单的条件在后端校验期直接 400 返回，错误信息带未登记字段名与可用字段提示（对应 F8）。

### 5.2 语义层扩展：条件登记

新增 `filters.yaml`（或 `tables.yaml` 末尾追加 `filter_fields` 段），登记表单可用的过滤字段：

```yaml
filter_fields:
  - field: orders.region
    display: 销售大区
    ops: [eq, in]
    values_from: enum          # 取值取自 tables.yaml 该字段的 enum
  - field: orders.channel
    display: 下单渠道
    ops: [eq, in]
    values_from: enum
  - field: orders.created_at
    display: 下单时间
    ops: [between, gte, lte]
    values_from: date
  - field: users.level
    display: 会员等级
    ops: [eq, in]
    values_from: enum
    join: users.id = orders.user_id    # 跨表条件携带 JOIN 依据，防 F4
```

四个关键点：

1. **取值来源指向已有枚举**，不为表单新造取值表。`value_synonyms` 继续承担口语到标准值的映射，表单侧直接用标准值；
2. **跨表字段带 JOIN 依据**，直接对应 F4；
3. **组合与互斥规则登记在语义层**，参照 AlertCenter 的先例（deviation 模式禁用维度）：在指标或字段上声明 `exclude_with`，前后端同一份规则，不散在两处；
4. **加载期校验**：算子必须在该字段的 `ops` 内、取值必须来自 `values_from`、JOIN 依据必须能在 `tables.yaml` 找到对应 `ref`。校验失败在启动时暴露，不留到运行时。`Catalog` 相应增加 `filter_fields` 索引（登记名 → 字段、算子、取值来源、JOIN）。

注意 `semantic/loader.py` 与 `semantic/dimension_check.py` 存在循环依赖，两侧都必须在函数体内延迟导入，新增代码遵守同一约定。

### 5.3 生成侧保真

`app/agent/prompts/generate.md` 在「## 语义层信息」与「## 问题」之间增加一节，表单路径渲染、自由提问路径省略（模板变量为空时整节不输出）：

```markdown
## 必须满足的查询条件（来自查询表单，逐条落入 SQL）

以下条件由用户在表单中确定，必须全部出现在 WHERE 或 HAVING 中，取值不得改写，
算子不得更换（区间为左闭右开）：

1. `orders.region` IN ('华东', '华南')
2. `orders.channel` = 'app'
3. `orders.created_at` >= '2026-01-01' AND `orders.created_at` < '2026-07-01'
```

LLM 仍写完整 SQL，不由代码代写谓词。代写会侵入生成架构、与 fix 回环的职责纠缠；保真的责任放在校验侧（§5.4），生成侧只负责把确定的信息完整传递。这与项目现有的分工一致：guard 管安不安全，签名管对不对，条件断言管全不全。

### 5.4 校验侧加强：表单条件强断言

`slot_coverage.check_slot_coverage` 现有 filter 核对按字面值与 `value_synonyms` 候选匹配，对自由提问是合理的启发式。表单条件下槽位确定，升级为强断言，新增独立函数而不是改原函数签名：

```python
def check_form_conditions(
    sql: str,
    conditions: list[dict[str, Any]],
    *,
    catalog: Any,
) -> list[SlotGap]:
    """表单条件逐条比对 SQL。缺口即阻断（表单路径），自由提问路径不调用本函数。"""
```

判定规则：

1. 每个条件经 `filter_fields` 索引解析到 (表, 列) 与算子，解析失败即缺口（登记名写错不该活到运行时）；
2. 谓词命中判定复用 `_filter_gaps` 的字面量 + `expected_columns` 逻辑，但候选集不收窄——表单值是库内标准值，不需要 `value_synonyms` 扩展；`expected_columns` 必须精确命中，不退回"只比值"；
3. 区间条件要求语句中同时存在起止两个边界（`>= start` 与 `< end`），只写一侧算缺口；
4. 排除已知假告警形态：该字段同时是本轮分组维度时不算缺失（复用 `_filtered_columns` 的既有处理）。`validate.py` 注释记录过教训：假告警一旦发生，会把正确语句改成放弃，后续所有基于它的判断都不可信。强断言必须先把这类形态排除干净再上阻断；
5. 阻断只对表单路径启用。`validate.py` 在 `query_source == "form"` 且缺口非空时走 fix 回灌（带条件清单），重试后仍缺则终止并归因 `slot`；自由提问的 `slot_gaps` 维持只记录。

失败编码沿用四归因：gap 条目带 `kind: "form_condition"`，与 guard 的 R 编号 notice 并列进前端分流。

### 5.5 时间处理

表单直接给确定日期区间（DatePicker.RangePicker），左闭右开，与 `time_terms` 的区间约定一致，作为 `orders.created_at` 的 between 条件进入 §5.4 的强断言。不使用"近 7 天"这类滚动窗口默认值：数据截止 2026-10-14，滚动窗口会整体落到数据之后返回空集，这是 T46 实测过的坑。相对时间词仅作为快捷选项存在，选中时按 `data_as_of` 换算成确定区间后再提交，换算结果回显给用户。

### 5.6 前端条件表单

- `Form.List` 条件行，字段 / 算子 / 取值三级联动：字段下拉来自 `filters.yaml`，算子下拉随字段的 `ops` 收窄，取值下拉随字段的 `values_from` 拉取（enum 或日期选择器）；
- 提交前回显面板：把每个条件渲染成"字段 算子 取值"与将生成的谓词形态，用户确认后执行（P5）；
- 维度多选 + 互斥规则与后端同一份 `exclude_with`，禁用的维度置灰并给原因，与 AlertCenter 的 deviation 处理一致；
- 指标未选时禁用条件区，维度选项随指标收窄（取自 `metric.dimensions`）。

### 5.7 空结果处理

保留现有空结果回灌（`empty_retry` 上限 1、fix 节点 `confirm_no_data`）。复杂条件下回灌提示与最终结论必须带上本轮条件清单，让"没数据"与"条件错了"在界面上可区分：回灌仍 0 行且模型确认无数据时，结论中列出全部条件；未确认时按条件缺口归因走 fix。

### 5.8 与既有功能的关系

表单入口是 `/api/chat` 的姊妹路径，共用同一 state、同一批节点、同一落库。逐项核对影响面：

| 功能 | 是否受影响 | 说明 |
|---|---|---|
| 守卫 R1–R9 | 不受影响 | 表单 SQL 仍过同一守卫，白名单不变 |
| 口径签名 | 不受影响 | 按召回指标断言，与入口无关 |
| 槽位覆盖核对 | 部分改造 | 表单条件走强断言；自由提问维持只记录 |
| fix / 空结果回灌 | 不受影响 | 同一 fix 节点；回灌提示带条件清单（§5.7） |
| baselines / findings | 不受影响 | 按结果集计算，与入口无关 |
| 脱敏 / 分享 / 回看 | 不受影响 | 落库走同一 `_persist` |
| 告警订阅 | 共享语义层校验 | `build_question` 与表单校验都用 `filters.yaml` 白名单，一处登记两处受益 |
| 下钻 | 可组合 | 下钻产出问句走 chat 入口；表单结果也可发起下钻，两条路径不互斥 |

### 5.9 端到端走查

以一条覆盖主要机制的条件组合走完全程，作为评审与首期实现的对照基准。

**表单输入**：指标=成交总额；分组维度=品类；条件=大区属于华东或华南、渠道为 app、时间 2026-01-01 至 2026-07-01；取前 10。

**请求体**：

```json
{
  "session_id": "s-001",
  "metric": "gmv",
  "dimensions": ["category_name"],
  "conditions": [
    {"field": "orders.region", "op": "in", "value": ["华东", "华南"]},
    {"field": "orders.channel", "op": "eq", "value": "app"},
    {"field": "orders.created_at", "op": "between", "value": "2026-01-01", "value_to": "2026-07-01"}
  ],
  "time_range": {"start": "2026-01-01", "end": "2026-07-01"},
  "order_by": {"field": "成交总额", "direction": "desc"},
  "top_n": 10
}
```

**后端校验**：三个条件经 `filters.yaml` 白名单校验通过（region 支持 in、channel 支持 eq、created_at 支持 between）；metric 与 dimension 在 `metrics.yaml` 的 gmv 登记中存在。

**渲染问句**（落库与回看用）："2026 年上半年华东区与华南区、app 渠道的成交总额，按品类分组，取前 10"。

**slots 直填**：

```python
{
  "metrics": ["成交总额"],
  "dimensions": ["品类"],
  "filters": [
    {"field": "区域", "value": "华东"},
    {"field": "渠道", "value": "app"}
  ],
  "time_range": "2026 年上半年",
  "order_by": {"field": "成交总额", "direction": "desc"},
  "top_n": 10
}
```

**谓词清单**（进 generate prompt，见 §5.3）：三条条件的 SQL 形态。

**期望 SQL**（口径取自 `metrics.yaml` gmv 的 example 形态）：

```sql
SELECT c.name AS 品类, ROUND(SUM(oi.quantity * oi.unit_price), 2) AS 成交总额
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
JOIN products p ON p.id = oi.product_id
JOIN categories c ON c.id = p.category_id
WHERE o.status NOT IN ('cancelled', 'pending')
  AND o.region IN ('华东', '华南')
  AND o.channel = 'app'
  AND o.created_at >= '2026-01-01' AND o.created_at < '2026-07-01'
GROUP BY c.name
ORDER BY 成交总额 DESC
LIMIT 10
```

**强断言核对**：region IN 两个值都在、channel = 'app' 在、created_at 起止两个边界都在、JOIN categories 在（品类维度携带）。任一缺失即缺口，走 fix 回灌。

## 6. 验证体系

### 6.1 评测组构成

`eval/cases.yaml` 新增 `form` 组，按现有约定在四处登记：`EXPECT_FIELDS` 白名单、run 函数、`--group` choices、`need_graph` 元组。漏任一处会导致字段静默不校验或拿不到 container。

用例构成（每条标注预期 SQL，断言方式沿用现有 `sql_contains` / `must_join` / `metric_signature` / `dimensions` 等字段）：

| 用例类型 | 覆盖 |
|---|---|
| 单条件 eq | region = 华东，基础落语句 |
| 多条件 AND | region + channel 双条件同时落语句 |
| IN 多值 | region IN (华东, 华南)，验证不漏值 |
| between 区间 | created_at 区间，验证左闭右开 |
| 跨表维度过滤 | users.level = gold，验证 JOIN 依据 |
| 过滤即分组 | 按 region 过滤又按 region 分组，验证强断言不误伤（假告警形态） |
| 互斥组合 | 声明 `exclude_with` 的组合被拒，验证前后端同一份规则 |
| 条件叠加空结果 | 多条件 0 行，验证 `confirm_no_data` 与条件清单回显 |
| 未登记条件 | 表单提交未登记字段，验证 400 与错误信息带字段名 |

样例条目（字段形态对齐现有 pipeline 组）：

```yaml
form:
  cases:
    - id: form-001
      intent: 多条件 AND + IN 多值 + 区间 + TopN 组合，全部落入语句
      request:
        metric: gmv
        dimensions: [category_name]
        conditions:
          - {field: orders.region, op: in, value: [华东, 华南]}
          - {field: orders.channel, op: eq, value: app}
          - {field: orders.created_at, op: between, value: "2026-01-01", value_to: "2026-07-01"}
        top_n: 10
      expect:
        status: ok
        min_rows: 1
        metric_signature: [gmv]
        must_join: [categories]
        sql_contains: ["region IN", "channel = 'app'", "2026-01-01", "2026-07-01", "LIMIT 10"]
```

依赖条件落语句的用例在桩模式下标 `mock_only`（mock SQL 不带区域过滤，见 §3.1 末段），与现有 slotcoverage 组的处理一致。

### 6.2 四归因统计

form 组输出按 guard / signature / slot / generate 四类统计失败，每类给出用例号与原因。归因数据决定下一轮补什么：补语义层登记、补 prompt、还是补路由，不先加功能。

### 6.3 数字分两组

form 组成绩在 `LLM_MOCK=true` 与 `LLM_MOCK=false` 下分别出数，两组并列呈现。桩模式下 SQL 来自模板，form 组中依赖条件落语句的用例标 `mock_only`；真实模型下的数字作为有效性依据。key 恢复前，form 组只做桩模式冒烟，不写"通过率"结论。

## 9. 风险与明确不做

**风险**

| 风险 | 缓解 |
|---|---|
| 强断言误伤正确语句 | 先排除"过滤字段同时是分组维度"形态；误伤一旦发生，后续所有基于它的判断都不可信，宁可先只记录一周 |
| 语义层登记成本随字段数增长 | 表单字段只从 `tables.yaml` 已登记枚举与 `metrics.yaml` 已声明维度中取，不新造取值体系 |
| 桩模式再次掩盖条件丢失 | form 组依赖条件落语句的用例标 `mock_only`，真实模型数字单独出 |
| 两个入口（chat 与 form）行为分叉 | 共用同一 state、同一节点、同一落库；form 只改 route 的输入形态与 slots 来源，diff 可控 |

**明确不做**

- 不做任意布尔表达式 DSL：`(A OR B) AND C` 这类组合初期由多个条件行的 AND 语义加 IN 多值覆盖，真需要 OR 组时再评估，不一次性做全套；
- 不引入 embedding 召回：架构基线约定表数超过 30 再换，当前 5 张表；
- 不改分层硬约束：`agent/nodes/` 不碰数据库连接、`semantic/` 不调 LLM 与 SQL 执行、密钥只在 `.env`；
- 不写库：表单查询仍走只读连接与 R1–R9；
- 不用桩模式数字单独作为任何验收依据。

## 11. 待确认问题

1. 强断言阻断的范围：只阻断 form 路径，还是自由提问的 filter 类 gap 也升级为阻断（建议前者，理由见 §5.4）；
2. 前端条件行的 AND/OR 表达上限：初期只做行间 AND + IN 多值是否满足演示需要；
3. `filters.yaml` 独立成文件还是并入 `tables.yaml`，影响加载器改动面；
4. 第四期真实模型回归依赖 key 恢复，若持续 401，验收结论如何表述（建议：明确标注"真实模型未回归"，不把桩模式数字当有效性证据）。
