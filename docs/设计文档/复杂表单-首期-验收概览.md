## 3. 关键落点

### 3.1 表单路径不调模型

`route_node` 在 `query_source == "form"` 时走 `_route_form` 早返回：槽位直填、问句重新渲染，全程零模型调用。测试用 `_NeverCalledGateway`（调用即抛）断言这一点。

问句仍然要渲染一句，原因是它承担三件事：语义召回（不渲染则指标口径标注为空）、落库、历史回看。表单没有「用户原话」，渲染出的这句就是原话。

### 3.2 白名单与取值标准化

`filters.yaml` 登记 6 个字段：`orders.region` / `orders.channel` / `orders.status` / `orders.created_at` / `users.level` / `refunds.reason`。取值接受显示值与库内值两种写法（「金卡」与 `gold` 都收），提交期统一成库内值再往下游走——谓词里必须写库内值，问句与回显里必须写显示值，两处转换集中在一处做。

跨表字段携带 `join`（`users.id = orders.user_id`），它既进加载期校验（指向未登记的表或字段即启动报错），也进生成提示词的条件清单，对应方案 F4：漏 JOIN 的语句在 SQLite 上未必报错，列名恰好存在于别的表时会静默过滤到错误的列上。

### 3.3 校验一次列全部问题

`validate_form_query` 返回问题列表而不是遇错即抛。表单一次提交六七个字段，逐个报错要来回六次才能提交成功。已覆盖的拒绝项：未登记字段、未登记维度、维度不属于该指标、算子越界、枚举取值不存在、区间缺界或倒挂、日期格式错、条件数量超 12、IN 取值超 20、TopN 越界、`order_by` 结构错。

### 3.4 谓词清单

`render_condition_block` 把条件渲染成提示词的一节，无条件时返回空串（模板整节不输出）。分组维度一并写进这一节：维度个数与顺序是确定的，交给模型自选会出现「结果集相同、行序不同、图表图例错乱」这类不报错的偏差（F6）。

## 4. 实跑结果

以下全部取自 2026-10-19 本机实跑（桩模式，`LLM_MOCK=true`），非构造数据。

### 4.1 方案 §5.9 的端到端走查

请求：指标 gmv、按品类分组、大区 IN（华东、华南）、渠道 = app、时间 2026-01-01 至 2026-07-01、TopN 10。

```
HTTP 200  status=ok  query_source=form  rows=10
question : 2026-01-01 至 2026-07-01，销售大区属于华东、华南，下单渠道为App的成交总额，按商品类目分组，取前 10
slots    : metrics=[成交总额] dimensions=[商品类目]
           filters=[销售大区=华东, 下单渠道=App, 下单时间>=2026-01-01]
           time_range=2026-01-01 至 2026-07-01  top_n=10
conditions: 3 条（region/in 两值、channel/eq、created_at/between），含解析出的 table / column
```

谓词清单（进 generate prompt）：

```
## 必须满足的查询条件（来自查询表单，逐条落入 SQL）

以下条件由用户在查询表单中确定，必须全部出现在 WHERE 或 HAVING 中。取值不得改写，算子不得更换；between 为左闭右开：

1. `orders.region IN ('华东', '华南')`
2. `orders.channel = 'app'`
3. `orders.created_at >= '2026-01-01' AND orders.created_at < '2026-07-01'`

分组维度按下述顺序与个数输出，不要自行增删（顺序变了结果集相同、行序不同，前端图表系列会错乱）：
- 商品类目：`categories.name`
```

**桩模式下生成的 SQL 里没有这三个条件**，slot_gaps 如实记录了 4 条缺口（dimension ×1、filter ×3）。这是桩 SQL 的短板而非本期实现的缺陷：mock SQL 从语义层模板派生，不带时间谓词、不带区域过滤。条件是否真的落进语句，要等第三期强断言接上、并在真实模型下复验才能判定——方案 §3.1 已把「桩模式会掩盖 F1 与 F2」列为贯穿性风险。

### 4.2 校验拒绝（四条实跑）

| 场景 | HTTP | 错误信息 |
|---|---|---|
| 未登记字段 `orders.coupon_id` | 400 | 第 1 个条件的字段「orders.coupon_id」未登记为可用条件，可用字段：orders.region（销售大区）、orders.channel（下单渠道）、orders.status（订单状态）、orders.created_at（下单时间）、users.level（会员等级）、refunds.reason（退款原因） |
| 算子越界 `orders.region` + between | 400 | 第 1 个条件：字段 orders.region 不支持算子 between，支持 ['eq', 'in'] |
| 维度不属于指标 order_count + category_name | 400 | 指标「订单量」不支持按「category_name」分组，可用维度：下单日期、下单月份、下单季度、销售大区、下单渠道、会员等级、城市 |
| 未登记维度 coupon_name | 400 | 分组维度「coupon_name」未在语义层登记 |

### 4.3 跨表条件

`users.level = gold` 解析出的条件带 `join: users.id = orders.user_id`，谓词清单里额外渲染一段 JOIN 提醒。渲染问句为「会员等级为金卡的成交总额」——显示值进问句，库内值进谓词。

### 4.4 time_range 快捷区间

`time_range: {start, end}` 在解析期合并成 `orders.created_at` 的 between 条件；请求里已写同一区间时不重复追加，避免同一区间在谓词清单里出现两遍。
