# T44 对比基准口径修正 验收概览

日期：2026-09-23  
范围：修正 FR-M-1 / FR-M-2 / FR-M-3 实现中的两处口径缺陷。不扩需求编号，不改规则表结构。

---

## 一、起因

T43 收尾时把「对比基准查询不进审计」写进了已知边界。回头核查 `app/agent/baselines.py` 时发现，真正的缺口不是留痕，而是两处会产出**错误基准值且不报错**的计算缺陷。

对比基准的既有实现是完整的：FR-M-1 至 FR-M-3 均已交付，`eval` 的 baseline 组 6/6 通过。但通过的用例全是自然月窗口（`上个月`、`本月`、`上周`），month 分支在非自然月窗口下的路径没有覆盖，缺陷因此一直没暴露。

---

## 二、缺陷一：month 粒度的环比窗口错位

### 现象

`_prior_window` 的 month 分支按整月对齐，day / week / year 分支按等长平移。窗口不是自然月时两条路径不一致。

实测（本期 2026-08-15 至 2026-09-15，跨度 31 天，推断粒度 month）：

|      | 窗口            | 与本期关系                  |
| ---- | ------------- | ---------------------- |
| 本期   | 08-15 → 09-15 | —                      |
| 应有环比 | 07-15 → 08-15 | 紧邻、等长                  |
| 实际给出 | 07-01 → 08-01 | 不相邻，08-01 至 08-15 无人覆盖 |

### 影响

同一个问句在修复前后的偏离度符号相反：

| 环比窗口               | 环比值          | 偏离度         | 结论会写成       |
| ------------------ | ------------ | ----------- | ----------- |
| 07-01 → 08-01（修复前） | 3,968,513.68 | **−10.19%** | 较上期下降约 10%  |
| 07-15 → 08-15（修复后） | 3,281,903.44 | **+8.59%**  | 较上期上升约 8.6% |

本期值均为 3,563,928.35。这不是精度误差，是结论方向反转——基准值会顺着 `baselines` 进 `findings` 异常标记与结论一致性校验，最终写进回答。

### 修法

在 `_prior_window` 前加 `_is_natural_month(start, end)`：窗口恰为自然月（start 为月初且 end 为次月月初）时才走月对齐，否则退回等长平移。

判定收在函数内部而不是调用处，两条平移路径的口径才统一。自然月窗口的月对齐语义保持不变：

| 本期窗口          | 粒度    | 环比窗口                    | 路径         |
| ------------- | ----- | ----------------------- | ---------- |
| 08-01 → 09-01 | month | 07-01 → 08-01           | 月对齐（不变）    |
| 01-01 → 02-01 | month | 2025-12-01 → 2026-01-01 | 月对齐，跨年（不变） |
| 08-15 → 09-15 | month | 07-15 → 08-15           | 等长平移（修正）   |
| 08-01 → 09-15 | month | 06-17 → 08-01           | 等长平移（修正）   |

## 三、缺陷二：无别名聚合时取到维度列

### 现象

`_exec_scalar` 的 `prefer`（聚合列别名）缺失时退回「取第一个数值列」。去掉 GROUP BY 之后 SELECT 里仍保留维度列，维度本身是数值时会取到维度值。

实测：

```sql
SELECT CAST(strftime('%Y', o.created_at) AS INTEGER) AS yr,
       SUM(oi.unit_price * oi.quantity)
FROM orders o JOIN order_items oi ON oi.order_id = o.id
WHERE o.created_at >= '2026-08-01' AND o.created_at < '2026-09-01'
GROUP BY yr
```



|       | 值                                      |
| ----- | -------------------------------------- |
| 结果行   | `{'yr': 2026, 'SUM(...)': 3968513.68}` |
| 修复前取到 | **2026.0**                             |
| 真实成交额 | 3968513.68                             |

年份、金额档位、渠道 id 这类数值维度都会触发。错误值不抛异常，会直接进入异常标记与结论校验。

### 修法

取值改为三级：别名 → SELECT 中**唯一的**聚合表达式 → 放弃。

新增 `_aggregate_positions(sql)`，从解析树取聚合表达式的下标，**按位置取值而不是按列名**。原因是无别名聚合列在结果集里的键是表达式原文（如 `SUM(oi.unit_price * oi.quantity)`），与 sqlglot 生成的文本在空格与大小写上未必逐字一致，按名匹配会静默落空。

第三档不再是「取第一个数值列」。多个无别名聚合时无法判定取哪个，返回 `None` 由调用方记 `missing_reasons`——猜错的基准比缺失更危险，使用者会拿它当结论用。

| 形态          | 修复前        | 修复后              |
| ----------- | ---------- | ---------------- |
| 有别名聚合       | 按别名取       | 不变               |
| 无别名 + 数值维度列 | 取到维度值 2026 | 取到聚合值 3968513.68 |
| 单列无别名       | 取到（偶然正确）   | 取到               |
| 两个无别名聚合     | 取第一个（可能错）  | `None`，记缺失       |

### 新增测试

`tests/test_baseline.py` 新增 11 条：

- `_is_natural_month` 三种形态判定
- 非自然月窗口的两个具体期望值
- 参数化的通用性质断言：任意窗口下环比必须紧邻本期且等长（4 组窗口）。这条是对两处缺陷的通用防线——与其逐个窗口写期望值，不如断言性质，新增粒度或调阈值时同样受约束
- `_exec_scalar` 四类：数值维度列、别名优先、两个无别名聚合返回 `None`、执行失败返回 `None`

数值维度列那条断言落在「等于真实聚合值」而不是「不等于年份」：后者在维度值恰好等于聚合值时也会通过，测不出问题。

## 五、边界

本批只修上述两处。以下项已识别，按确认结果不在范围内：

| 项          | 现状                                                                         |
| ---------- | -------------------------------------------------------------------------- |
| 对比期查询的审计留痕 | 每轮多跑的 3 条 SQL（本期标量、环比、同比）仍只有 `record_comparison_query()` 的计数，无原文、无耗时、无失败原因 |
| 规则表粒度下限    | `min_granularity` 一项同时管 mom 与 yoy，无法表达「环比要月粒度、同比周粒度就够」                     |
| 周期完整性判定    | 用 `dt.date.today()`；`data_freshness` 已作为参数传入 `compute_baselines` 却未参与判定    |
| 对比期零值口径    | COUNT 类聚合无匹配行返回 0 被当有效基准值，SUM 返回 NULL 判为缺失，两者不一致                           |
