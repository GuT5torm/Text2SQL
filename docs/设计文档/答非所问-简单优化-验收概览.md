## 二、各处改动与依据

### 2.1 指标近似兜底：候选分数打平时整轮不猜

`recall` 在整句零精确命中时，用 `_approx_score` 的字符二元组重叠度兜底，原阈值 0.6。

实测「上个月退了多少」的分数分布：销量 0.667、毛利 0.667、**退款率 0**。
两者打平说明这一处说法里根本没有能区分指标的信号——销量、毛利、退款率在业务上
共用「X 了多少」同一套说法模板，字形相近恰好是业务上最容易混淆的指标的特征。

打平时选谁都是错的，而猜错比不猜更糟：猜错会生成一条能执行、有数据、图表正常的
语句，全程不报错；不猜则落到空命中逻辑，至少看得见。

改法是两道闸，缺一即不猜指标：

- `APPROX_MIN_OVERLAP = 0.75`（原 0.6）
- `APPROX_MIN_GAP = 0.15`——最优候选必须显著高于次优

实测中正确命中（精确匹配）的 gap 最小 0.25、多数为 1.0，两道闸不会误伤。
维度判定与示例池排序仍走原来的 0.6 阈值，`_approx_score` 新增 `min_overlap` 参数区分场景。

### 2.2 口语词表：把实测为空的说法登记进去

诊断出的空命中说法按语义归属登记，未登记的一律不猜：

- 成交总额：生意、经营情况、经营状况、销售情况、卖得怎么样
- 毛利：赚钱能力、赚的钱、挣钱能力
- 客单价：平均每单、每单多少钱、一单多少钱、平均订单价
- 订单量：成交笔数、下单量
- 成交用户数：下单用户数、购买人数、付费用户、成交客户数
- 退款率：退了多少、退了多少单、退单量、退单、退款笔数、退款订单

两处需要说明的取舍：

1. 「生意」「经营情况」这类泛词没有唯一指向，登记为成交总额是本项目认定的默认。
   理由不是它一定对，而是空命中会让模型在完全没有字段清单的情况下凭常识编列名，
   比给一个默认口径更糟。口径说明会随指标一并进入 prompt，用户能看到这是哪个口径。
2. 「退了多少」要的其实是数量，库内没有退款金额指标，登记到退款率是退而求其次：
   至少落在退款域，且 caveats 会标出这是比率。

一处必须整词登记的地方：只登记「退单」时，「单量」会作为订单量的同义词同时命中且
同分，「上个月退单量」的召回结果里订单量反而排在退款率前面。登记「退单量」后，
长短语支配短短语的逻辑会把「单量」判为被支配而剔除。

### 2.3 未收录维度误报

`detect_unsupported_dimensions` 有两处误报，都会把错误的口径提示写进答案：

1. 「各区域付费用户数」报出未收录维度「付费数」。
   根因是 `_residue` 直接迭代 `vocabulary` 集合，剥离顺序由哈希决定：
   先剥掉「用户」就会留下「付费数」。改为按长度降序剥离，长词先剥，结果确定。
2. 「各品牌上个月表现」报出未收录维度「表现」。
   「表现」「走势」「变化」这类词看着像维度，实际是「怎么样」的替代表达，
   加进 `_TAIL_NOISE` 剥离。

修复后真正的未收录维度（「各种支付方式的分布」→ 支付方式）仍能正常检出。

## 五、未覆盖的部分

1. **件均价缺口**：「每件商品平均卖多少钱」仍为空。件均价是 `SUM/SUM(quantity)`，
   与客单价 `SUM/COUNT(DISTINCT order)` 不是同一个口径，库内没有对应指标。
   需要新增指标或明确拒答，不属于本次范围。
2. **域外与归因问题仍会走取数**：「帮我预测下个月销量」仍会去查历史销量，
   「为什么上个月销售额下降了」仍会返回一个数字。这需要 route 增加
   `out_of_scope` / `attribution` 意图与两个终态节点，属方案第三层。
3. **slots 仍不参与下游决策**：route 抽的槽位依旧只用于前端标注与落库，
   三处理解互不校验的架构问题没有动，属方案第一层。
4. **过滤、排序、TopN 仍无结果侧校验**：问「华东」查出全国这类偏差目前拦不住，
   属方案第四层。
