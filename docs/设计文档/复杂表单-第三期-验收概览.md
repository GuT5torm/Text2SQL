### 2.1 为什么先动桩实现

强断言上阻断后，桩模式会立刻暴露一个问题：桩 SQL 从语义层模板派生，**不带任何过滤条件**。照原样上断言，桩模式下每一条表单查询都会被判定缺条件 → 三次回灌 → give_up，表单功能在桩模式下彻底不可用，而判定红的全部是桩的短板，不是链路的缺陷。

这与「桩模式会掩盖问句不完整类缺陷」是同一件事的两面：桩不写条件，于是既掩盖不了、也验证不了条件落地。因此本期先让桩把条件写进 WHERE（含跨表 JOIN 与显式分组维度），强断言才在桩模式下具备判据能力。

## 3. 判定规则与边界

`check_form_conditions(sql, conditions, *, catalog, grouped)` 逐条比对：

| 规则 | 说明 |
|---|---|
| 候选集不扩展 | 表单值是库内标准值，不用 `value_synonyms` 兜；扩候选等于把漏写判成命中 |
| 字段精确命中 | 不像自由提问那样退回「只比值」，否则放过「过滤落在另一列上」 |
| 区间要两个边界 | 只写 `>= start` 算缺口；`< end` 与 `<= end-1` 视为等价写法 |
| 过滤即分组不算缺 | 排除已知假告警形态，见下 |
| 跨表条件查 JOIN | 条件声明了 `join` 但语句里没有该表 → 缺口（F4） |
| 登记名解析失败算缺口 | 不静默跳过：「没进语句」与「没被核对」不能是同一种表现 |

两处刻意的取舍：

1. **区间上界容忍闭区间写法**。表单下发的是左闭右开的 `< '2026-07-01'`，模型写 `<= '2026-06-30'` 语义等价。不认这个写法属于误伤，而误伤的代价是把正确语句改成放弃。
2. **表单路径下槽位核对的 filter 类让位**。槽位记口语字面值「App」，库内标准值是 `app`，两套判定并存会给出互相矛盾的结论（一条说缺、一条说有）。

### 3.1 误伤的退路

方案 §8 记的缓解措施落实为代码结构：强断言是独立函数、独立事件类型、仅在 `query_source == "form"` 时启用。评审数据上一旦出现误伤，把 validate 里那一段删掉即回到「只记录」，不影响自由提问路径。

| 用例 | 终态 | 行数 | 修正 | 归因 | 语句里的条件 |
|---|---|---|---|---|---|

| form-m002 会员等级 | ok | 5 | 0 | — | `JOIN users u ON u.id = o.user_id` + `u.level = 'gold'` |
| form-m003 过滤即分组 | ok | 2 | 0 | — | 按 `o.region` 分组，未报缺口 |
| form-m004 仅时间区间 | ok | 4 | 0 | — | `o.created_at >= '2026-07-01' AND < '2026-10-01'` |
| form-m005 注入漏条件语句 | error | 0 | 3 | **slot** | 缺口两条：销售大区、下单渠道 |
| form-m006 注入未登记表语句 | error | 0 | 3 | **guard** | `R4 表 secret_ledger 未在语义层登记` |
| form-m007 成交总额写成销量 | error | 0 | 3 | **signature** | 条件一条不落，聚合缺 `unit_price` |
| form-m008 销量写成金额 | error | 0 | 3 | **signature** | 含 `quantity` 但所有聚合都带单价 |

m005 的错误原文：

```
表单条件未全部落到语句：满足条件「销售大区属于华东、华南」：语句里没有这个条件的取值；
满足条件「下单渠道为app」：语句里没有这个条件的取值
```

m007 与 m008 的错误原文，两者走的是签名校验的两条独立分支：

```
m007  成交总额的口径不成立：语句中未出现 ['unit_price']，该指标的聚合表达式缺少必要成分
m008  销量的口径不成立：所有聚合都含有 ['unit_price', 'cost_price']，该指标要求至少有一个聚合不含这些字段
```

m007 验的是「必要成分缺失」：问成交总额只算 `SUM(quantity)`，守卫放行、条件核对也放行，唯一能抓到它的是口径签名。m008 验的是「纯度」：语句里 `quantity` 确实出现了，只查必要成分的签名拦不住，靠的是「要求存在一个不带单价的聚合」这一条。两条不能互相替代——删掉任何一条，报表上 signature 仍有数字，但覆盖少一半。

两条用例的注入语句都把表单条件写全了。这不是为了好看：签名校验排在强断言之前，条件写不全的话失败会先落在别处，归因就分不清是哪一道关卡拦下的。

失败四归因报表：

```
失败四归因（共 4 条失败）
  guard       1 条  守卫拦下——补语义层登记表 / 字段
             用例：form-m006-unregistered-table-blocked
  signature   2 条  口径签名不符——补 metrics.yaml 的指标定义
             用例：form-m007-metric-signature-degraded、form-m008-purity-check-degraded
  slot        1 条  条件没落进语句——补提示词条件清单或强断言
             用例：form-m005-missing-conditions-blocked
  generate    0 条  其余失败——换模型或调生成参数
```

归因统计的是「这一轮真的失败了」的条目，不是「用例没通过」——本组一半用例期望的就是失败，按未通过计会让归因表永远是空的。

### 4.1 单元级判定（非 eval，取自 pytest）

| 场景 | 判定 |
|---|---|
| 条件全部落语句 | 0 缺口 |
| 漏掉一整个条件 | 1 条 `form_condition`，指名「下单渠道」 |
| 区间只写一侧 | 缺口指名缺 `2026-07-01` |

## 6. 未闭合

1. **真实模型未复验**。key 仍 401，第四期阻塞。桩模式下条件落地由桩自己写入，这一组数字证明的是「强断言判定准确 + 阻断与归因通路成立」，不证明真实模型会照着谓词清单写全条件。切真实模型后 form 组需重跑，两组数字分开呈现。
2. **signature 归因覆盖的是两条分支，不是两条同类用例**。m007 走「必要成分缺失」，m008 走「纯度检查」；删掉任一条报表上仍有数字，但覆盖少一半。
3. **前端未展示归因**。四归因目前只在评测报表里，界面上没有对应呈现。方案里写的是「评测与前端按同一套编码分流」，前端部分未做。
4. **m006 不断 `conditions_covered`**。守卫在强断言之前拦下，条件压根没被核对；「没核对」与「没覆盖」合成一个字段会分不清，该用例只断归因。

## 7. 过程中的两个坑

- **`Write` 工具覆盖写**：给 `tests/test_slot_coverage.py` 追加用例时误用了覆盖写，原 219 行被替换。`git checkout` 还原后改用「新内容写临时文件 + 字节级追加」，diff 复核为纯新增 209 行。已有文件追加内容一律不要直接用覆盖写。
- **eval 的 session_id 触发审计外键错误**：`eval-*` 会话在 sessions 表里不存在，守卫拦截事件写入时 FOREIGN KEY 失败，日志有 Traceback 但主链路不受影响（记录器吞掉了）。这是既有行为，非本期引入，未改。
