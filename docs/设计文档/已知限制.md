
## 三、时间词锚点的两个边界

1. `partial_period`（本期是否未走完）自 T46.1 起按数据截止日判定，与召回、槽位核对同一锚点；`baselines.py` 内部另有「周期未开始（future）」分支，同样按锚点走，无第二套日期。
2. 数据陈旧时区间整体滞后：截止 2026-09-22 时问「近 7 天」得到 9-16 至 9-23，而不是系统日期对应的 10 月。这是刻意行为——按系统日期换算会落到没有数据的月份，语句能执行、结果必然是空。解除方式是重造数（`data/seed.py --end-date`），不是改代码。

## 四、造数脚本的固有形态

- 退款记录的 `created_at` 取「订单创建时间 + 1 至 12 天」，因此退款表截止日系统性地晚于订单表（当前 10-19 对 10-14，相差 5 天），刷新到 10-14 之后的一段窗口内退款日期会略超系统日期。`data_as_of` 取两表较早者，不受此影响；`/api/health` 的 `data_freshness.note` 会如实呈现这个差。
- 造数写死 2025-01-01 起算、随机种子固定（20260914），同一截止日生成的库完全一致；`--end-date` 只能往后，往前会让月度分布改变。

## 五、部署与运维前提

- 异常订阅依赖外部计划任务每小时调用 `POST /api/alert/check`，忘配时订阅静默不工作；`/api/health` 的 `alert_last_eval_at` 长期为 `null` 即此状态（FR-O-3 的部署前提）。
- 告警求值按 `(rule_id, evaluated_at)` 幂等，同一小时内重复调用返回旧记录。
- 桩模式下 `generate` 的 SQL 来自语义层模板，不带时间谓词与区域过滤；槽位覆盖核对在桩模式下几乎每条都会报时间缺口，这是桩的短板而非核对器的问题，相关用例标 `mock_only`。
