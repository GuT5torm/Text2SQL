## 关于本文档的定位

PRD 描述第一版要交付什么，本文只描述第一版交付后核查出的缺口要补什么。因此：

- PRD 已覆盖且已实现的部分不在本文重复。
- PRD 第六节列为「明确不做」的条目，除本文第十一节另有说明外，不作调整。
- `功能与预期效果说明.md` 第十节的「待建部分」与第十二节的「实现状态小结」在本文写作时已全部建成（前端、评测集、部署配置、测试均已落地），本文以最新实现状态替代这两节的结论；该文档第十一节记录的「接口 15 个」与守卫规则口径，本文沿用「接口 15 个」，守卫规则按代码实际为 R1–R9 九条（R8 由仓储层实现，见 1.3）。
- 任务拆分、排期与里程碑不在本文范围，沿用 `开发任务文档.md`。

### 1.3 前置事实

以下事实决定了部分需求在本轮只能登记、无法验收：

- `.env` 的 `LLM_API_KEY` 为空，`LLM_MOCK=true`，SQL 来自 `gateway.py` 的预置模板。凡依赖模型判断的能力（指代消解、槽位识别、结论生成、写法说明、SQL 解释）在配置密钥前都不可验证。
- 评测基线：`eval/report.json`（2026-09-15T17:03:10，`llm_mock=true`）recall 32/32、pipeline 9/9、safety 8/8，共 49 条计分。recall 四个子项为指标命中 30/30、维度命中 29/29、时间解析 24/24、空召回避 2/2。
- 用例定义 50 条（recall 32、pipeline 10、safety 8），报告计分 49 条，差额一条的成因已在 v1.1.0 查明：`flow-p010`（闲聊分支）在 `cases.yaml` 中标了 `requires_llm: true`，桩模式下由 `run_eval.py` 跳过，不计入 `total`，但该条仍以 `passed=true` 留在 `groups.pipeline.cases` 里。因此「定义 10 条、计分 9 条」不是数据错误，而是报告结构没有把跳过项标出来（见 FR-K-2）。
- `pytest` 153 passed（函数级用例 121 个，其余来自参数化）。
- HTTP 接口 15 个：会话 5、对话 2、语义层 6、运维 2。
- 守卫规则 R1–R9 共九条。其中 R8（扫描量上限与超时中断）由 `sqlite_repo.py` 的 progress handler 实现，不在 `guard.py` 内。九条规则在抛出侧的编号覆盖并不一致：只有 R4、R5、R7、R9 把编号写进了错误文本；R1、R2、R3 的编号只存在于代码注释；R6 是静默改写，通过 `guard_warnings` 通道产出一条「已包裹为最多返回 N 行」；R8 的文本为「查询超过 N 秒被中断」，同样无编号（见 FR-I-2）。
- `summarize_result` 返回 22 个字段，`TurnRecord` 落库 10 个字段，未落库 8 个：`stages`、`original_sql`、`guard_warnings`、`retry_count`、`truncated`、`intent`、`insight`、`highlights`（见 FR-H-2，其中 `insight` 与 `highlights` 经核对可不补列）。
- 自动纠正的重试计数 `retry_count` 上限 3，由 fix 节点递增，耗尽进 `give_up`。
- `eval/cases.yaml` 的 `reference_today` 为 `2026-09-15`，该锚点只存在于评测集，运行时零引用——界面与接口都无法回答「数据到哪一天」。

### 1.4 业务侧六项弊端（第三轮）

这一轮的问题不是从代码里读出来的，是从使用者的角度提出的。逐条核对后，每条都能在代码或数据里找到落点；下表把「用户描述」与「实测结论」并置，供评审时逐条对照。

| 弊端 | 用户描述 | 实测结论 | 本文对应条目 |
|---|---|---|---|
| 1 数据可信度说不清 | 数据只到 8-31，今天已 9-16，时效信息藏在小字里；口径没有可点开的定义入口；全是横截面数字，没有环比同比 | 时效信息**完全不存在**，不是「藏在」某处（`reference_today` 只在评测集里）；口径文本存在但只有 tooltip 一个入口；对比基准**零实现**，只在一句 prompt 里要求模型自行说明。另实测数据边界与用户判断不符，见 1.4.1 | FR-D-2、FR-D-3（升级）、FR-M-1 至 FR-M-5 |
| 2 异常断在半路 | 退货率 14.2% 标了「需要跟进」但点不进去，不能按区域/品类/退货原因下钻，也看不到趋势 | 结论里的异常标记是纯文本（`highlights` 是字符串数组）；全链路无任何下钻机制；`refunds.reason` 字段与四个枚举值已在语义层登记，但没有对应维度，按退货原因下钻做不了 | FR-L-1 至 FR-L-3、FR-L-5 |
| 3 结论和数字都不能点 | 「8 月 8 日峰值 66.74 万」「华中占比 22.6%」是纯文本，验证一个可疑结论只能重新提问 | `ResultTable` 只渲染文本，无单元格交互；结论里的数字同样无锚点。验证路径只剩「人工把数字抄进新问题里重问」 | FR-L-1、FR-L-2 |
| 4 汇报场景没覆盖 | 只有单卡导出 CSV；需要整页（结论+图表+明细）导 PDF/PPT 或分享链接放进周会材料 | 导出**完全不存在**（原表未落，图表 option 无 `toolbox`，表格无按钮）；更无整页导出与分享链接的概念 | FR-B-1、FR-N-1 至 FR-N-4 |
| 5 没有预警订阅 | 退货率超阈值这种异常得人主动来问才发现，工具退化成高级查询器 | 全项目检索「阈值、告警、预警、订阅、调度」零命中。结论里的「需要跟进」是模型一次性文案，没有任何持久化的判定与复检 | FR-O-1 至 FR-O-5 |
| 6 版面被研发信息占满 | 链路耗时（2.9s/3.8s/0.8s）和默认展开的 SQL 代码块，业务人员不关心，应该默认收起 | React 版与用户描述不符：`SqlPanel` 的 `Collapse` 未设 `defaultActiveKey`，SQL 已默认收起；`StageIndicator` 完成后收起为一行。**但高保真稿把两者都画成常显**（全文 0 处 `<details>`），且收起行本身仍带毫秒值「共 N 个阶段 · X ms」 | FR-P-1 至 FR-P-4 |

#### 1.4.1 与弊端 1 相关的实测数据

用户对数据边界的判断与库内实情不符，这个偏差本身就是需求依据：界面拿不出时效信息，使用者只能凭印象估计。

| 项 | 实测值 | 说明 |
|---|---|---|
| 订单数据边界 | `2025-01-01 07:08:27` ~ `2026-09-13 20:45:29` | 用户判断为「只到 8-31」，实际多出 13 天 |
| 退款数据边界 | `2025-01-02 10:34:48` ~ `2026-09-14 10:43:10` | 与订单表不同步，晚 1 天 |
| 2026-09 订单量 | 259 单（截至 13 日） | 8 月为 610 单。直接按月对比会得到「9 月暴跌 58%」的错误结论 |
| 退款率（全部订单为分母，2026 年至今） | 4.96% | `refund_rate` 的当前口径 |
| 退款率（排除 cancelled/pending，2026 年至今） | 5.70% | `gmv` 口径下的同期订单量 |
| 两种分母的相对差 | 15% | 用户看到的 14.2% 是高是低，取决于分母用的是哪一个 |
| `refunds.reason` 分布 | 七天无理由 330 / 质量问题 159 / 发错货 60 / 买家拒收 56 | 字段与枚举已在 `tables.yaml` 登记，缺的是维度 |
| 一单多退 | 605 笔退款对应 605 个订单，0 例重复 | 当前数据无重复，但 `refunds.grain` 明确允许「同一订单可能发生部分退款」 |
| 同比可比性 | 2025-08 为 497 单，2026-08 为 610 单 | 数据跨两个年度，同比可算；环比同样可算 |
| 可用维度数 | 9 个（日期、月份、季度、区域、渠道、品类、品牌、会员等级、城市） | 无退款原因、无周粒度 |

`orders.region` 的 7 个枚举在语义层里 key 与 value 同为中文字符串（`'华东': '华东'`），**没有说明划分依据**——是按收货地址、按用户注册地还是按下单主体划分，语义层回答不了。这一条对应 FR-M-4。

## 二、优先级与分批

优先级沿用 PRD 的 MoSCoW 标注：M 为本版必须交付，S 为应当交付，C 为可选。

分批依据是「是否改动数据结构」与「是否依赖真实模型」：

| 批次 | 判定标准 | 条目 | 说明 |
|---|---|---|---|
| 第一批 | 不改数据结构、不动接口契约 | FR-B-1、FR-B-2、FR-B-4、FR-C-1、FR-C-3、FR-D-3、FR-D-4、FR-E-2、FR-I-1、FR-K-1 至 FR-K-3、**FR-L-4、FR-M-4、FR-P-1 至 FR-P-4** | 呈现、语义层配置与评测脚本，改动集中在前端组件与 YAML |
| 第二批 | 涉及表结构、接口或状态字段 | FR-A-1、FR-A-2、FR-B-3、FR-D-1、FR-D-2、FR-D-5、FR-E-1、FR-E-3、FR-F-1、FR-F-2、FR-G-1 至 FR-G-4、FR-H-1 至 FR-H-3、FR-I-2 至 FR-I-4、**FR-L-1 至 FR-L-3、FR-L-5、FR-M-1 至 FR-M-3、FR-M-5、FR-N-1 至 FR-N-4、FR-O-1 至 FR-O-5** | 需要 `turns` 补列、新增 `feedback`／`alerts`／`alert_rules`／`shares` 四张表与十二个接口 |
| 第三批 | 依赖真实模型判断才能验收 | FR-A-3、FR-A-4、FR-A-5、FR-C-2、FR-J-1、FR-J-2、FR-J-4、FR-J-5 | 登记待 `LLM_API_KEY` 配置后开展 |

第三轮的 23 条需求**没有一条依赖真实模型**：异常判定用确定性规则、对比基准服务端计算、下钻走槽位继承、导出与订阅与模型无关。因此它们全部可以排在密钥配置之前完成并验收，不需要等第三批。

FR-K 仍排在最前，理由与 v1.1.0 相同：真实模型的准确率是第三批的核心交付，而准确率目前没有可信的度量。第三轮的条目不改变这个判断，但它们回答的是另一个问题——度量准了之后，这个工具好不好用。

## 四、需求详述

### 4.1 提问与多轮（FR-A）

| 编号 | 需求 | 现状与缺口 | 验收方式 |
|---|---|---|---|
| FR-A-1 | 多轮中可改条件、可改粒度 | 改条件靠 route 节点的指代消解把省略主语的问法补全，改粒度靠 `order_month`/`order_quarter` 维度召回。两者都是「模型愿意这么做」的行为，没有显式约束；「按周」无对应维度 | 同一会话连问三句：各区域成交总额 → 只看华东 → 改成按月看。第三问的语句须含 `order_month` 分组且过滤条件继承华东 |
| FR-A-2 | 桩模式下也能演示多轮改写 | `gateway.py` 的 route 桩只返回 `intent=query` 与 `reason`，`rewritten_question` 恒为空。桩模式下多轮只能靠 prompt 里的历史原文兜 | 桩模式下连问三句，第二问命中「那上个月呢」类关键词时图内 `question` 被改写，阶段时间线显示改写结果 |
| FR-A-3 | 识别排序与 TopN | 完全没有识别。「成交额前 5 的品类」这类问法靠模型自行理解，`generate.md` 只写了「趋势类按时间升序、对比类按度量降序」的约定 | 「成交额前 5 的品类」产出的语句含 `ORDER BY ... DESC LIMIT 5`，「各区域成交额排名」含排名语义 |
| FR-A-4 | 识别数值型过滤条件 | 只有枚举值口语（「江浙沪」→ `orders.region='华东'`）会给出提示，数值条件（「金额大于 500」）无处理 | 三条数值过滤用例产出的语句含对应比较条件，且阈值不被当作维度取值处理 |
| FR-A-5 | 意图槽位结构化 | 没有任何地方把问题解析成 `{指标, 维度, 过滤, 时间, 排序, TopN}` 的结构化槽位 | 槽位进入轮次返回体；排序、TopN、数值过滤三类用例在槽位上可断言 |

**设计说明**

槽位的作用是约束而不是替代模型判断。落点建议放在 `RouteDecision` 增加 `slots` 字段，由 route 节点一次调用同时产出意图与槽位，不新增模型调用；`retrieve_node` 用槽位里的指标名与维度名做精确命中（当前是完全基于同义词的规则打分），`generate` 把槽位作为硬约束写进 prompt。桩模式下的槽位由关键词规则填充，保证链路与用例可跑。

槽位与 FR-K-3、FR-L-2 是三处同构的需求：评测集要表达「这一句期望哪些维度、哪个指标、什么粒度」，运行时槽位要表达「这一句识别出什么」，下钻要表达「在上一轮槽位基础上加深一层」。三者必须共用同一组字段名，否则改一处漏两处。FR-L-2 是槽位的第一个真实用途——下钻的本质是槽位继承加维度加深，不是新链路。

「按周」需要新增维度。当前九个维度为下单日期、下单月份、下单季度、区域、渠道、品类、品牌、用户等级、城市，没有周粒度。若要在 `tables.yaml` 增加 `order_week`，SQLite 侧用 `strftime('%Y-%W', ...)`，需注意跨年周的编号归属（第 1 周的定义与年末几天归入上年末周的问题），并在语义层注明口径。这一条可以拆成独立需求单独评估，因为它会改变维度的对外数量（九个变十个）。

### 4.2 结果呈现与导出（FR-B）

| 编号 | 需求 | 现状与缺口 | 验收方式 |
|---|---|---|---|
| FR-B-1 | 结果表导出 CSV | 前后端均无导出实现，`ResultTable` 只做展示 | 点击导出得到可被 Excel 正确打开的中文表格，行列数与界面一致 |
| FR-B-2 | 图表导出 PNG | `chart/builder.py` 只设置了 `tooltip`、`grid`、`legend`，没有 `toolbox` 与 `saveAsImage` | 图表卡片出现下载入口，得到的 PNG 含完整图例与坐标轴 |
| FR-B-3 | 摘要数字可回溯校验 | 结论由模型依据结果集生成，服务端不校验结论中的数字是否真在结果集里 | 见下方判定规则 |
| FR-B-4 | 结论与要点复制 | 只能整段选中复制 | 一键复制本轮结论与要点列表 |

**设计说明**

导出在前端完成，不打新接口。前端已持有 `columns` 与 `rows`，可直接生成文件，避免为导出增加一次服务端查询。CSV 需带 UTF-8 BOM，否则 Excel 打开中文列名会乱码；列名取结果集列名，与表格一致，不做映射。行数被 `SQL_MAX_ROWS` 截断时，导出的文件名与文件内首行注释都要标注「已截断」，不能让用户误以为拿到的是全量。

图表导出建议在前端用实例的 `getDataURL()` 触发下载，而不是给 option 加 `toolbox.saveAsImage`。原因是 option 由后端生成、前端只负责渲染的边界已经确立（`ChartPanel` 明确声明「前端只核对字段，不重新决策业务图型」），加 `toolbox` 会让后端生成的内容里混入交互控件；同时 `toolbox` 的 `dataView` 默认会把 option 暴露给用户，需要额外关闭。

FR-B-3 是防编造的实现方式。核查其他项目的实测经验是：模型在生成结论时会自行补全提示词里没有给出的中间数值。v1.0.0 把判定写成「凡在结果集中找不到出处的数字都要标记」，这条规则过于粗糙，按字面实现会立刻产生大批误报，功能会被关掉。判定规则需要写死到下面这个程度：

1. 从结论文本抽取数值 token，处理千分位分隔符、百分号、货币符号、中文数量级（万、亿）；
2. 与结果集所有数值型单元格比对，命中条件为相对误差 ≤ 1% 或绝对误差 ≤ 0.01，百分比与小数按同一量纲换算；
3. 结论文本中的序数（第 1 名、前三）、行数与耗时（`row_count`、`query_elapsed_ms`）、时间范围起止日期属于合法来源，不参与判定；
4. 其余无法命中的数值记为待查，随轮次返回，不进结论正文；
5. 误报率门限：在现有 50 条用例上不得产生误报——即模型给出的数字若确实出自结果集，必须全部一次命中。

第 5 条是这条需求能否存活的前提。一个误报率高的核对会对每条正常回答都报警，用户很快学会忽略它。FR-L-1 的异常标记与 FR-M-1 的对比值同样进入这个白名单：它们是服务端计算的结果，不是模型编的数据。

### 4.3 SQL 展示与解释（FR-C）

| 编号 | 需求 | 现状与缺口 | 验收方式 |
|---|---|---|---|
| FR-C-1 | 写法说明落位到 SQL 面板 | `SqlDraft.reasoning` 已存在，但只被 `generate.py` 用作阶段 detail 文本，`SqlPanel` 不展示它 | SQL 面板出现「写法说明」折叠项，内容为模型给出的写法依据 |
| FR-C-2 | 按需 SQL 解释 | 无任何针对语句的解释能力 | 对一条四表 JOIN 语句得到逐段说明，说明中出现的表与字段都在语义层登记范围内 |
| FR-C-3 | SQL 下载为文件 | 只有复制 | 下载得到的 `.sql` 文件内容与面板展示的语句一致 |

**设计说明**

FR-C-1 的改动量最小：`SqlDraft.reasoning` 已在数据流里，缺的只是 `summarize_result` 没有把它带出来。建议新增 `sql_reasoning` 与 `fix_reasoning` 两个字段，前者来自 generate，后者在经 fix 修正时给出最后一次的修正理由（`fix.py` 已把 `draft.reasoning` 用于阶段文案，可直接复用）。

FR-C-2 建议做成按需触发，形态为 `POST /api/sql/explain`，请求体带 `session_id`、`sql` 与原始问题。不做成每轮自动解释，原因是解释会为每轮问答增加一次模型调用，而多数用户只看结论；也不落库，理由是解释内容不参与评测，落库会让 `turns` 表的写入路径变复杂。解释的输入只包含语句、语义层字段说明与问题，不包含结果集，避免解释过程中重新生成数字。解释失败时返回可读错误，不影响已展示的结果。按需触发的接口超时按 15 秒设定，超时返回可读错误而不占用对话链路的超时额度。

### 4.4 口径、来源与时间范围（FR-D）

| 编号 | 需求 | 现状与缺口 | 验收方式 |
|---|---|---|---|
| FR-D-1 | 展示本轮来源表 | `retrieve_node` 已把命中的表名放进 `retrieved.tables`，但 `summarize_result` 没有带出来，界面无从展示 | 四表 JOIN 的问题返回四张表名，与实际语句的 `FROM`/`JOIN` 一致；被守卫拒绝时来源表为空 |
| FR-D-2 | 数据时效的常驻与超期提示 | 无任何数据快照日期的概念。评测集里有 `reference_today`（`2026-09-15`），运行时零引用。实测订单表最大 `created_at` 为 `2026-09-13`、退款表为 `2026-09-14`，两者还不同步 | 口径标签行常驻「数据截至 2026-09-13（3 天前）」；截止日期取值单一来源；超过配置的时效阈值时高亮 |
| FR-D-3 | 口径定义入口 | 口径边界只放在 tooltip 里，触屏设备与截图场景看不到；且 tooltip 只含 `caveats`，不含表达式、依赖条件与单位 | 点击口径标签展开面板，含 `expression`、`required_filters`、`dimensions`、`unit`、`caveats`、`examples` 六项（`/api/semantic/metrics` 已提供全文） |
| FR-D-4 | 未命中口径时的显式提示 | `metric_used` 为空时 `MetricBadge` 在三者皆空的情况下整行不渲染，看起来与「有口径」无异 | 未命中时显示「本轮未命中已登记指标口径」，且该状态在评测中可识别 |
| FR-D-5 | 时间范围与语句的一致性核对 | 界面展示的时间范围来自语义层召回结果（`retrieved.time_range`），而语句里的过滤条件由模型撰写，两者可能不一致，且当前无人核对 | 见下方判定规则 |

**设计说明**

FR-D-1 的来源表应取自**实际执行的语句**，而不是召回候选。理由是被召回但未使用的表若被展示为来源，等于给出错误出处。守卫在解析语句时已经提取过表名（`guard.py::_check_tables`，含 CTE 名与子查询别名的排除逻辑），建议把这部分逻辑抽成一个公开函数供两处复用：守卫用于越权判断，来源展示用于提取。召回得到的 `retrieved.tables` 可作为辅助信息放在「语义层命中」而非「数据来源」的位置，两者不可混淆。

FR-D-2 与 FR-D-3 在 v1.2.0 从「展示」升级为「可核验的入口」，这是弊端 1 的直接落点。两条的关键约束：

- FR-D-2 的日期来源必须单一。评测集已固定 `reference_today`，运行时的「数据截至」应当与之同源，否则同一句话在不同文档与界面里会得到两个日期。落点建议：由配置项提供日期，或由业务库 `MAX(orders.created_at)` 计算并在启动时缓存，二者择一并在文档中写明；不得在 `tables.yaml` 里再写第三份日期。需要如实呈现两张表不同步的情况——订单表与退款表的最大时间相差 1 天，界面取较早者作为统一截止点，并在口径说明里写明。
- FR-D-3 的面板要能回答用户实际会问的三个问题：成交额是否含退款（`gmv.caveats` 已写明「不扣除退款，退款影响需另看 refund_rate」）、区域按什么划分（当前语义层答不了，见 FR-M-4）、退款率的分母是订单还是销量（`refund_rate.caveats` 已写明「按订单数口径」）。因此面板必须能同时承载 `caveats` 全文与字段级的划分依据，只放 `caveats` 不够。

FR-D-5 与 FR-B-3（结论不出现结果集以外的数字）属于同一类问题的两个面：都是「界面所述」与「语句所做」的一致性问题。这一条在答辩中最容易被追问，建议与 FR-B-3 一并实现，共用同一套核对思路。判定规则同样需要写具体，否则会出现「怎么核都对」的空转：

1. 从执行语句的 `WHERE` 子树中提取日期字面量与 `strftime` 参数，得到语句实际生效的时间区间；
2. 与 `retrieved.time_range` 的 `start`/`end` 比对，区间端点相同或语句区间是召回区间的子集时判为一致；
3. 语句中不含任何时间条件而召回结果给出了时间范围，判为不一致——这是最常见的一类（模型漏写过滤而界面仍显示「上个月」）；
4. 不一致时在口径标签行给出提示，并把该轮标记为可被评测识别的状态。

### 4.5 执行状态（FR-E）

| 编号 | 需求 | 现状与缺口 | 验收方式 |
|---|---|---|---|
| FR-E-1 | 阶段时间线随轮次落库 | `turns` 表不存 `stages`，前端 `turnToChatTurn` 把 `stages` 置空，历史回看看不到阶段与耗时 | 刷新页面后打开旧轮次，仍能看到完整阶段、每节点耗时与修正次数 |
| FR-E-2 | 动作态阶段文案 | 阶段标签是节点语义（如「检索口径」「安全校验」），不是用户语言 | 运行中的阶段行显示动作态文案；后端 `stage.label` 保持不变 |
| FR-E-3 | 中断、超时与异常三态区分 | 用户中断、连接中断与服务端异常共用「未收到服务端结果」一类文案，可重试性也不同 | 三种情况分别构造，文案与是否给重试入口各不相同 |
| FR-E-4 | 失败时的修正历史可见 | `give_up` 的答案里只有最后一次语句与报错，`fix_history` 里的逐次修改记录不展示 | 耗尽重试的轮次可展开查看每次修正前后的语句与原因 |

**设计说明**

FR-E-2 的映射放在前端做，不改后端标签。后端 `stage.label` 同时被日志与评测使用，改成动作态文案会让日志里出现「正在生成查询」这类与节点名不对应的记录。前端增加一张标签映射表即可，语义层与编排层不受影响。

FR-E-3 的判定依据在前端有限：`AbortError` 可以确定是用户中断；SSE 流在没有 `result` 帧的情况下收到 `done` 或直接断开，说明是连接或服务端问题。服务端侧的节点失败不进 `error` 帧（那是 `give_up` 的职责），这一点在 `chat.py` 的注释里已经写明，前端不应把节点失败当作接口异常。三态的判定优先级为：`AbortError` → 用户中断，不给重试（重试等于重复用户已经放弃的请求）；无 `result` 帧且流正常结束 → 服务端未产出结果，给重试；连接异常中断 → 给重试并提示网络。

FR-E 与 FR-P 的分工需要在这一节写明：链路进度对开发与排障有用，因此保留，但从默认视图移出。FR-P-3 定义技术细节入口，FR-E-1 保证它落库可回看，两者不是冲突的两组需求。

### 4.6 纠错（FR-F）

| 编号 | 需求 | 现状与缺口 | 验收方式 |
|---|---|---|---|
| FR-F-1 | 空结果回灌重写 | 查询成功但 0 行时，`summarize_node` 直接给出可读解释并结束，不触发纠错 | 构造「时间区间内无数据」的用例，系统或给出放宽条件后的结果，或明确判定「确认无数据」并说明依据 |
| FR-F-2 | 修正痕迹进入结论 | 修正过但最终成功的轮次，结论里看不出修正痕迹（只有 SQL 面板上的「修正 N 次」） | 修正过的轮次，结论中标注修正次数与主要原因 |

**设计说明**

空结果与报错是两类不同的失败：报错说明语句执行不了，空结果说明语句能执行但条件不合理。因此 FR-F-1 需要独立的重试计数，不能与 `retry_count` 共享，否则空结果重试会把报错重试的额度吃掉，导致原本能靠三次修正解决的报错只修两次就放弃。建议增加 `empty_retry`，上限为 1，写进配置。

回灌必须允许「不改」这个答案。用户问的区间确实没有数据时，正确行为是确认无数据并说明依据（例如「该区间内订单表无记录」），而不是为了凑出行数把条件放宽到失真。因此 fix 节点需要能返回「确认无数据」的判定，前端据此展示为正常结论而不是错误。这一条不加约束会直接演变成数据失真，是本条设计里最需要注意的地方。

空结果回灌还需要两个前置条件：语句确实通过了守卫并执行成功（守卫拒绝或执行报错走现有的报错回环，两条路径互斥）；放宽后的条件不得移除时间过滤或维度过滤，只允许放宽区间端点与枚举取值范围。第二条是为了让「放宽」有边界——把 `WHERE region='华东'` 整条删掉也能凑出行数，但那样得到的答案与用户问的不是同一件事。

FR-F-1 与 FR-M-2 有一处交互要定：时间区间的「放宽」不得跨入数据不完整的周期（见 FR-M-2）。例如把「本月」放宽为「近三个月」，若本月数据只到 13 日，放宽后的结果仍然是不完整周期与完整周期的混合，不能当作对比依据。

### 4.7 反馈闭环（FR-G）

| 编号 | 需求 | 现状与缺口 | 验收方式 |
|---|---|---|---|
| FR-G-1 | 点赞点踩 | 前端无按钮，后端无接口 | 答案卡片底部有点赞与点踩，操作后状态可回看 |
| FR-G-2 | 点踩原因与正确口径 | 无收集通道 | 点踩可选择原因，也可填写认为正确的问法或口径 |
| FR-G-3 | 反馈转为评测条目 | 评测失败条目靠人工改 YAML，没有回流路径 | 一条点踩记录可导出为待确认的评测用例片段，人工确认后写入 `cases.yaml` |
| FR-G-4 | 反馈落库位置 | 无 feedback 表 | 反馈写入 `app.db`，与业务库分离 |

**设计说明**

FR-G-1 的表结构建议为 `feedback(id, turn_id, session_id, rating, reason_code, note, created_at)`，其中 `rating` 取 `up`/`down`，`reason_code` 为枚举（口径错、字段错、数字错、答非所问、其他），`note` 为自由文本。`turn_id` 关联 `turns` 表，因此反馈只能针对已落库的轮次，正在流式输出的轮次不接收反馈。

FR-G-3 是 Few-shot 闭环的落点。当前 `metrics.yaml` 里每个指标带的问答示例是人工维护的静态配置，评测跑出的失败条目要人工回补。反馈导出只是把「人工发现」变成「可导出的候选」，最终仍需人工确认后写入配置——不建议自动写入，理由是单条点踩不能证明口径错了，可能只是问法超出语义层覆盖范围，自动写入会把个案变成通用规则。

FR-G-4 沿用既有约定：会话与评测等运行时数据写入 `app.db`，不与业务库共用连接。反馈同属运行时数据，落 `app.db`。

FR-G 与 FR-O 的关系需要在实现时对齐：`feedback.reason_code` 里的「口径错」与 FR-O 的阈值命中是两类不同信号，前者来自人，后者来自规则。两者都进 `app.db`，但不合并成一张表——人的判断需要人工确认，规则命中是自动产生的，处理路径不同。

### 4.8 历史会话（FR-H）

| 编号 | 需求 | 现状与缺口 | 验收方式 |
|---|---|---|---|
| FR-H-1 | Checkpointer 默认落库 | `.env` 实配 `CHECKPOINTER=memory`，进程重启后图内上下文丢失，旧会话可看历史但接不上上下文。另外 `/api/health` 返回的是配置值而非实际生效的模式，`SqliteSaver` 导入失败退回 `MemorySaver` 时健康检查会显示成功 | 重启服务后在同一会话继续追问，模型能拿到上文；`/api/health` 返回实际生效的模式 |
| FR-H-2 | 历史回看字段补全 | 见下方清单 | 刷新后打开旧轮次，阶段时间线、原始语句、拦截提示、截断标记与当轮一致 |
| FR-H-3 | 原始问句与改写问句的处置 | `AgentState.original_question` 已声明并在 `initial_state` 赋值，但全项目没有任何地方读取它，是死字段；route 节点把改写后的问题写回 `question`，图内后续节点用的是改写后版本 | 死字段要么被消费（日志与落库同时保留原话与改写句），要么删除；不得保留不生效的字段 |
| FR-H-4 | 会话导出 Markdown | 无导出 | 导出内容含问题、结论、口径、语句与结果表 |
| FR-H-5 | 归档会话清理策略 | 归档是软删除，无保留期与清理动作，`app.db` 会随使用持续增长。`rows_json` 每轮最多存 200 行，是增长的主要来源 | 明确保留期与清理触发方式，清理前给出提示。FR-O 的 `alerts` 与 FR-N 的 `shares` 并入同一策略 |

**FR-H-2 的字段清单（v1.1.0 逐一核对）**

`summarize_result` 返回 22 个字段，界面在历史回看时重建的字段有 8 个与当轮不一致。逐项判断是否需要补列：

| 字段 | 当前取值 | 是否需要补列 | 理由 |
|---|---|---|---|
| `stages` | 置空 | 需要 | 阶段时间线与耗时只在当轮可见，回看全丢 |
| `original_sql` | 置空 | 需要 | 守卫改写前后的对照消失 |
| `guard_warnings` | 置空 | 需要 | 被拦截的轮次回看时看不出被拦过 |
| `retry_count` | 置 0 | 需要 | 「修正 N 次」的标注消失 |
| `truncated` | 置 false | 需要，但语义要重定义 | 见下方说明 |
| `intent` | 置 null | 暂不补 | 当前界面无展示位；FR-L-2 落地后需重新评估，因为下钻要读上一轮的槽位 |
| `insight` | 置空 | 不补 | `answer` 已包含结论与要点的拼接文本（`summarize.py:81-84`），`AnswerCard` 优先渲染 `answer`（`AnswerCard.tsx:152`），回看时文本完整 |
| `highlights` | 置空 | 不补 | 同上。`highlights` 只在 `answer` 为空时作为兜底路径渲染，正常轮次不会走到 |

`truncated` 的语义需要重定义：它当前表达的是「执行期被 `SQL_MAX_ROWS`（1000）截断」，而落库时还有一次截断——`chat.py` 的 `PERSIST_ROWS=200`。两个上限不一致会导致历史回看出现「共 N 行」而表格里只有 200 行的情况（例如真实 800 行，回看显示 800 行、表格 200 行、且不提示）。落点建议：新增列记录落库截断，并把 `row_count` 与落库行数分别存储；或者把 `PERSIST_ROWS` 提升到与 `SQL_MAX_ROWS` 一致，用存储量换一致性。两者择一，需要明确选择并在界面文案上区分「查询结果被截断」与「回看数据不完整」。

### 4.9 权限、只读与脱敏提示（FR-I）

| 编号 | 需求 | 现状与缺口 | 验收方式 |
|---|---|---|---|
| FR-I-1 | 只读说明常驻 | 只读能力真实生效（`mode=ro` 加 `PRAGMA query_only=ON`，R1–R9 守卫），但界面没有任何常驻说明，只有被拦截时才出现黄条 | 界面固定位置有只读与沙箱说明，不依赖是否发生拦截 |
| FR-I-2 | 守卫告警的分类与编号 | 见下方说明 | 拦截提示中出现规则编号与对应的可读说明；改写类告警与拦截类告警文案、配色不同 |
| FR-I-3 | 敏感字段标记与掩码 | 无任何脱敏能力。当前业务库无手机号、身份证这类字段，暂无暴露面，但能力与提示都不存在 | 在测试表中构造敏感字段用例：标记为敏感的字段在界面上被掩码，并标注「已脱敏」 |
| FR-I-4 | 回合追溯信息补全 | `turns` 表存了问题、语句、状态、报错与耗时，但没有拦截告警与本轮走过的节点序列，事后无法判断「这一轮是否被拦过、改了几次」 | 归因信息可从落库记录中还原，无需重跑 |
| FR-I-5 | 行列权限不进本轮范围 | 只有全库表与字段白名单，没有按角色裁剪可见表与可见行 | 见第十一节，本条不作实现要求 |

**设计说明**

FR-I-2 有两类问题，v1.0.0 只写到编号这一层：

一是编号覆盖不全。九条规则里只有 R4、R5、R7、R9 把编号写进错误文本；R1 报「检测到 2 条语句，只允许单条查询」、R2 报「只允许 SELECT 查询，当前语句类型为 XXX」、R3 报「语句中包含被禁止的 XXX 操作」，编号都只在代码注释里；R8 报「查询超过 N 秒被中断」，也无编号。统一编号的意义不只是好读——评测的 `safety` 组要断言「该被 R3 拦下的语句确实被 R3 拦下」，当前只能靠文本匹配，加一条规则就得改一次匹配式。

二是通道混用。「被拦截」与「被改写」是两件事：R1–R5、R7–R9 是拒绝执行，R6 是放行但包裹 LIMIT。两者共用 `guard_warnings` 一个数组，前端 `AnswerCard` 对所有条目统一渲染为「SQL 被安全沙箱拦截」的黄色告警（`AnswerCard.tsx:99-112`）。被包裹了 LIMIT 的正常查询会显示成被拦截，语义是反的。落点建议：`GuardResult` 把 `errors` 与 `warnings` 分别映射为 `rejected` 与 `rewritten` 两类，前端分别渲染为黄色告警与中性提示。FR-P-3 的技术细节入口要能同时承载两类。

FR-I-3 的脱敏必须在服务端执行，前端只负责呈现标记。理由是前端脱敏对数据已出服务端的场景无效（浏览器网络面板、SSE 原始帧都能看到明文）。落点建议在结果集返回前对标记字段做掩码，掩码规则按字段类型区分：手机号保留前三位与后四位，身份证保留前六位与后四位，其余一律用固定长度占位符。`tables.yaml` 增加 `sensitive: true` 标记，由 `loader.py` 的加载期校验一并检查其是否与字段类型相容。需要一并处理的是 `rows_json`——落库的结果集同样要写掩码后的值，否则脱敏只在传输层生效，库里仍是明文。FR-N 的导出与 FR-N-3 的分享快照都要走同一条掩码路径，不能在导出侧绕过。

FR-I-5 之所以不作实现要求：行列权限依赖用户体系与角色定义，而 PRD 第六节已明确「不做用户体系与鉴权，本地单用户使用」。在没有用户主体的情况下实现行列权限只会得到一套没有主体的规则，属于过度设计。本文把这个结论写在这里，是为了避免评审时被当成遗漏。FR-N-3 的分享链接是这条边界上唯一新增的对外暴露面，其处理方式见 4.13。

**设计说明**

FR-J-2 需要明确它做到什么程度：做到「方言可在配置层切换」，不承诺换库可用。仓储实现目前只有 SQLite（`sqlite_repo.py`），换到其他数据库需要新增仓储实现；语义层里有方言敏感表达式（季度）；prompt 里的方言说明也要随之变化。本文把这一条的范围限定在「不再四处硬编码」，理由是完整的多方言适配需要真实的第二个数据库来验证，当前条件下无法验收。

FR-J-3 的成本换算需要价格表放在配置里，模型名与单价一一对应。不同厂商的计价单位不同（按千 token 计的输入输出单价通常不同），表结构要能表达输入与输出两个单价。价格表是配置项，不写进代码——单价会变，写进代码意味着发版才能更新。FR-O 的阈值求值会按周期重复执行，成本监控在这条需求落地后从「可选」变成「必要」：一个每天跑 12 次的订阅规则，其消耗与人工提问不在同一量级。

FR-J-4 标为可选，理由是收益完全取决于真实模型的候选多样性。桩模式下两次生成的 SQL 会完全相同（关键词命中相同分支），此时重排没有意义。本条应在配置密钥、积累真实失败用例之后再评估。

### 4.11 异常诊断与下钻（FR-L）

这一组回答弊端 2 与弊端 3：系统能指出「退货率 14.2% 需要跟进」，但指出来之后没有任何下一步动作。发现异常与定位原因是两件事，前者已经做了，后者完全没做。

| 编号 | 需求 | 现状与缺口 | 验收方式 |
|---|---|---|---|
| FR-L-1 | 异常标记的结构化 | 结论里的异常是纯文本（`highlights` 为字符串数组），没有结构，界面无法据此生成交互 | 返回体新增 `findings[]`，每项含 `metric`、`dimension`、`slice`、`value`、`baseline`、`deviation`、`severity`、`reason`；界面据此渲染可点击标记 |
| FR-L-2 | 从标记与单元格发起下钻 | 全链路无下钻机制；验证一个可疑结论只能人工把数字抄进新问题里重问 | 两个触发点各有用例：点击异常标记得到「该指标 + 该切片」的加深查询；点击结果表单元格得到「同口径 + 该维度值过滤」的查询 |
| FR-L-3 | 下钻维度的补齐 | `refund_rate` 的 `dimensions` 只有 order_month、region、channel、category_name；`refunds.reason` 字段与四个枚举值已在语义层登记，但没有对应维度，按退货原因下钻做不了 | 新增 `refund_reason` 维度并补入 `refund_rate.dimensions`；四类原因的产出语句可断言 |
| FR-L-4 | 退货率分母口径唯一 | `refund_rate` 的 `required_filters` 只有 `refunds.order_id = orders.id`，没有 status 过滤，而 `gmv` 排除了 cancelled 与 pending。同一份数据两种分母算出 4.96% 与 5.70%，相对差 15% | 明确分母口径并写进 `caveats`；若与 `gmv` 共用「同期订单量」，两个指标的过滤条件必须由加载期校验一致性 |
| FR-L-5 | 退款原因维度下的计数口径 | `refunds.grain` 写明「同一订单可能发生部分退款」，按 `reason` 分组后 `COUNT(DISTINCT order_id)` 会把一单多退的订单计入多个原因。当前 605 笔退款对应 605 个订单、无重复，但表设计允许 | `refund_reason` 维度注明按退款笔数还是按订单数计数；评测集补一条一单多退的构造数据用例 |

**设计说明**

FR-L-1 的判定必须由服务端确定性规则完成，不能交给模型。三条理由：桩模式下模型不产出真实结论，规则判定才能让这条需求在密钥配置前就可验收；「什么算异常」是业务定义，写进配置才可复现，让模型每次自由发挥会导致同一条数据这次算异常、下次不算；异常标记要携带 `baseline` 与 `deviation`，这两个值是计算出来的，不是生成的。

判定规则建议三条并行，任一命中即为异常：与对比基准的偏离超过配置阈值（默认 ±20%）；在同维度内的排名处于前或后若干位（默认各 20%）；绝对值超过配置阈值（如退款率 > 10%）。`severity` 取提示与关注两级，用于界面区分提示强度。

FR-L-2 的实现不是新链路，而是槽位继承。异常标记自带 `metric`、`dimension`、`slice` 三个字段，把这三个字段加一层维度后拼成完整问句，走现有的 route → retrieve → generate → validate → execute 链路即可。桩模式下不需要模型参与——字段齐备，可以用确定性映射直接拼出问句，这与 FR-A-2 的处理方式一致。真实模型下的自然语言下钻（「再看看品类」）依赖 FR-A-5 的槽位，属于增强形态。

下钻会增加查询次数，需要在实现时限定边界：一次下钻只加深一层维度，不做多级递归；下钻查询沿用同一守卫、同一超时与同一行数上限；下钻轮次与普通轮次一样落库，历史回看可见。

FR-L-4 是本组的前置。分母口径不统一时，下钻看到的数字与结论里的数字会对不上——用户点开 14.2%，下钻明细按另一种口径算出来是 12.3%，此时无法判断是下钻错了还是原结论错了。这条需求排在 FR-L-1 之前实现，成本只是一个 YAML 改动加一条加载期校验。

FR-L-3 与 FR-L-5 要一起做。新增 `refund_reason` 维度时若不定义计数口径，四类原因的退款率之和会超过整体退款率（一单多退的场景下），这在当前数据里不会出现，但 `refunds.grain` 已经写明表设计允许，构造用例必须覆盖。

### 4.12 对比基准与口径自洽（FR-M）

这一组回答弊端 1 的后半段：「25.6% 算高还是低」没法判断。横截面数字本身不携带高低信息，高低来自比较。当前链路里没有任何一处计算对比期数据，`summarize.md` 的 prompt 只写了「涉及增长或下滑时说明对比基准是什么」——模型没有基准可依据，只能从单期结果里编或者回避。

| 编号 | 需求 | 现状与缺口 | 验收方式 |
|---|---|---|---|
| FR-M-1 | 对比基准自动附带 | 无任何对比期计算。数据覆盖 2025-01 至 2026-09，同比与环比都可算，但链路不取 | 指标默认附带环比与同比两个基准值，随轮次返回；无法计算时输出「无对比期数据」而不是留空 |
| FR-M-2 | 不完整周期的标注与隔离 | 2026-09 只有 259 单（截至 13 日），8 月为 610 单。直接按月对比会得到「9 月暴跌 58%」的错误结论 | 未走完的周期在结果与图表上标注「本期未完整」；不参与环比结论生成；FR-F-1 的条件放宽步骤不得跨入不完整周期 |
| FR-M-3 | 基准值的选取规则 | 无规则可循 | 环比取相邻等长周期，同比取去年同期；对比期数据缺失或不完整时不输出该基准并说明原因 |
| FR-M-4 | 枚举取值的划分依据 | `orders.region` 的 7 个枚举 key 与 value 同为中文字符串，没有说明划分依据（收货地址/注册地/下单主体）；`categories` 有 `parent_id` 表示层级但没有一级二级类目维度 | 枚举字段补 `definition` 字段说明划分依据，加载期校验枚举字段必有 `definition`；口径面板（FR-D-3）展示该依据 |
| FR-M-5 | 口径一致性的加载期校验 | 语义层已有加载期一致性校验（表、字段、`ref`、同义词目标），但不校验指标之间的口径关系 | 指标若声明共用同一分母概念，其 `required_filters` 中的状态过滤必须一致；不一致时抛 `SemanticError` 阻止启动 |

**设计说明**

FR-M-1 的实现位置在 `summarize` 之前而不是之后。理由是结论生成需要基准值作为输入——先算基准，再把「本期值 + 基准值」一起交给模型，模型才能写出「较上月下降 8%」这类判断；如果先让模型出结论、再补基准，模型写下的比较句与后算的基准对不上，会退化成 FR-B-3 要拦的那种编造。

对比期查询走同一套守卫与限额，但要注意成本：一条问句从一次执行变成三次（本期、环比期、同比期）。这个放大倍数可以接受，但要在 FR-J-3 的延迟指标里体现出来，且对比期查询不需要全量返回，只取聚合值。

FR-M-2 与 FR-D-2 是同一件事的两个层次：FR-D-2 告诉使用者「数据到 9-13」，FR-M-2 告诉使用者「因此 9 月这一列不能与 8 月并列比较」。只有前者时，使用者看得到日期但仍然会去比；两条一起才有用。判定方式：周期的自然结束日超出数据截止日期即为不完整周期，周粒度按周结束日判断，月粒度按月末判断。

FR-M-3 的三条规则要写进配置而不是硬编码，因为不同指标的合理基准粒度不同：退款率按月环比合理，客单价按周环比噪声过大。规则表按指标名索引，未配置的指标取默认规则。

FR-M-5 把 FR-L-4 从一条个例修正升级为机制。九条守卫规则管的是 SQL 能不能跑，加载期校验管的是语义层自不自洽，两者都在进程启动时就位，口径类的问题应当在启动时暴露而不是等用户发现两个数字对不上。

### 4.13 汇报交付（FR-N）

这一组回答弊端 4。当前只有单卡导出（FR-B-1 与 FR-B-2），而周会材料需要的是「一个问题一页，含结论、图表、明细与时效」。逐项导 CSV 再手工拼 PPT 的过程本身就违背了「不重复提问」的初衷。

| 编号 | 需求 | 现状与缺口 | 验收方式 |
|---|---|---|---|
| FR-N-1 | 整页导出 PDF | 无任何整页导出。CSV 只含结果表，不含结论与图表 | 导出物含问句、结论、异常标记、口径与数据时效、图表、明细表；图表为矢量或高分辨率位图，非截图缩放 |
| FR-N-2 | 按周会模板导出 PPTX | 无 | 一页一回合，可在 PowerPoint 与 WPS 中打开，图表以图片嵌入、无外链依赖 |
| FR-N-3 | 只读分享链接 | 无 | 打开链接看到与导出内容一致的只读页面，页面无提问入口、无写能力 |
| FR-N-4 | 导出物带时效与生成时间 | 无 | PDF 页脚与 PPTX 首页含「数据截至」与生成时间 |

**设计说明**

FR-N-1 与 FR-N-2 都在前端完成，不打新接口。前端已持有渲染所需的全部数据（结论、图表 option、结果集、口径、时效），导出属于呈现层职责。PDF 用打印样式（`@media print` 加 `window.print()`）或前端库生成，PPTX 用前端库按模板拼装；两者的共同约束是**不得依赖服务端二次查询**——否则导出会变成一次隐式的重跑，数据可能与屏幕上的不一致。

FR-N-3 是本版唯一新增的对外暴露面，需要明确边界。项目没有用户体系（PRD 第六节），因此分享链接不做访问控制，采用「链接即凭据」的方式：生成时写入一条只读快照记录，返回一个不可猜测的 token，链接指向 `shares` 表中的记录，服务端只返回已落库的内容，不接受任何参数化查询。三条必须写进实现约束：快照内容是生成时刻的数据，不随业务库更新而变化；token 支持撤销与有效期；快照生成时同样走 FR-I-3 的掩码路径，不因为是「自己的数据」而跳过。这条与 FR-I-5 的边界不冲突——FR-I-5 说的是不做基于角色的行列权限，FR-N-3 加的是单条记录级别的可撤销凭据，两者不是同一层概念。

FR-N-4 是弊端 1 在汇报场景的复现。材料一旦脱离界面被转发，时效信息就彻底丢失，接收方无法判断「9 月数据只有 13 天」这件事。这一条的实施成本极低，但不做会让前面所有时效需求的努力在汇报环节归零。

### 4.14 异常订阅（FR-O）

这一组回答弊端 5。当前系统是被动查询：异常存在，但要有人主动来问才会被发现。判定异常的规则（如果实现）只在单次问答里生效，不留存、不复检，用户关掉页面后系统不再关心。

| 编号 | 需求 | 现状与缺口 | 验收方式 |
|---|---|---|---|
| FR-O-1 | 阈值规则配置 | 全项目检索「阈值、告警、预警、订阅、调度」零命中 | 可对已登记指标按维度设置阈值（如「任一区域退款率 > 10%」），规则落 `app.db` 并可增删改查 |
| FR-O-2 | 规则求值与命中记录 | 无 | 求值复用现有图（同一口径、同一守卫、同一超时），命中写入 `alerts` 表，含命中时的指标值、切片与对比基准 |
| FR-O-3 | 求值触发方式 | 无 | 提供 `POST /api/alert/check`，由外部计划任务按周期调用；接口幂等，重复调用不产生重复行 |
| FR-O-4 | 命中项的可达性 | 无 | 命中项在会话列表与首页有可见入口，可一键跳转到 FR-L-2 的下钻 |
| FR-O-5 | 求值失败与未命中的区分 | 无 | 求值失败（守卫拒绝、超时、口径不成立）不得写成「未命中」，失败与未命中在记录中分别标记 |

**设计说明**

FR-O-3 的触发方式需要解释，因为它看起来违反了「不做异步任务队列」的边界。边界本身不变：本项目不引入 Celery、MQ、Redis 之类的组件，也不引入进程内的常驻调度器。做法是提供幂等的求值接口，由操作系统自带的计划任务按周期调用（Windows 任务计划或 cron）。这样做有三个好处：调度不在应用进程内，应用重启不影响调度；求值是普通请求，走同一套守卫与超时；触发频率可随时调整而不用改代码。代价是需要一次部署配置，这一点写进 README。

FR-O-5 是这一组里最容易做错的地方。求值失败与规则未命中在返回值上很容易都表现为「没有告警」，但两者的处理方式相反：未命中是正常结果，失败是需要人介入的问题。若混淆，一个口径错误导致的持续求值失败会表现为「一切正常」，订阅功能静默失效且无人察觉。落点建议：`alerts` 表增加记录求值结果的状态列，成功求值未命中也写一行 `status=ok, hit=false`，失败写 `status=error` 并带原因；健康检查暴露最近一次求值时间与连续失败次数。

FR-O-2 的求值要复用现有图而不是新写一套 SQL。理由是一致性：订阅里算出来的退款率必须与用户提问时看到的退款率是同一个数，两套实现迟早会分叉。复用带来的约束是求值也要走守卫与限额，因此复杂规则可能被守卫拒绝——这类情况按 FR-O-5 记为失败而不是未命中。

FR-O 与 FR-L-1 共用异常判定规则（三条阈值的定义一致），但产出路径不同：FR-L-1 在单次问答内判定，FR-O 按周期批量判定。规则定义写在一处配置里，两处引用。

### 4.15 信息分层（FR-P）

这一组回答弊端 6。需要先分辨事实：React 版的 SQL 面板**已经**默认收起（`SqlPanel` 的 `Collapse` 未设 `defaultActiveKey`），阶段时间线完成后也收起为一行。所以这一组的需求重点不是「把已展开的收起来」，而是三件事：收起行本身不该带研发信息、技术细节应该有一个统一入口、以及稿件与实现的默认态要一致。

| 编号 | 需求 | 现状与缺口 | 验收方式 |
|---|---|---|---|
| FR-P-1 | 默认视图只含业务信息 | 高保真稿把链路与 SQL 都画成常显（全文 0 处 `<details>`），与 React 实现的默认态不符；链路行含每节点耗时（如 2.9s/3.8s/0.8s） | 首屏不展开任何折叠项时，看不到毫秒值、看不到 SQL 文本、看不到节点名 |
| FR-P-2 | 耗时从摘要行移除 | 收起行本身含「共 N 个阶段 · X ms」（`StageIndicator.tsx:62`） | 收起行只保留「已完成 N 步」，耗时移入展开区 |
| FR-P-3 | 技术细节入口统一 | 链路、SQL、告警、技术错误分散在卡片不同位置 | 一个固定位置的「技术细节」入口收纳四类内容；FR-I-2 的两类告警按类型分别渲染 |
| FR-P-4 | 高保真稿与实现的默认态一致 | 稿件与实际不符，评审时无法判断以哪个为准 | 稿件同步修订；两者不一致时以本文为准 |

**设计说明**

FR-P-1 的判断标准需要一个明确的分界线：默认视图承载的是「业务读者看完能采取行动的信息」，技术细节承载的是「研发与排障用的信息」。按这个分界，问句、结论、异常标记、口径与时效、图表、明细表属于前者；节点名、单节点耗时、SQL、守卫告警、模型自述属于后者。

耗时全部移除是过度处理。总耗时对业务读者有轻微价值（判断要不要等），单节点耗时没有——用户无法基于「retrieve 用了 3.8 秒」采取任何行动。因此 FR-P-2 只把毫秒值移入展开区，进度本身保留在默认视图，用「已完成 N 步」表达。

FR-P-3 与 FR-E 的分工见 4.5 的设计说明。合并入口不等于删除能力：阶段时间线仍然逐节点渲染、仍然随轮次落库（FR-E-1）、仍然用 `×N` 标记回环，只是默认不占据首屏。

FR-P-4 不是形式要求。高保真稿是设计与评审的依据，稿件与实现不一致会让后续每一轮评审都要重新确认「现在到底是哪个样子」，成本累加在沟通上。

三个唯一约束要写进建表语句，不能只靠接口层校验：`feedback` 的 `UNIQUE(turn_id)` 保证 FR-G-1 的幂等；`alerts` 的 `UNIQUE(rule_id, evaluated_at)` 保证 FR-O-3 的幂等；`shares.token` 作为主键天然唯一。

第 0 步的顺序理由与 v1.1.0 相同：断言是度量的尺子，尺子没校准之前量出来的数不能用。

第 1 步被提到最前，是因为它成本最低而阻塞最多：FR-L-4 只改 `metrics.yaml` 与一条加载期校验，但它决定了后续所有退款率相关的数字是否可信；FR-M-4 回答「区域按什么划分」，口径面板要用；FR-M-5 把两者变成机制。这三条做完，语义层从「能跑」变成「自洽」，后面所有依赖口径的工作都建在更稳的基础上。

第三轮新增的条目全部落在第 1 至 7 步，没有一条依赖第 8 步。

## 十一、范围边界

PRD 第六节列出的不做项，本版不作调整：

- 不做用户体系与鉴权（因此 FR-I-5 的行列权限不作实现要求）；
- 不做写入类功能，业务库只读；
- 不做向量检索，语义层召回仍是规则匹配；
- 不做多数据源接入；
- 不做查询缓存与异步任务队列（因此性能工程只补可观测与成本，不补缓存；FR-J-5 的复用限定在评测脚本内，不引入运行时缓存）；
- 不做容器化与编排。

本版另外不加的：不引入 Redis、Prometheus 等外部组件，可观测性靠 `/api/stats` 与日志扩展；不为解释功能单独建表；不引入第二个数据库实例；不为 FR-K 引入评测平台或看板，断言补在现有 `cases.yaml` 与 `run_eval.py` 内。

第三轮新增条目涉及的边界说明三条：

- **FR-N-3 的分享链接是唯一的对外暴露面**，采用「链接即凭据」，不做访问控制。这是 PRD「不做用户体系」的直接后果，不是遗漏；实现上以不可猜测的 token、有效期与撤销来约束，不以权限来约束。
- **FR-O-3 不引入进程内调度器**。订阅的周期由外部计划任务提供，应用只提供幂等的求值接口。因此订阅功能有一个部署前提（配置计划任务），这一前提写进 README 而不是用代码绕开。
- **FR-L-2 不做多级递归下钻**。一次只加深一层，用户需要更深时可以连续点击。做递归会引入路径管理与返回上一级的状态机，收益不足以支撑这份复杂度。

## 十二、风险与未决问题

| 项 | 说明 | 处理方式 |
|---|---|---|
| 密钥未配置 | 第三批需求无法验收，且交互层前四项的模型侧能力同样未经验证 | 最高优先级。先完成 FR-K-1，再配置 `LLM_API_KEY` 重跑 `pipeline` 组拿到真实基线，然后开展第三批 |
| 断言补强后通过率下降 | flow-p006 至 flow-p009 在补断言后大概率失败，pipeline 基线数字会从 9/9 变成更小的值 | 这是修正度量而不是引入缺陷。首次重跑前先在文档里写明预期，避免被读成功能退化 |
| 空结果回灌可能放宽到失真 | 为凑出行数而放宽条件的倾向，会让结果失去意义 | 用「允许确认无数据」、`empty_retry` 上限 1、以及「不得移除时间与维度过滤」三条约束，并在评测中加入失真用例 |
| 数值核对误报 | FR-B-3 若按字面实现会对正常回答大量报警，功能会被关掉 | 按 4.2 的五条判定规则实现，误报率门限为零，并在单测中覆盖容差边界；FR-L-1 的异常标记与 FR-M-1 的基准值进白名单 |
| 异常判定的阈值来源 | 三条判定规则的默认值（±20%、前后 20%、绝对值阈值）是提案值，没有业务依据 | 默认值写在配置里而不是代码里；在 README 与口径面板中说明这些是演示用默认值，接入真实业务时需业务方确认 |
| 对比基准的口径一致性 | 环比与同比的结果依赖对比期过滤条件与本期完全一致，任何一处不同都会让比较失去意义 | FR-M-5 的一致性校验覆盖状态过滤；对比期查询由同一个函数生成，不接受手写过滤 |
| 不完整周期的处理方式 | 标注「本期未完整」是提示性做法，使用者仍可能忽略标注去比较 | 除标注外，环比值在不完整周期下不输出数字（只输出「本期未完整，暂不提供环比」），从源头阻断误比较 |
| 订阅的部署前提 | FR-O-3 依赖外部计划任务，忘记配置时订阅功能静默不工作 | 健康检查暴露最近一次求值时间与连续失败次数；首次启动时若规则存在但从未求值过，在界面上给出提示 |
| 分享链接缺少访问控制 | 任何人拿到链接即可查看快照内容 | 在文档与界面中明确说明「链接即凭据」；提供有效期与撤销；快照内容走掩码路径，不因分享而放宽 |
| 下钻带来的查询放大 | 连续下钻会让每轮的实际查询次数成倍增长 | 一次只加深一层（FR-L-2 的边界）；下钻走同一守卫与超时；延迟计入 FR-J-3 的 p95 |
| FR-D-2 的日期来源选择 | 配置项与库内 `MAX` 两种取法各有代价：配置项需人工维护，库内取法随数据变化而变 | 在实现 FR-D-2 时确定并写入本节；无论选哪个，都要如实呈现订单表与退款表相差 1 天的情况 |
| 阶段标签的两套表述 | 后端推送「检索口径」，UIUX 文档写「正在匹配指标口径」 | 按 FR-E-2 的方式处理：后端标签不动，前端做动作态映射。FR-P-1 生效后这些文案默认不出现在首屏 |
| `PERSIST_ROWS` 与 `SQL_MAX_ROWS` 的取值选择 | 提升落库上限会增加 `app.db` 增长，保持 200 则回看与当轮不一致 | 在实现 FR-H-2 时确定，并把结论写入本表；无论选哪个，界面都要能区分「查询截断」与「回看不全」 |
