# T41 口径断言与口径守卫 验收概览

日期：2026-09-23
范围：增强回答能力的第 1、2 层——评测判别力与运行时校验。本批不含 FRD 需求编号，属核查中发现的缺陷修复。

---

## 一、起因（实测发现的两处漏报）

核查 `eval/report.json`（桩模式，生成于 2026-09-23T11:20:38）时发现 `pipeline` 组漏报两条：

| 用例 | 问题 | 实际生成的度量 | 判定 |
|---|---|---|---|
| flow-p003 | 各品类今年的毛利 | `SUM(oi.quantity * oi.unit_price)`（成交总额口径，全程无 `p.cost_price`） | passed=true |
| flow-p009 | 上个月各种支付方式的下单人数 | 成交总额口径（无 `user_id`） | passed=true |

两条的 caveats 都挂对了（毛利口径说明、成交用户数口径说明），说明**召回正确、漂移发生在生成环节**。界面后果是同一张卡片上「成交总额」列与「毛利」口径提示并存，两者矛盾而系统不报错。

根因：断言维度不全。`status` / `min_rows` / `chart_type` 只能证明「跑出了结果」，`dimensions` / `must_join` 只能证明「用了对的表与列」，没有一条能证明「算的是对的量」。

## 二、交付内容

### 1. 语义层声明口径签名（`app/semantic/metrics.yaml`）

七个成交类指标各加 `expression_signature`：

| 指标 | 判据 | 拦的是 |
|---|---|---|
| gmv | `require_all: [unit_price]` | 退化 |
| sales_volume | `require_all: [quantity]` + `require_plain_aggregate.exclude: [unit_price, cost_price]` | 问销量答成金额 |
| order_count | `require_all: [count(distinct` | 问订单量答成金额 |
| aov | `require_all: [unit_price, count(distinct` | 比值退化成单侧 |
| refund_rate | `require_all: [refunds, count(distinct` | 用订单状态顶替退款表 |
| paying_users | `require_all: [user_id]` | 问人数答成金额 |
| gross_profit | `require_all: [cost_price]` | 问毛利答成成交额 |

纯度判据取「存在一个干净聚合」而非「全部干净」，用来放行同一轮命中多指标的正常写法。

### 2. 校验器（新增 `app/semantic/expression_check.py`）

纯函数，不执行 SQL、不调用模型。

| 函数 | 职责 |
|---|---|
| `normalize_sql` | 小写、压空白、吃掉左括号两侧空格，使 `COUNT ( DISTINCT` 与 `COUNT(DISTINCT` 等价 |
| `check_expression_signatures` | 按签名比对，返回可直接回灌 fix 的中文说明 |
| `signatures_for` | 从指标定义摘签名，跳过未声明者 |

与 `db/guard.py` 的分工：guard 管语句安不安全，本模块管口径对不对，两者互不替代。

### 3. 运行时接入 validate 节点

| 位置 | 改动 |
|---|---|
| `app/agent/state.py` | `RetrievedContext` 补 `metric_signatures`；补齐此前已写入却未声明的 `unsupported_dimensions` |
| `app/agent/nodes/retrieve.py` | 把命中指标的签名摘进 `retrieved`——「本轮哪些指标要校验」留在召回环节 |
| `app/agent/nodes/validate.py` | 守卫通过后再过口径，不符则 `_fail`，说明进 `fix_history` 并回 fix 回环（重试上限 3 沿用）；两道关卡顺序固定为先安全后口径 |

### 4. 评测接入

| 位置 | 改动 |
|---|---|
| `eval/run_eval.py` | `EXPECT_FIELDS` 的 pipeline 组加 `metric_signature`；判定调用与运行时同一个校验器；用例写了不存在的指标名会直接报失败 |
| `eval/cases.yaml` | 九条 pipeline 用例各补齐期望指标；顶部注释载明该字段与 `sql_contains` 的分工 |

### 5. 桩实现改为从语义层派生（新增 `app/llm/mock_sql.py`）

原 `_MOCK_SQL_BY_KEYWORD` 是关键词到整条 SQL 的映射，只有成交总额与退款率两种聚合表达式，问毛利、问订单量、问客单价、问成交用户数全部落到成交总额模板。**这是第 1、2 层可验证的前提**：不修的话，运行时守卫会让桩模式下这四类问句全部进 fix 回环直到重试耗尽。

新模块按「指标决定聚合表达式、维度决定分组列与 JOIN」从语义层拼装，仍不调用模型。TopN、排名、数值过滤三类修饰保留。

顺带修两处：

- 比较阈值改为从问句解析（`高于 0%` → 0，`大于一百万` → 1000000）。原先写死两档，会让「退款率高于 0%」与「退款率高于 999999」得到同一个 HAVING，两条评测用例一真一假无法区分
- `_mock_subject` 改为按小节截断到下一个二级标题。原先取「## …问题」标题之后的**全部**内容，而 `fix.md` 的「## 原始问题」后面还跟着「## 语义层信息」，语义层段落里列着全部指标名，桩实现会照着「退款率」生成一条退款查询

## 四、已知边界

- **签名只覆盖两类判据**：必要成分与聚合纯度。过滤条件是否与口径声明一致（时间范围、`status NOT IN ('cancelled','pending')`）不在签名职责内，仍由 `caveats` 与结论数字核对器把关
- **存在假阳性可能**：若模型采用语义层未覆盖的等价写法（例如先子查询算出成本再相减），`require_all` 会因找不到 `cost_price` 而误报。当前未观察到；出现时按具体情况放宽签名，不要为了消除误报而取消该指标的签名
- **桩实现仍不处理过滤值**：「华东区的销售情况」不会落到 WHERE，也不做问法改写。它依旧只是链路打通与单测替身，产出不代表真实模型能力
