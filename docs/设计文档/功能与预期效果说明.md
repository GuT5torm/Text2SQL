> 项目：基于 Text2SQL 的电商数据分析 Agent　｜　版本：v1.0.0
> 上游：《PRD-产品需求规格说明书.md》《Text2SQL-Agent-系统架构设计.md》《UIUX-界面设计文档.md》

## 一、总体效果

用户输入一句中文问题，系统在一次 HTTP 流中完成意图识别、口径召回、SQL 生成、安全校验、只读执行、图表决策与结论生成，并在界面上同时给出四样东西：经营结论、图表、实际执行的 SQL、本轮采用的指标口径。

一句话概括预期效果：**业务人员不用知道表结构，也能在十几秒内拿到一个可以追溯口径的数据结果。**

与传统取数路径的差异体现在三处：

| 环节 | 原有路径 | 本系统预期效果 |
|---|---|---|
| 提出需求 | 向数据团队提需求、等排期 | 直接中文提问，无需中间人 |
| 口径确认 | 口头约定，事后扯皮 | 口径来自 `semantic/metrics.yaml`，前端标注，可逐条比对 |
| 结果可信度 | 无法判断数字怎么算出来的 | 语句与口径随结果一同展示，数字可追溯到具体表达式 |

## 三、功能一：对话取数

### 3.1 单轮问答

用户输入自然语言问题，例如「上个季度华东区各品类的成交总额」，系统在数秒至十几秒内返回结论、图表、语句与口径。

后端链路为 LangGraph 状态机，八个业务节点加三个终态节点：

```
route ──┬─ chitchat ─► respond  ─► END
        ├─ clarify  ─► clarify  ─► END
        └─ query ─► retrieve ─► generate ─► validate ─┬─ 通过 ─► execute
                                                      └─ 失败 ─► fix ─┐
                                        execute ─┬─ 成功 ─► visualize ─► summarize ─► END
                                                 └─ 失败 ─► fix ──────┘（回到 validate）
```

`fix` 修正后必须回到 `validate` 重新过守卫，不允许绕过校验直接执行。校验与执行共享重试配额，默认上限 3 次（`SQL_MAX_RETRY`），耗尽后进入 `give_up`，返回包含最后一次语句与报错的可读说明，而不是无限循环消耗 token。

### 3.2 多轮追问

用户接着问「那上个月呢」这类省略主语的问法时，`route` 节点在识别意图的同时把问题补全为完整表述（例如补全时间范围与主体指标），写回 `question` 后交给下游。上下文由 LangGraph Checkpointer 按 `session_id` 作为 `thread_id` 累积，最近 6 轮回灌给模型（`HISTORY_WINDOW`）。

预期效果：连续追问时不需要重复说明指标与维度，且落库记录的是补全后的问题，回看历史时能看懂当时问的是什么。

### 3.3 信息不足时反问

缺少时间范围或分析维度时，系统反问而不是猜测。反问文案由模型生成，模型判定需要澄清但没有给出具体问题时，代码会改判为按取数处理，避免卡在一个空反问上。

### 3.4 阶段进度可见

等待期间按节点推送进度。后端实际推送的节点标签与典型文案：

| 节点 | 标签 | 说明文案示例 |
|---|---|---|
| `route` | 理解问题 | 判定为取数问题 / 信息不足，需要反问用户 |
| `retrieve` | 检索口径 | 命中 1 个指标口径、3 张表；时间范围 上个季度 → 2026-04-01 ~ 2026-06-30 |
| `generate` | 生成查询 | 已生成查询，涉及 3 张表 |
| `validate` | 安全校验 | 通过校验，涉及 3 张表 / 失败时给出规则编号与原因 |
| `execute` | 执行查询 | 返回 12 行，耗时 34 ms |
| `fix` | 修正查询 | 第 1 次修正未成功 |
| `visualize` | 绘制图表 | 选择 bar 图：单维度「品类」对比，用柱状 |
| `summarize` | 分析结果 | 已生成 12 行数据的解读，口径说明 1 条 |

三条终态分支：`respond`（闲聊，返回可用问法示例）、`clarify`（反问）、`give_up`（重试耗尽）。传输方式为 SSE，三类事件：`stage`（节点进度）、`result`（本轮结果）、`error`（未预期异常），最后发 `done` 关闭连接。

### 3.5 闲聊与非取数问题

输入「你好」这类内容时走 `respond` 分支，返回本数据集能回答的问题示例，不调用数据库、不生成 SQL。

## 四、功能二：SQL 展示与口径标注

这是本系统与「把建表语句直接丢给大模型」做法的实质区别所在，也是答辩时最值得演示的部分。

### 4.1 展示实际执行的语句

每轮回答下方以折叠面板展示实际执行的 SQL。守卫对无 LIMIT 或 LIMIT 超限的语句会做包裹改写，因此同时保留改写前语句（`original_sql`）与改写后语句（`sql`），前端两版都展示，避免「看到的语句」与「跑的语句」对不上。

### 4.2 标注本轮口径

语义层登记七个指标，每个指标含口径表达式、必带过滤条件、适用维度、边界说明与示例：

| 指标 | 显示名 | 口径表达式 | 边界说明 |
|---|---|---|---|
| `gmv` | 成交总额 | `SUM(oi.quantity * oi.unit_price)` | 不含已取消与未支付订单；不扣退款 |
| `sales_volume` | 销量 | `SUM(oi.quantity)` | 默认件数口径，非订单数 |
| `order_count` | 订单量 | `COUNT(DISTINCT orders.id)` | 不 JOIN 明细表，避免一单多商品重复计数 |
| `aov` | 客单价 | 成交总额 / 订单数 | 分母为订单数，非用户数 |
| `refund_rate` | 退款率 | 退款订单数 / 订单数 | 按订单数口径，非金额口径 |
| `paying_users` | 成交用户数 | `COUNT(DISTINCT orders.user_id)` | 区间内多次下单只计一次 |
| `gross_profit` | 毛利 | `SUM(oi.quantity * (oi.unit_price - p.cost_price))` | 成本取当前成本，非下单时点成本；不含履约与推广费用 |

召回命中后，指标显示名与边界说明随结果返回（字段 `metric_used` 与 `caveats`），前端渲染为口径标签。预期效果：用户看到「成交总额 12,345,678 元」时，同时看到「不含已取消与未支付订单；不扣除退款」这个前提。

### 4.3 拦截原因可见

安全守卫在 AST 层做校验，规则如下：

| 规则 | 内容 | 行为 |
|---|---|---|
| R1 | 只允许单条语句 | 拦截 |
| R2 | 只允许 SELECT / UNION / EXCEPT / INTERSECT | 拦截 |
| R3 | 语句树中不得出现 DDL / DML / 管理类关键字 | 拦截 |
| R4 | 表必须在语义层登记 | 拦截，提示疑似模型编造 |
| R5 | 字段必须存在于所属表元数据 | 拦截，并给出形近字段提示 |
| R6 | 无 LIMIT 或超限时包裹为最多 1000 行 | 自动改写并提示 |
| R7 | 多表查询必须带连接条件，禁止 CROSS JOIN | 拦截 |
| R8 | 执行超时中断 | 由仓储层 progress handler 实现 |

预期效果：校验不通过时，界面展示具体规则编号与原因，例如「R5 字段 oi.price 在表 order_items 中不存在，是否为 unit_price？」，而不是静默失败。R5 的形近字段提示会一并进入 `fix` 节点的修正上下文，提高一次修正成功率。

### 4.4 修正过程可见

每次失败都会记录 `fix_history`，包含所处阶段、当时的语句与数据库原始报错。预期效果：构造一次失败场景后，用户能看到系统在哪个阶段失败、依据什么报错、做了几次改动、最终是否成功。重试耗尽时给出最后一次的语句与失败原因，并提示换一种问法或补充口径定义。

## 五、功能三：图表与分析结论

### 5.1 自动选图

采用模型优先、规则兜底的两条路径。`visualize` 节点让模型输出图型与字段映射，`chart/builder.py` 校验字段是否真实存在于结果集中；字段对不上时按结果集结构重新决策。

规则决策依据（后端实测实现）：

| 结果集特征 | 图型 |
|---|---|
| 结果集为空 | 表格 |
| 列数超过 4 或没有数值度量 | 表格 |
| 没有可用于横轴的维度 | 表格 |
| 问占比构成、单维度单度量、行数不超过 12 | 饼图 |
| 首个维度为时间维度 | 折线 |
| 单维度对比、行数不超过 30 | 柱状 |
| 其余维度组合 | 表格 |

图型只有折线、柱状、饼图、表格四类，不做数字卡。饼图带百分比标签，多条系列时按 `series_field` 拆线并自动挂图例，横轴标签过长时倾斜 30 度。

预期效果：模型选错图型或选错字段时，界面不会渲染出空白图表，最多退化为表格。

### 5.2 经营结论

`summarize` 节点依据本轮结果集生成结论与要点，口径边界从语义层召回结果中获取，不允许模型自行补充。结果集为空时给出可读解释（筛选过严、区间内无成交记录、维度取值不一致等），而不是报错。结论生成调用失败时退回事实陈述，例如「查询返回 12 行结果，具体见上方图表与结果表」，数据与图表照常呈现。

预期效果：结论中不出现结果集以外的数字；每轮回答都注明所用口径与数据范围。

### 5.3 结果表格

结果集随 SSE 全量返回，落库时只保留前 200 行用于回看。单次下发上限由守卫的 LIMIT 强制为 1000 行。宽表以横向滚动呈现。

## 六、功能四：历史会话

每次问答写入独立的会话库 `data/app.db`，与业务库不共用连接。留档内容包括问题、结论、语句、本轮口径与边界说明、图表配置、结果集快照、行数、耗时与状态。

接口能力：创建会话、列表（支持按标题或提问内容关键词搜索、含归档筛选）、详情（含全部轮次）、重命名与归档、删除。归档为软删除，归档后不在默认列表出现，可通过状态筛选找回。

预期效果：重启后历史列表仍在，回看某一轮时无需重跑查询即可看到当时的结论、图表与语句。

## 七、功能五：评测集

评测集目录 `backend/eval/` 已建，用例与脚本待补。设计目标为每条用例含问题与验证方式，覆盖七个指标与主要维度，脚本一键输出可执行率与准确率汇总。

评测结果用于回答答辩必问的准确率问题。按项目约定，先跑基线再设目标值，不预先设定数字。评测通过 `POST /api/chat/sync` 非流式接口驱动，便于脚本批量调用。

## 八、一次完整问答的预期效果

以「上个季度华东区各品类的成交总额」为例，界面上的完整过程：

| 阶段 | 用户看到 |
|---|---|
| 提交后 | 输入框禁用，出现用户气泡 |
| 逐节点 | 阶段指示依次追加：理解问题 → 检索口径 → 生成查询 → 安全校验 → 执行查询 → 绘制图表 → 分析结果，每条带耗时 |
| 收到结果 | 结论卡片（经营解读 + 要点列表）、口径标签（成交总额、不含已取消与未支付订单）、柱状图、可折叠 SQL 面板、结果表格 |
| 结束 | 收到 `done`，关闭连接，输入框恢复 |

回答卡片的结构固定，顺序为：阶段指示（完成后收起为一行）→ 结论文本与要点 → 口径标签 → 图表 → SQL 折叠面板 → 结果表格。

## 九、安全与性能的预期效果

| 类别 | 预期效果 | 依据 |
|---|---|---|
| 语句安全 | 只允许单条查询类语句，表与字段走白名单，多表必须带连接条件 | 守卫 R1–R7 |

| 密钥管理 | 密钥只出现在 `.env`，代码与配置文件中无字面量 | `config.py` |

## 十一、两处待对齐的表述差异

在整理过程中发现三处表述与实现不一致，建议在后续文档中统一：

1. **接口数量**：此前记录为 14 个，按路由装饰器实测为 15 个（会话接口是 5 个而非 4 个：创建、列表、详情、重命名与归档、删除）。本文按 15 个表述。
2. **阶段文案**：`retrieve` 节点实际推送的标签是「检索口径」，《UIUX-界面设计文档.md》5.2 节写为「正在匹配指标口径」。前端实现时以接口实际返回为准，或同步修改节点标签。
3. **守卫规则条数**：`db/guard.py` 与部分节点注释写「八条规则」，项目对外口径为「七条规则 + 仓储层一项超时中断」。差异来源是 R8 由 `sqlite_repo.py` 的 progress handler 实现，不在 `guard.py` 内。PRD 已按后者表述，本文沿用。
