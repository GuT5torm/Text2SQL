# T43 审计日志 验收概览

日期：2026-09-23
范围：守卫判定与 SQL 执行的审计通道。本批不含 FRD 需求编号，属功能新增；前端页面与写操作审计按确认结果不在范围内。

---

## 一、起因

FRD 功能需求完善文档里有一句判断：「留痕算查询记录不算审计（无规则编号、无节点路径）」。核查代码后确认属实，缺的是三类记录：

| 缺什么 | 现有什么 | 为什么不够 |
|---|---|---|
| 被守卫拒绝的语句 | `turns.guard_warnings_json` | 只记最终落库那一轮的告警；候选语句被拒后既不落 turns 也不进日志，查不到「系统曾经试图执行什么」 |
| 会话删除后的历史 | `turns` 表 | `delete_session` 级联清空，业务操作能抹掉执行痕迹 |
| 可查询的执行记录 | 各处 `logging.getLogger` | 只有 stdout，重启即丢，无法按条件检索 |

`turns` 表本身字段很全（SQL、口径、阶段耗时、来源表都在），它是**业务留痕**，面向使用者回看；审计面向排查与追责，两者生命周期不同，因此本批新建独立通道而不是往 turns 上加字段。

## 二、交付内容

### 1. 审计领域模块（新增 `app/audit/`）

| 文件 | 职责 |
|---|---|
| `events.py` | `AuditEvent` 数据结构、六类事件常量、`extract_rule_id`（从守卫文案取 R1–R9）。**不 import 项目内任何模块**——事件被存储层、编排层、接入层三方引用，反向依赖会成环 |
| `sinks.py` | 四个落点：`DatabaseSink` / `LoggingSink` / `NullSink` / `MemorySink`。只暴露 `write`，让「写不进去」有统一兜底位置 |
| `recorder.py` | 进程内单例。写入异常吞掉并记 warning——审计是旁路，它失败时正确的处理是继续，不是中断主链路 |

事件类型按**判定发生在哪一步**划分，不按结果好坏划分：

| 事件 | 结果 | 采集点 | 记什么 |
|---|---|---|---|
| `sql_guard_block` | denied | validate | 守卫拒绝，带规则编号与错误列表；语句不会被执行 |
| `sql_guard_rewrite` | ok | validate | 守卫通过但补了 LIMIT（R6），带 warnings |
| `sql_guard_pass` | ok | validate | 通过且未改写 |
| `sql_metric_block` | denied | validate | 安全过关但口径签名不符 |
| `sql_execute` | ok | execute | 行数、耗时、来源表、列名（上限 50） |
| `sql_execute_error` | error | execute | 数据库原始报错、来源表、第几次尝试 |

改写与直接通过分成两类：改写量是要盯的运维信号（说明模型没写 LIMIT），合并后只能翻 `detail` 才看得出。

### 2. 存储层

| 文件 | 改动 |
|---|---|
| `app/db/models.py` | 新增 `AuditLog` 表：`ts` / `event_type` / `outcome` / `rule_id` / `session_id`（均带索引）、问句、语句、原因、来源表、行数、耗时、`detail_json` |
| `app/db/repository.py` | 新增 `AuditRepository` 接口：`record` / `search` / `count` / `summary` |
| `app/db/audit_repo.py` | SQLite 实现 |

结果集明细不进审计表：审计要能追溯到「访问了哪些表哪些字段」，不需要复制一份业务数据。

### 3. 埋点与接线

| 位置 | 改动 |
|---|---|
| `app/agent/nodes/validate.py` | 四类判定各记一条；`_record` 统一补 `session_id` 与问句（这两个来自状态而非依赖注入，调用点不必各自记得传） |
| `app/agent/nodes/execute.py` | 成功与失败各记一条，失败路径也带来源表 |
| `app/agent/graph.py` | `build_graph` 增 `audit` 参数，注入 validate 与 execute |
| `app/api/deps.py` | `_configure_audit` 分三档装配：关闭 → NullSink，正常 → DatabaseSink，库不可用 → LoggingSink 并告警；Container 增 `audit` 与 `audit_recorder`；`reset_container` 一并复位记录器 |
| `app/config.py` | 增 `audit_enabled`（默认 true） |

分层约束未被破坏：`FORBIDDEN_IN_NODES` 不含 `app.audit`，节点引入的是领域模块而非存储实现；落库由装配时注入的 sink 完成。

### 4. 查询接口（新增 `app/api/audit.py`）

| 接口 | 用途 |
|---|---|
| `GET /api/audit` | 检索。按类型 / 结果 / 规则 / 会话 / 关键词 / 时间区间筛选，带总数供分页 |
| `GET /api/audit/summary` | 按类型、结果、规则编号分别计数 |
| `GET /api/audit/export` | 按当前筛选导出 CSV 或 JSON，上限 5000 条 |

两处刻意的设计：枚举参数拼错返回 400 并把可选值回给调用方（静默忽略会返回全部记录，排查更费时间）；审计不可用时返回 409 而非空列表——空列表会被读成「这段时间没有拦截」，与「审计根本没在工作」是两回事。CSV 带 BOM，问句里的逗号与换行走 `csv.writer` 转义。

### 新增测试 16 条的覆盖点

- 守卫拦截事件带规则编号 `R4`、会话与问句齐全
- 改写与通过是两类事件，各自 1 条
- 口径拦截事件无规则编号（如实留空）
- 执行成功记行数与来源表，执行失败记原始报错
- **sink 抛异常时节点照常返回**（用会炸的 sink 跑 validate，断言无 `sql_error`）
- 关闭时彻底静默
- 删会话后审计仍在且 `session_id` 保留原值，同时 `turns` 已被清空——这条同时验证分界线两侧
- 仓储的筛选、时间区间、倒序、汇总计数
- 接口的检索 / 筛选 / 汇总 / CSV / JSON / 400 / 409

### 一处设计更正（实测撞出来的）

初版给 `session_id` 加了 `ForeignKey(sessions.id, ondelete="SET NULL")`。测试里写入一个不存在的会话 id 时，SQLite 直接抛 `FOREIGN KEY constraint failed`——**审计因为业务表里没有对应行而丢记录**，等于让业务表绑架审计。同时 SET NULL 会把唯一的追溯线索抹掉，与审计目的相反。

改为不带外键的普通索引列：删会话不影响审计，会话已删也保留原 id 供追溯。这不是妥协，是审计语义的正确写法——审计与业务数据之间不该有引用完整性约束。

## 四、已知边界

- **对比基准查询与数据时效探针不进审计**。`baselines.py` 的环比同比查询、`_freshness.py` 的 `MAX(created_at)` 直接调 `repository.execute_readonly`，不经过 execute 节点，也没有会话上下文；审计以 `session_id` 为主要归属维度，塞进无归属的记录会稀释价值。要覆盖需给这两条路径补上下文传递
- **候选重排的守卫判定不重复记**。`candidate_rerank.py` 给候选打分时也调 `guard.check`，未记：同一条语句会被记两遍，排查时反而分不清哪条是最终判定。最终进入 validate 的语句才是判定点
- **actor 只有会话粒度**。项目明确不做用户体系，审计记录里没有账号、IP、UA，「谁」只能回答到会话
- **接口无鉴权**。审计日志同时含问句与语句原文，比业务数据更敏感。单机演示环境下接口本身即访问边界，部署到共享环境必须在外层加访问控制
- **审计表没有保留期与清理**（本批未选该项）。数据量增长后需另开一批处理
