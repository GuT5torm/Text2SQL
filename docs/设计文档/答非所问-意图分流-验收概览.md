## 二、两类终态的判定

### out_of_scope：三类触发

1. 要一个尚未发生的数——「帮我预测下个月销量」「预估下季度的成交总额」；
2. 数据集里没有的实体——「库存还有多少」「各商品还有多少存货」；
3. 根本不是数据分析任务——「怎么写爬虫」。

此前这三类都按取数处理：「预测下个月销量」会去查历史销量，「库存还有多少」会硬生成
一条查不到的语句。终态文案给出判定依据与三条可照着问的例子。

### attribution：为什么不给数字

「为什么上个月销售额下降了」，一条聚合查询能给出的只有下降了多少，而这个数字用户往往
已经知道。给出它等于把一个解释型问题当成取数问题回答——是答非所问最典型的一种形态。

替代问法按 route 已识别的槽位拼，不给通用建议：

```
1. {时间}与上一个同长度周期的{指标}，看变化幅度有多大
2. {时间}各{维度}的{指标}及环比，看变化集中在哪一块
3. {时间}订单量、客单价、退款率分别的变化，区分是量的问题还是价的问题
```

槽位缺失时有兜底（成交额 / 区域 / 最近一个月），保证三种问法始终可照着问。

### 与既有终态的边界

`give_up` 是「想答但答不出来」（语句写错、数据没有），这两个是「不该答」或「不该给数」。
混为一谈会让用户误以为是系统能力不足。前端因此不用 error 色，用 warning 提示条。

## 三、桩实现必须同步

两个新分支在真实模式下由 route 节点判定，桩模式下只能靠关键词表。只改提示词而漏改
`gateway._mock_route_decision`，会出现桩模式下新分支永不触发的评测假绿——评测全绿，
线上照旧答非所问。

归因关键词不登记裸词「原因」：`eval` 里有「各退款原因的退款率」这种维度名用法，登记裸词
会把正常取数判成归因。只登记带疑问语素的组合（为什么 / 为何 / 什么原因 / 归因等），
并补了一条反向用例 `oos-neg-reason-dim` 锁住这个边界。

域外与归因的判定放在槽位填充之后、取数判定之前：两者都会命中指标词（「预测下个月销量」
含「销量」、「为什么销售额下降」含「销售额」），放在后面会被 query 吃掉。

## 五、遗留

- **slots 下沉**（方案一）未做：route 抽出的槽位仍不参与 retrieve 与 generate 的约束，
  两者各自理解一遍问句，彼此不比对。
- **槽位覆盖校验**（方案四）未做：「SQL 合法但答的不是问的那件事」仍不可检测——少了华东
  的过滤条件，口径签名照样匹配。
- **件均价**仍是缺口：库里没有 `SUM/SUM(quantity)` 这个口径，未硬塞映射。
- 真实模型下两个新意图的判定准确率未测：本环境无可用密钥，评测与单测都在桩模式下取，
  切到真实模型后 outofscope 组的 8 条会自动从关键词判定转为模型判定。
