## 二、最终产物的形态

### 2.1 交付物构成

按《【参数】Text2SQL电商数据分析Agentv1.0.0.md》，交付包包含 1 个应用、1 份案例 PPT、7 份实训指导书、3 份附录、1 份代码、18 份 RAG 语料与 1 份提示词。本文描述的"使用流程"针对其中的**应用部分**，即那 1 个可运行的 Text2SQL-Agent。

### 2.2 运行形态

应用是一个单进程 FastAPI 服务：

| 项 | 取值 | 说明 |
|---|---|---|
| 进程 | `uvicorn app.main:app` | 单进程，不使用容器 |
| 端口 | 8000 | 交互式接口文档在 `/docs` |
| 前端 | `frontend/dist` 存在时自动挂载 | 由 `main.py` 的 `FRONTEND_DIST` 判断；不存在时只提供 API |
| 业务库 | `backend/data/ecommerce.db` | 只读连接，6 张表，由 `seed.py` 生成 |
| 会话库 | `backend/data/app.db` | 读写，与业务库不共用连接 |
| 接口数量 | 15 个 | 运维 2、对话 2、会话 5、语义层 6 |

开发期前端由 Vite 单独跑在 5173 端口，`vite.config.ts` 配 `/api` 代理到后端；交付期执行 `npm run build` 产出 `frontend/dist`，只启动后端一个进程即可。

### 2.3 三类使用者与入口

| 使用者 | 目标 | 入口 |
|---|---|---|
| 业务人员 | 提问题、拿结论 | 浏览器打开界面 |
| 开发 / 运维 | 验证链路、排查问题 | `/docs` 交互文档、curl、日志 |
| 教学实训 | 按实训指导书逐步复现 | 命令行 + 接口 |

前端界面目前尚未实现（`frontend/` 为空目录），因此在界面可用之前，所有流程都通过 HTTP 接口完成。本文第五节描述的界面操作是目标态，第十节给出等价的接口调用路径，两者覆盖同一条链路。

## 三、启动前准备（一次性）

### 3.1 环境

虚拟环境实测 Python 3.13.14。创建与装依赖：

```bash
cd /c/Text2SQL/backend

./.venv/Scripts/python.exe -m pip install -r requirements.txt
```

命令统一用 `.venv/Scripts/python.exe` 全路径调用，PowerShell 与 Git Bash 均可执行，无需激活虚拟环境。

### 3.2 配置文件

复制 `.env.example` 为 `.env` 后按需修改。配置项分五组，均读取自环境变量或 `backend/.env`，代码中不出现密钥字面量：

| 组 | 关键项 | 默认值 |
|---|---|---|
| 应用 | `DEBUG`、`LOG_LEVEL`、`CORS_ORIGINS` | `false`、`INFO`、`http://localhost:5173,...` |
| LLM 网关 | `LLM_API_KEY`、`LLM_BASE_URL`、`LLM_MODEL`、`LLM_MOCK` | 空、百炼兼容入口、`qwen-plus`、`false` |
| 存储 | `BUSINESS_DB_PATH`、`APP_DB_PATH` | `data/ecommerce.db`、`data/app.db` |
| SQL 安全 | `SQL_TIMEOUT_SECONDS`、`SQL_MAX_ROWS`、`SQL_MAX_RETRY`、`SQL_SCAN_LIMIT` | 10.0、1000、3、20000000 |
| 会话 | `HISTORY_WINDOW`、`CHECKPOINTER` | 6、`memory` |

`LLM_MOCK` 是首次启动最容易踩的一项：默认 `false`，未配 `LLM_API_KEY` 时调用会失败。**没有密钥的离线环境必须显式置 `true`**，此时由桩实现按固定模板生成 SQL，整条链路仍可端到端跑通，用于验证编排、守卫与图表，而结论的自然语言质量不代表真实模型水平。

### 3.3 造数

```bash
./.venv/Scripts/python.exe data/seed.py
```

脚本固定随机种子（`SEED = 20260914`），生成 2000 用户、500 商品、12000 订单，时间范围自 2025-01-01 至造数当日。重复执行结果一致，因此演示数据与评测结果可复现。加 `--keep` 参数则在库已存在时跳过。

## 四、启动与自检

```bash
./.venv/Scripts/python.exe -m uvicorn app.main:app --reload --port 8000
```

启动时做一次预热：加载语义层、装配容器、编译 LangGraph 图。语义层配置错误会在这一阶段直接抛出并终止进程，而不是等到用户提问才暴露。

启动后按三项自检：

```bash
curl.exe http://127.0.0.1:8000/api/health
```

返回 `llm_mock`、`model`、`checkpointer`、`metrics`、`tables` 五项。其中 `llm_mock` 为 `true` 时日志会打出告警，提示当前是桩实现模式。

```bash
curl.exe http://127.0.0.1:8000/api/semantic/health
```

对比语义层登记项与库内实际表名，`consistent` 为 `true` 表示一致。`missing_in_semantic`（库里有、YAML 没登记）与 `missing_in_db`（YAML 登记了、库里没有）两个字段直接指出差异位置，任一非空都要回到 `tables.yaml` 修正。

```bash
curl.exe "http://127.0.0.1:8000/api/semantic/recall?q=上个季度华东区各品类的成交总额&with_context=false"
```

验证典型问法的召回结果是否覆盖问题中的指标、维度与时间词。漏召回时先补 `synonyms.yaml` 的同义词。

### 启动失败的两类原因

| 现象 | 原因 | 处理 |
|---|---|---|
| `FileNotFoundError` | 业务库未生成 | 执行 `data/seed.py`。`main.py` 的 lifespan 会直接打印这条修复提示 |
| `SemanticError`，进程退出 | 语义层校验未过 | 进程拒绝启动，错误清单含具体字段与表名，逐条修 YAML 后重启 |

## 五、主流程：一次完整问答

界面可用后的正常路径共六步。

### 5.1 新建会话

点「新建会话」，拿到一个会话 ID。该 ID 同时是 LangGraph Checkpointer 的 `thread_id`，多轮上下文按这个键在图内部累积，接入层不需要自己维护对话历史。

### 5.2 提问

在输入框输入中文问题。问题应包含指标、维度、时间范围三类信息中的至少两类，否则走澄清分支。

| 组成 | 说明 | 例子 |
|---|---|---|
| 指标 | 要算什么 | 成交总额、订单数、退款率、客单价 |
| 维度 | 按什么分组 | 按商品类目、按渠道、按城市 |
| 时间 | 统计区间 | 上个月、近7天、2025 年第三季度 |
| 筛选 | 额外取值限制 | 只看已支付订单、只看华东 |
| 排序与条数 | 要前几名 | 前 10 名、按金额降序 |

相对时间词共 22 个，由代码换算成具体日期区间后写进提示词，左闭右开：今天、昨天、本周、上周、本月、这个月、上个月、上月、本季度、这个季度、上季度、上个季度、今年、本年度、去年、去年同期、近7天、近30天、近三个月、近半年、上半年、下半年。

词条为精确匹配，写法需与配置一致：配置里是「近7天」而非「最近 7 天」。「上个月」按上一个自然月换算，不等于最近 30 天。

### 5.3 观察阶段进度

提交后输入框禁用，阶段指示按 SSE 到达顺序逐条追加：

| 节点 | 标签 |
|---|---|
| `route` | 理解问题 |
| `retrieve` | 检索口径 |
| `generate` | 生成查询 |
| `validate` | 安全校验 |
| `execute` | 执行查询 |
| `fix` | 修正查询 |
| `visualize` | 绘制图表 |
| `summarize` | 分析结果 |
| `respond` / `clarify` / `give_up` | 回复 / 反问 / 放弃 |

阶段数量不固定：校验或执行失败时会插入 `fix` 并回到 `validate` 重走；闲聊只经过 `route` 就进入终态；信息不足时进入 `clarify`，不执行后续节点。

### 5.4 读结果

回答卡片结构固定，顺序为：阶段指示（完成后收起为一行）→ 结论文本与要点 → 口径标签 → 图表 → SQL 折叠面板 → 结果表格。

建议的读取顺序是：先看结论，再看口径标签确认统计范围，最后看图表与表格，需要核对时展开 SQL 面板。数字对不对，第一判断依据在口径标签，不在图表。

### 5.5 追问

第二轮可以直接说「那上个月呢」「按渠道拆开」，`route` 节点在识别意图的同时把问题补全为完整表述后交给下游。上下文由 Checkpointer 按 `thread_id` 累积，最近 6 轮回灌给模型（`HISTORY_WINDOW`）。

### 5.6 回看

关闭页面后从历史会话回到同一会话，之前的问答、SQL 与图表都在，无需重跑查询。

## 六、结果五件套的解读

### 6.1 结论与要点

`summarize` 节点依据本轮结果集生成，口径边界从语义层召回结果中获取，不允许模型自行补充。结果集为空时给出可读解释（筛选过严、区间内无成交记录、维度取值不一致等），不报错。结论生成调用失败时退回事实陈述，数据与图表照常呈现。

判断准则：结论中不出现结果集以外的数字。

### 6.2 口径标签

语义层登记七个指标，命中后指标显示名与边界说明随结果返回（字段 `metric_used` 与 `caveats`）：

| 指标 | 显示名 | 口径表达式 | 边界说明 |
|---|---|---|---|
| `gmv` | 成交总额 | `SUM(oi.quantity * oi.unit_price)` | 不含已取消与未支付订单；不扣退款 |
| `sales_volume` | 销量 | `SUM(oi.quantity)` | 件数口径，非订单数 |
| `order_count` | 订单量 | `COUNT(DISTINCT orders.id)` | 不 JOIN 明细表，避免一单多商品重复计数 |
| `aov` | 客单价 | 成交总额 / 订单数 | 分母为订单数，非用户数 |
| `refund_rate` | 退款率 | 退款订单数 / 订单数 | 按订单数口径，非金额口径 |
| `paying_users` | 成交用户数 | `COUNT(DISTINCT orders.user_id)` | 区间内多次下单只计一次 |
| `gross_profit` | 毛利 | `SUM(oi.quantity * (oi.unit_price - p.cost_price))` | 成本取当前成本；不含履约与推广费用 |

三处最容易产生分歧的口径：成交总额不扣退款；退款率的分母是订单数而非金额；时间区间左闭右开，SQL 条件为 `>= 起始 AND < 结束`。

### 6.3 图表

图型由后端在 `result.chart.chart_type` 中给出，前端不重新决策。前端右上角的切换只改变渲染形态，不触发重新查询。

| 结果集特征 | 图型 |
|---|---|
| 结果集为空 | 表格 |
| 列数超过 4 或没有数值度量 | 表格 |
| 没有可用于横轴的维度 | 表格 |
| 问占比构成、单维度单度量、行数不超过 12 | 饼图 |
| 首个维度为时间维度 | 折线 |
| 单维度对比、行数不超过 30 | 柱状 |
| 其余维度组合 | 表格 |

决策顺序为模型优先、规则兜底：`visualize` 节点让模型输出图型与字段映射，`chart/builder.py` 校验字段是否真实存在于结果集中，字段对不上时按上表重新决策。因此模型选错图型时不会渲染出空白图表，最多退化为表格。

### 6.4 SQL 面板

面板默认折叠，展开后展示本轮实际执行的语句。核对三处即可：

1. `FROM` 后面的表是否是预期的那几张；
2. `WHERE` 里的时间条件是否与口径标签上的日期一致，是否带上了指标要求的必带条件（例如成交总额要排除已取消订单）。漏掉必带条件比聚合表达式写错更常见，且从结果上更难发现；
3. 聚合表达式是否与指标口径一致。

返回中同时含 `sql` 与 `original_sql` 两个字段。守卫对无 `LIMIT` 或超限的语句会包裹成 `SELECT * FROM (...) AS _guard_limited LIMIT 1000`，此时 `sql` 是改写后语句、`original_sql` 是改写前语句。手工核对用 `original_sql`，它与模型输出一一对应；两条都能复制到 SQLite 命令行执行。

### 6.5 结果表格

| 字段 | 含义 |
|---|---|
| `row_count` | 本轮下发的行数，**不是**结果集的真实命中行数 |
| `truncated` | 为 `true` 表示已被守卫的 `LIMIT` 截断，真实行数大于 `row_count` |
| 落库行数 | 结果集前 200 行（`chat.py` 的 `PERSIST_ROWS`），全量结果已随 SSE 返回 |

需要全量数据时应改为聚合查询，而不是调大上限。

## 七、五条分支路径与判别依据

一轮问答结束后的走向由 `result.status` 判定，取值集合为 `ok`、`clarify`、`chitchat`、`error`。

| `status` | 路径 | 界面表现 | 用户动作 |
|---|---|---|---|
| `ok` | 正常取数 | 完整回答卡片 | 读结果或继续追问 |
| `clarify` | 信息不足反问 | 灰色提示条，列出需补充的信息 | 补充时间范围或维度 |
| `chitchat` | 闲聊 | 常规气泡 + 可用问法示例 | 从示例中选择一个继续 |
| `ok` + `guard_warnings` 非空 | 守卫改写 | 黄色提示条，含规则编号与说明 | 通常无需干预 |
| `error` | 重试耗尽或生成失败 | 红色提示，展示最后一次语句与报错 | 缩小范围、补充口径或换问法 |

守卫规则共七条（R1–R7，外加仓储层一项超时中断 R8）：

| 规则 | 内容 | 行为 |
|---|---|---|
| R1 | 只允许单条语句 | 拦截 |
| R2 | 只允许 SELECT / UNION / EXCEPT / INTERSECT | 拦截 |
| R3 | 语句树中不得出现 DDL / DML / 管理类关键字 | 拦截 |
| R4 | 表必须在语义层登记 | 拦截，提示疑似模型编造 |
| R5 | 字段必须存在于所属表元数据 | 拦截，并给出形近字段提示 |
| R6 | 无 LIMIT 或超限时包裹为最多 1000 行 | 自动改写并提示 |
| R7 | 多表查询必须带连接条件，禁止 CROSS JOIN | 拦截 |
| R8 | 执行超时中断 | 由仓储层 progress handler 实现 |

拦截时展示具体规则编号与原因，例如「R5 字段 oi.price 在表 order_items 中不存在，是否为 unit_price？」，而不是静默失败。R5 的形近字段提示会一并进入 `fix` 节点的修正上下文。

重试配额由 `validate` 与 `execute` 共享，默认上限 3 次（`SQL_MAX_RETRY`），含义是首次生成之外最多再修正 3 次。耗尽后进入 `give_up`，返回最后一次语句与数据库原始报错，不做无限循环。`result.retry_count` 记录实际修正次数，`stages` 数组中每条记录含所处阶段与当时的报错。

## 八、多轮追问的边界

**能接住的**：指代时间（「那上个月呢」「去年同期」）、增删维度（「按渠道拆开」「不看渠道，看类目」）、增减筛选（「只看已完成的」）、改排序与条数（「改成前 5 名」）。

**接不住的**：隔轮指代（第三轮说「再看看它的退款率」而第二轮没有明确的「它」）、跨指标引用（「把上面那个数除以订单数」）、隐含口径切换（上一轮含退款，这一轮说「按净额算」）。

接不住的表现是系统重新生成一条与预期无关的 SQL，或走澄清分支。此时把问题写完整即可，不必重开会话。落库记录的是补全后的问题，回看历史时能看清当时问的是什么。

## 九、历史会话管理

每次问答写入独立的会话库 `data/app.db`，与业务库不共用连接。留档内容包括问题、结论、语句、本轮口径与边界说明、图表配置、结果集前 200 行、行数、耗时与状态。

| 操作 | 接口 |
|---|---|
| 创建 | `POST /api/session` |
| 列表（支持关键词搜索、归档筛选） | `GET /api/session?keyword=&include_archived=` |
| 详情（含全部轮次） | `GET /api/session/{session_id}` |
| 重命名与归档 | `PATCH /api/session/{session_id}` |
| 删除 | `DELETE /api/session/{session_id}` |

归档为软删除：归档后不在默认列表出现，可通过 `include_archived=true` 找回。删除为物理删除，连带清除轮次记录。

一项需要注意的语义：`CHECKPOINTER` 默认为 `memory`，多轮上下文保存在进程内存中，**重启后上下文丢失**，但已落库的问答记录仍在。若需要跨重启保留多轮上下文，把 `CHECKPOINTER` 改为 `sqlite`。

## 十、无界面时的等价接口流程

前端未就绪时，用以下四步走完同一条链路。HTTP 请求用 `curl.exe`，避开 PowerShell 中 `curl` 指向 `Invoke-WebRequest` 的别名问题。

**第一步，创建会话。**

```bash
curl.exe -X POST http://127.0.0.1:8000/api/session ^
  -H "Content-Type: application/json" -d "{\"title\":\"演示会话\"}"
```

返回中的 `id` 即后续使用的 `session_id`。

**第二步，非流式提问。**

```bash
curl.exe -X POST http://127.0.0.1:8000/api/chat/sync ^
  -H "Content-Type: application/json" ^
  -d "{\"session_id\":\"<上一步的 id>\",\"question\":\"上个季度华东区各品类的成交总额\"}"
```

返回结构与 SSE 的 `result` 事件一致，字段见第十节末的表。评测脚本与批量验证走这个接口。

**第三步，流式提问（观察节点进度）。**

```bash
curl.exe -N -X POST http://127.0.0.1:8000/api/chat ^
  -H "Content-Type: application/json" ^
  -d "{\"session_id\":\"<id>\",\"question\":\"那上个月呢\"}"
```

`-N` 关闭缓冲，否则进度会被攒到最后一次性吐出。事件类型：

| 事件 | 时机 | 负载 |
|---|---|---|
| `stage` | 每过一个节点 | 节点名、标签、说明、耗时 |
| `result` | 本轮结束 | 结论、语句、口径、结果集、图表配置 |
| `error` | 未预期异常 | 错误文案 |
| `done` | 流结束 | 空对象，前端据此关闭连接 |

**第四步，回看。**

```bash
curl.exe http://127.0.0.1:8000/api/session/<id>
```

`turns` 数组中每一轮含 `question`、`answer`、`sql`、`metrics`、`chart`、`result`、`row_count`、`elapsed_ms`、`status`。

`result` 事件（与 `/api/chat/sync` 返回）的关键字段：

| 字段 | 说明 |
|---|---|
| `status` / `intent` | 终态状态与意图判定 |
| `answer` / `insight` / `highlights` | 结论文本、经营解读、要点列表 |
| `sql` / `original_sql` | 实际执行语句、守卫改写前语句 |
| `sql_error` / `guard_warnings` | 数据库原始报错、守卫提示 |
| `columns` / `rows` / `row_count` / `truncated` | 结果集与截断标记 |
| `chart` | 图表配置，含 `chart_type` 与字段映射 |
| `metric_used` / `caveats` / `time_range` | 本轮命中的指标、边界说明、时间区间 |
| `retry_count` / `query_elapsed_ms` | 修正次数、查询耗时 |
| `stages` | 本轮全部节点记录 |

## 十一、结果存疑时的三步核查

数字与预期不一致时，按下面三步定位，比反复改问法有效。

**第一步，比对 SQL 与口径标签。** 若 SQL 中的聚合表达式与指标口径不同，说明模型没有采用召回的口径，属于生成问题。

**第二步，查召回了什么。**

```bash
curl.exe "http://127.0.0.1:8000/api/semantic/recall?q=<原问题>&with_context=false"
```

接口返回命中的指标、表、维度、匹配词与时间区间。指标未命中多半是同义词配置缺失，需往 `synonyms.yaml` 补词。

**第三步，把 SQL 复制到 SQLite 命令行手工执行。** 这一步用于区分"模型写错"与"口径本身就是这个数"。很多看似错误的数字，实际是口径定义与提问者的预期不同。

## 十二、评测流程

评测集目录 `backend/eval/` 已建，用例与脚本待补。设计目标为每条用例含问题与验证方式，覆盖七个指标与主要维度，脚本一键输出可执行率与准确率汇总。

评测通过 `POST /api/chat/sync` 驱动，便于脚本批量调用。按项目约定，先跑基线再设目标值，不预先设定数字。

## 十三、运维操作

| 操作 | 方式 |
|---|---|
| 换模型 / 换服务商 | 改 `.env` 的 `LLM_BASE_URL` 与 `LLM_MODEL`，重启。代码无需改动 |
| 从桩实现切到真实模型 | 填入 `LLM_API_KEY` 并把 `LLM_MOCK` 置 `false`，重启 |
| 调整安全边界 | 改 `SQL_TIMEOUT_SECONDS`、`SQL_MAX_ROWS`、`SQL_MAX_RETRY`、`SQL_SCAN_LIMIT` |
| 重建样例库 | 执行 `data/seed.py`，固定种子保证结果一致 |
| 备份 | 复制 `data/ecommerce.db` 与 `data/app.db`。业务库可由 `seed.py` 重建，会话库不可 |
| 查模型用量 | `GET /api/stats` 返回本进程内的调用次数与 token 用量 |
| 部署到 Nginx | 见《18-Nginx_HTTPS服务配置语料库.md》。SSE 需关闭缓冲，`chat.py` 已在响应头带 `X-Accel-Buffering: no` |

日志格式含时间戳、级别、模块名。启动时若处于桩实现模式会打出告警，提示当前 SQL 来自固定模板。

## 十四、演示顺序建议

课程演示按以下顺序走，覆盖全部关键能力：

1. **单指标单维度**：最近 30 天各渠道的订单数。展示基础链路与柱状图。
2. **时间趋势**：2025 年每月的成交总额。展示折线图与相对时间换算。
3. **追问**：改成按商品类目。展示多轮上下文与指代接住。
4. **触发澄清**：只问「看看销售」。展示澄清分支的回问。
5. **触发拦截**：问一个会命中守卫规则的问题，例如让模型查一张未登记的表。展示拦截文案与规则编号。
6. **透明性**：展开 SQL 面板，打开 `/api/semantic/health`。展示口径可追溯与一致性自检。

## 十五、常见卡点

| 现象 | 原因 | 处理 |
|---|---|---|
| 启动报 `FileNotFoundError` | 业务库未生成 | 执行 `data/seed.py` |
| 启动报 `SemanticError`，进程退出 | 语义层与库不一致 | 按错误清单修 YAML，改完重启 |
| 提问后一直无响应 | 未配密钥且 `LLM_MOCK` 为 `false` | 置 `LLM_MOCK=true` 或配置 `LLM_API_KEY` |
| 生成的 SQL 明显是模板 | `LLM_MOCK` 为 `true` | 配密钥后置 `false` 并重启 |
| 指标没有召回 | 同义词未覆盖问法 | 补 `synonyms.yaml`，再查 `/api/semantic/recall` 验证 |
| 「最近 7 天」没生效 | 相对时间词精确匹配，配置中是「近7天」 | 改用配置中的写法 |
| 结果行数恰好是 1000 | 被守卫的 `LIMIT` 截断 | `truncated` 为 `true`，改为聚合查询 |
| 重启后追问接不住 | `CHECKPOINTER` 为 `memory`，上下文在内存中 | 改为 `sqlite` |
| 界面打不开，只有 API | `frontend/dist` 不存在 | 执行 `npm run build` 或单独启动 Vite |
