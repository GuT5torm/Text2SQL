# STORY.md · Text2SQL 电商数据分析 Agent 答辩

## 一、意图对齐

- **场景**：课程/毕业答辩，12–15 分钟自述，之后是提问环节。听众是评审老师，多数不做数据工程，但会追问「你怎么知道它算得对」。
- **核心目标**：讲完后评审相信三件事——这个系统把「口径」当成一等公民而不是靠模型猜；它在算错之前会拦住自己；关键数字有可核对的出处。功能清单不是重点，可信性的实现路径才是。
- **页数**：16 页。封面、目录、结尾三个仪式页，13 个内容页。
- **视觉调性**：学术风，蓝白为基底，证据优先，不做营销表达。命中预设学术风，不另出 DESIGN.md。
- **内容边界**：
  - 必讲：选题痛点、六层架构、十四节点状态机、语义层口径配置、九条守卫规则、三层可信性设计、实测缺陷修复、评测方法与数据来源。
  - 不讲：模型训练与微调、prompt 逐字内容、部署运维细节、与同类产品的横向对比。
  - 禁碰：未经实测的数值、编造的数据来源、把「桩模式」数据说成真实模型结果。

## 四、数据与判据的对应关系

页面上的每个数字都写明来源，以下为唯一出处：

- 指标 7 个、表 6 张、模型 qwen-plus：`GET /api/health` 实测返回。
- 单元测试 548 passed：2026-10-16 本机 `pytest -q` 实跑（`LLM_MOCK=true`）。
- 评测十二组 109 条：桩模式 `backend/eval/report-baseline-2026-10-16.json`（2026-10-16 16:32，时间锚点 2026-10-14，通过 104、跳过 5、未通过 0）；真实模型 `backend/eval/report-real-fixed-assert.json`（2026-09-22 11:07，pipeline 组 10 条全通过；同日上午初版为 8/10，两条口径漂移失败是补入口径签名校验的直接起因）。两套口径在 P15 分别标注。
- 查询延迟 p50 9.8ms / p95 22.9ms：`report-baseline-2026-10-16.json` 的 telemetry，36 次采样。
- 九条守卫规则 R1–R9：`backend/app/db/guard.py` 模块文档字符串。
- 十四个节点与六条终态出口：`backend/app/agent/graph.py` 的 `add_node` / `add_conditional_edges` / `add_edge`。
- 依赖版本：`backend/.venv` 的 `importlib.metadata` 与 `frontend/package.json` 实测。
- 缺陷前后偏离度 +8.59% / −10.19%：`CHANGELOG.md` T44 节，端到端实跑记录。
- 六张运行截图：2026-09-29 真实模型（`LLM_MOCK=false`，qwen-plus）跑出的界面，存于 `assets/`。

## 五、不写进页面的话

- 不写「准确率 90%」这类没有分母的结论。评测给出的是一组通过率，且注明是桩模式还是真实模型。
- 不写「提升效率 X 倍」。项目没有做对照组测量，没有可比的基线。
- 不把桩模式的 10/10 说成模型能力。桩模式验证的是链路完整性，模型能力由 P15 的真实模型一行单独说明。
